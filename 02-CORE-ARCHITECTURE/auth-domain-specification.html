Opening Statement

Preamble & Stack Decision Framework

Constitutional Statement

Authentication is the first system. Before a user can apply for funding, submit a service request, make a deposit, or negotiate a collaboration, they must prove who they are. If authentication fails—if it is inconsistent, insecure, or confusing—every system built atop it is compromised before it begins.

This specification governs how identity is verified, how sessions are established and maintained, and how access is controlled across every KSDRILL SA platform. The four flagship systems serve as reference implementations. This document maps directly to the Auth Implementation Blueprint v1.1—every constitutional rule has a corresponding implementation section.

Amendments follow the Constitutional Order protocol only. No implementation-level decision supersedes this document.

The Stack Decision Framework Impl §1

Before authentication rules are applied, a system's technology stack must be determined. This decision is made once at system design time and is immutable. The decision is driven by requirements, not preference. Every new system documents its stack selection in an Architecture Decision Record.

Part 0

Authentication Strategy Selection

Rules A1–A4 · Both Stacks · Foundation Impl §1
A1One Strategy Per Stack, Never Mixed
CriticalBoth Stacks

Every KSDRILL SA system uses exactly one authentication strategy, determined by its technology stack. No system runs two strategies simultaneously. Next.js Stack: NextAuth.js with database-backed sessions in PostgreSQL. Angular+FastAPI Stack: JWT-based authentication issued and validated by FastAPI.

Next.js · Maphophe & SyncUp
NextAuth.js with Prisma Adapter. Opaque session tokens in HttpOnly cookies. Instant revocation by deleting session rows from PostgreSQL.
Angular+FastAPI · FundsLink & Reserve Bank
RS256-signed JWT. Access tokens in Angular memory (15 min). Refresh tokens in HttpOnly cookies (7 days). Rotation with replay detection.
A2All Authentication Data in PostgreSQL
CriticalBoth Stacks

Every piece of authentication data resides in PostgreSQL. Redis is a cache, never a primary store. MongoDB is never used for auth data—even on the Angular stack where MongoDB exists for AI-generated content. FundsLink: PostgreSQL stores user accounts; MongoDB stores AI-generated scholarship content only. Reserve Bank: PostgreSQL stores accounts and transactions; MongoDB stores application logs. Auth data requires ACID guarantees.

Implementation: Impl Blueprint §1.2–1.9 — All auth tables defined in PostgreSQL only. Redis structures §1.10 are cache-only with TTLs.

A3Password Hashing — bcrypt Minimum Cost 12
CriticalBoth Stacks

Every password on every system hashed with bcrypt at cost factor 12+. Forbidden: MD5, SHA-1, SHA-256, reversible encryption, plain text. Cost factor from BCRYPT_ROUNDS env var—never hardcoded. At cost 12, each hash ~300ms—imperceptible to users, computationally infeasible for attackers. Maphophe: Residents and ward admins protected. Reserve Bank: Account holders protected. Cost factor can increase without code changes.

Implementation: Impl Blueprint §2.1 step 4, §4.1 step 4, §6.1, §8.2 — bcrypt with environment-driven cost factor.

A4Rate Limiting — Three Protection Layers
CriticalBoth Stacks

Layer 1: 10 requests/IP/15min — Redis counter with TTL. Layer 2: 5 failed attempts → account locked 15min + security email to verified address. During lock, even correct credentials return identical error. Layer 3: 1000 auth requests/min globally. Reserve Bank: Attacker blocked at Layer 1 from single IP or Layer 2 when distributed across IPs.

Implementation: Impl Blueprint §1.10 Redis structures, §8.4 — Three-layer implementation with Redis fallback behavior.

Part 1 — Next.js Stack Only

NextAuth.js Strategy

Rules A5–A12 · Maphophe · SyncUp · Future Next.js Systems Impl §4–5
Rules A5–A12 apply exclusively to Next.js systems. Angular+FastAPI systems use Part 2 (A13–A20).
A5Database Sessions, Never JWT Sessions
CriticalNext.js Only

Prisma Adapter with session:{strategy:"database"}. JWT session strategy forbidden. Database sessions revoke instantly—deleting row invalidates all devices. Maphophe: Compromised ward admin changes password → attacker logged out everywhere immediately—not after token expiry. SyncUp: Creator account accessed from shared device → logout terminates session instantly.

Implementation: Impl Blueprint §1.6 Session table, §4.1 step 5, §5.2 session management API.

A6HTTP-Only Session Cookies
CriticalNext.js Only

HttpOnly, Secure, SameSite=Lax. Never localStorage/sessionStorage. XSS attacks cannot steal HttpOnly cookies. SyncUp: Malicious script in negotiation message cannot access session cookie—creator session remains secure.

A7Middleware-Based Route Protection
Next.js Only

Middleware verifies session on every protected route. API routes independently verify. Maphophe: Residents browse announcements without auth. Clicking "Submit Request" triggers middleware check—expired sessions redirect to login with callbackUrl preserved.

A8Session Callback — Safe Fields Only
Next.js Only

Expose only: id, email, name, role, image. Never: password_hash, reset_token, deleted_at. Session object is client-accessible—treated as public document.

A9Session Lifetime — Environment Configurable
Next.js Only

SESSION_MAX_AGE_SECONDS env var (default 30 days). Sliding expiration on active use. Daily cron cleans expired sessions. Maphophe: Daily visitors stay logged in. 31-day absentees must re-authenticate.

A10OAuth Through NextAuth Exclusively
Next.js OnlyOAuth

Custom OAuth flows forbidden. NextAuth handles PKCE, state validation, token exchange. Maphophe: Google. SyncUp: Google + GitHub.

Implementation: Impl Blueprint §4.2 — Full OAuth flow with institutional domain check.

A11CSRF Protection Never Disabled
Next.js Only
A12Email Verification — Configurable Mode
Next.js Only

Strict: no access until verified (Reserve Bank standard). Progressive: limited access, sensitive ops require verification (FundsLink, Maphophe). Verification tokens expire 24h. Resend limited to 3/hour/user.

Implementation: Impl Blueprint §3 — Complete verification flow with token lifecycle.

Part 2 — Angular+FastAPI Only

JWT Authentication Strategy

Rules A13–A20 · FundsLink · Reserve Bank · Future Angular Systems Impl §6–7
A13RS256-Signed JWT Issued by FastAPI
CriticalAngular+FastAPI

Access Token: 15-min RS256 JWT (sub, role, email, jti, version). Refresh Token: 64-byte random, SHA-256 hashed in DB, raw in HttpOnly/SameSite=Strict cookie scoped to /api/v1/auth. Why RS256: Asymmetric—private key signs (Railway Secrets only), public key verifies (safely distributable). FundsLink: Students receive 15-min tokens via FastAPI. Reserve Bank: Account holders authenticated seamlessly across banking sessions.

Implementation: Impl Blueprint §1.5 RefreshToken table, §6.1 JWT issuance, §7.1–7.2 refresh flow.

A14Split Token Storage — Cookie + Memory
CriticalAngular+FastAPI

Refresh token: HttpOnly cookie (XSS-proof, 7-day life). Access token: Angular memory (readable for Bearer headers, 15-min life, lost on tab close). XSS attack steals access token → 15-min window only. Cannot read refresh token to persist access.

A15HTTP Interceptor — Single Auth Handler
CriticalAngular+FastAPI

Attach Bearer + X-Request-ID. On 401: silent refresh with deduplication. FundsLink: Dashboard loads 3 API calls → one refresh, all retry. Without dedup: Request 2 presents revoked old token → replay detected → user logged out.

Implementation: Impl Blueprint §7.1–7.2 — Complete refresh flow with concurrent deduplication.

A16Refresh Rotation with Replay Detection
CriticalAngular+FastAPI

Every refresh issues new pair, revokes old. Replay detected → revoke ALL tokens for user → Sentry alert → security email → universal logout. Token family chain via replaced_by enables forensic tracing. FundsLink: Stolen token via malicious extension detected on first legitimate refresh.

A17FastAPI Depends() for JWT Validation
Angular+FastAPI

get_current_user: Decode RS256 → verify exp → check JTI deny-list → query User → verify not deleted. require_role(Role): Wraps get_current_user, checks role or ADMIN override. Business logic NEVER checks roles—dependency layer is the sole authorization gate.

A18Logout — Revoke, Deny-List, BroadcastChannel
Angular+FastAPI

Revoke refresh token in PostgreSQL → Add JTI to Redis deny-list (TTL=remaining life) → Clear cookie → Clear Angular memory → BroadcastChannel notifies all tabs. Redis down? Access token valid ≤15min—acceptable risk.

Implementation: Impl Blueprint §7.3 — Coordinated three-step logout.

A19Angular Route Guards — UX Layer, Server Is Authority
Angular+FastAPI
A20Secrets in Railway Secrets Exclusively
CriticalAngular+FastAPI

RS256 keys, bcrypt rounds—all in Railway Secrets. Never committed. Dev/staging/prod separate keys. .env.example lists names with placeholder descriptions only.

Part 3

Role-Based Access Control

Rules A21–A25 · Both Stacks
A21Roles as Database Enums — Never String Literals
CriticalBoth Stacks

PostgreSQL enum types. Base: USER, ADMIN. System-specific: CREATOR (SyncUp), STUDENT/FUNDER (FundsLink), ACCOUNT (Reserve Bank), WARD_ADMIN (Maphophe). ADMIN-only assignment, audit-logged. New accounts default to minimum role via database default.

A22Ownership Verification on Every Resource
CriticalBoth Stacks

Pattern: Authenticate → Authorize → Verify Ownership → Process. FundsLink: Student A cannot view Student B's application even though both have STUDENT role. Reserve Bank: Account holder cannot access another's balance.

A23Authorization at Route Entry, Not Business Logic
Both Stacks
A24Least Privilege Default
Both Stacks
A25Role Change Audit Trail — Immutable History
Both Stacks

Every role change logged: target, old role, new role, actor admin, IP, timestamp, reason. Entries never updated or deleted. Complete history of who had what authority and when.

Part 5

Security Baseline

Rules A28–A32 · Both Stacks Impl §8
A28HTTPS Only in Production
Critical

All auth traffic HTTPS-only. HSTS: max-age=31536000; includeSubDomains. Vercel and Railway enforce by default—never disabled.

A29CORS Locked to Known Origins
Critical

Explicit origin list per environment—never wildcard * in production. Preflight from unlisted origin → 403.

A30Password Reset — Time-Limited, Enumeration-Proof
Both Stacks

32-byte random token, SHA-256 hashed before storage. 1-hour lifetime. One-time use—consumed on success. Always identical response: "If an account exists, a reset link has been sent." Post-reset: all sessions/refresh tokens revoked (A35).

Implementation: Impl Blueprint §5.1 (Next.js), §6.2 (Angular+FastAPI) — Complete reset flow with token lifecycle.

A31Security Headers on All Responses
Both Stacks
A32Password Strength & Breach Detection
Both Stacks

Min 8 chars, uppercase, digit, special char. Not on common passwords list. Breach check via HIBP API (k-anonymity—full hash never sent). Rejected if found in known breaches. Client-side for UX, server-side authoritative.

Implementation: Impl Blueprint §2.1 steps 2–3, §8.1–8.2 — Full validation pipeline.

Part 6

Audit Logging & Governance

Rules A33–A36 · Both Stacks Impl §1.8
A33Universal Auth Event Logging
Critical

Every auth event logged to AuditLog table: login success/fail (with reason in metadata), logout, token refresh, token theft, password change, password reset, email verification, role change, account lock/unlock, registration, OAuth link/reject. Structured JSON, append-only, no deleted_at column. Immutable retention. Enables queries like "How many OAuth vs password logins this month?"

Implementation: Impl Blueprint §1.8 — Complete AuditLog table schema with 20 event types and JSONB metadata.

A34Security Alerts on Threat Indicators
Both Stacks
A35Session Invalidation on Password Change
Both Stacks

Next.js: DELETE FROM Session WHERE userId=?. Angular: UPDATE RefreshToken SET revoked_at=NOW() WHERE user_id=? AND revoked_at IS NULL + JTI deny-list. All devices logged out immediately.

A36Cross-Constitution Governance
Critical

Any auth change requires Backend-Review-Required + Frontend-Review-Required labels. CI fails without both. Strategy-level changes require documented security review. Auth touches every system layer—no single team can assess full impact.

Forbidden Patterns

Constitutional Violations

FP01–FP20 · Build Failure or Merge Rejection

The following patterns are constitutional violations across all KSDRILL SA systems. Violation = build failure or merge rejection.

FP01Mixed auth strategies on one system
FP02Authentication data in MongoDB or non-PostgreSQL store
FP03Non-bcrypt password hashing or below cost factor 12
FP04Missing rate limiting on any authentication endpoint
FP05JWT session strategy on Next.js (database sessions only)
FP06Refresh tokens in localStorage or sessionStorage
FP07Access tokens in HttpOnly cookies on Angular stack
FP08No refresh token rotation
FP09Missing replay detection on token refresh
FP10Hardcoded role strings instead of enum constants
FP11Missing ownership verification on user-owned resources
FP12CORS wildcard in production
FP13Reset tokens stored in plain text
FP14User enumeration via distinguishable responses
FP15Sessions not revoked on password change
FP16Secrets committed to version control
FP17Sensitive data in JWT payload beyond defined claims
FP18Auth changes without cross-constitution review
FP19Missing audit logging for any authentication event
FP20Custom OAuth implementation on Next.js stack
