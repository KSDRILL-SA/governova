§ Part 1 — Naming & Structure (D1-D7a)
Purpose

Consistent, self-documenting database schema with modern PostgreSQL features.

PART 1 / D1-D7aNaming & Structure5 Critical · 2 High · 1 Medium
D1Table Names — Plural, snake_caseCritical

Table names MUST be lowercase, snake_case, PLURAL (e.g., users, user_sessions, audit_logs). Junction tables use {singular}_{plural} format (e.g., user_organizations).

Violation
User, userSession, AuditLogs
Compliance
users, user_sessions, audit_logs
D2Column Names — snake_caseCritical

Column names MUST be lowercase, snake_case. Use @map() in Prisma to map camelCase field names to snake_case columns.

Violation
createdAt, PasswordHash, userId
Compliance
created_at, password_hash, user_id
D3Primary Keys — UUID v7Critical

Every table MUST have a primary key named id using UUID v7 (time-sortable UUID). Use @default(dbgenerated("gen_random_uuid()")) or uuid_generate_v7() extension.

⚡
v2.0 CHANGE: UUID v7 replaces cuid()/uuid() for time-sortability and better index performance.
D4Foreign Keys — {table}_id FormatCritical

Foreign key columns MUST follow format: {singular_table_name}_id (e.g., user_id, session_id). Self-referential FKs use parent_{table}_id or {role}_{table}_id.

D5Required Timestamps + Version ColumnCritical

Every table MUST have created_at, updated_at, AND version Int @default(1) for optimistic concurrency control.

⚡
v2.0 ADDITION: version column for optimistic locking.
D6Soft Delete — deleted_at + deleted_byCritical

Tables that require soft delete MUST have deleted_at AND deleted_by for audit trail. Required for user data and audit logs.

⚡
v2.0 ADDITION: deleted_by for audit compliance.
D7Boolean Column NamingHigh

Permanent states: active, verified, paid. Transient states: is_pending, is_processing. Existence: has_subscription, has_verified_email.

D7aJSONB Column StandardsHigh

Every JSON column MUST have a comment documenting expected structure. Use @db.JsonB for performance.

§ Part 2 — Indexing Strategy (D8-D14a)
Purpose

Performance without waste. Smart indexing for modern query patterns.

PART 2 / D8-D14aIndexing Strategy2 Critical · 5 High · 1 Medium
D8Foreign Key IndexesCritical

Every foreign key column MUST have an index. Multi-column FKs MUST be indexed in the same order.

D9Soft Delete IndexCritical

Every deleted_at column MUST have an index. Use partial index for active records: WHERE deleted_at IS NULL.

D10Created At Index — Expression for Date QueriesHigh

Use expression indexes for date truncation: CREATE INDEX idx_events_day ON events ((date_trunc('day', created_at))).

D11Remove Unused IndexesHigh

Indexes with idx_scan = 0 for 30 consecutive days MUST be removed.

D12Maximum Indexes GuidelineMedium

Write-heavy tables (1000+ writes/sec): ≤5 indexes. Read-heavy: ≤10 indexes. Monitor dead tuple ratio.

D13Composite Index CommentsHigh

Composite indexes with 3+ columns MUST have a comment explaining column order and query pattern.

D14aBRIN Indexes for Time-Series DataHigh

Tables with append-only time-series data (>1M rows) MUST use BRIN indexes instead of B-tree for timestamp columns.

🆕
v2.0 ADDITION: BRIN indexes use 10x less space for time-series data.
§ Part 3 — Data Integrity & Constraints (D15-D18b)
Purpose

Data accuracy, consistency, and security at the database level.

PART 3 / D15-D18bData Integrity & Constraints4 Critical · 3 High
D15NOT NULL Constraints — ExplicitCritical

All columns that cannot be null MUST have explicit NOT NULL constraint. Prefer database-level NOT NULL over application validation.

D16FK ON DELETE and ON UPDATE BehaviorsCritical

Every foreign key MUST define BOTH onDelete AND onUpdate behaviors. Never leave default.

⚡
v2.0 CHANGE: onUpdate now required.
D17No Business Logic in DatabaseCritical

Triggers, stored procedures, views with logic are FORBIDDEN. EXCEPTION: Immutable generated columns allowed for derived data.

D18Check Constraints and PostgreSQL EnumsHigh

Use PostgreSQL ENUM types for fixed value sets that rarely change. Use CHECK constraints for simple validations.

D18aRow-Level Security (RLS)Critical

Tables with multi-tenant data MUST implement Row-Level Security policies with current_setting('app.tenant_id').

🆕
v2.0 ADDITION: RLS for multi-tenancy.
D18bExclusion ConstraintsHigh

Use exclusion constraints with GiST indexes for non-overlapping ranges (bookings, reservations, time slots).

🆕
v2.0 ADDITION: Exclusion constraints prevent double-booking.
§ Part 4 — Data Retention & Purging (D19-D23)
Purpose

Controlled data growth, compliance, and performance.

PART 4 / D19-D23Data Retention & Purging3 Critical · 2 High
D19Audit Log Retention with PartitioningCritical

Audit logs: 90 days retention. Security events: 1 year. MUST be partitioned by month for efficient purging.

⚡
v2.0 CHANGE: Partitioning required for audit logs.
D20Soft Delete Purge with ArchivalHigh

Soft-deleted records MUST be permanently purged after 30 days. Archive to S3/Glacier before deletion. Batch 1000 rows per transaction.

D21Session PurgeHigh

Expired sessions MUST be purged 7 days after expiry. Partition if exceeding 1M rows.

D23Purge Jobs RequirementsCritical

Every table with soft delete or time-based retention MUST have an automated idempotent purge job. Run off-peak, batch commits (≤1000 rows), with monitoring.

§ Part 5 — Backup & Recovery (D24-D29b)
Purpose

Data durability, recoverability, and disaster readiness.

PART 5 / D24-D29bBackup & Recovery2 Critical · 5 High · 1 Medium
D24Automated Daily BackupsCritical

Automated daily backups MUST be configured for production database during lowest traffic period.

D25Backup Retention — 30d Daily + 12m Monthly + Cross-RegionHigh

Retention: 30 days daily, 12 months monthly snapshots. Copy to secondary region for DR.

D26Recovery Time Objective (RTO): 4 HoursHigh

Database MUST be restored and validated within 4 hours of disaster declaration.

D27Recovery Point Objective (RPO): 15 MinutesHigh

RPO: 24 hours with daily backups, 15 minutes with PITR enabled.

D28Point-in-Time Recovery (PITR) RequiredCritical

PITR MUST be enabled for production databases. Provides 15-minute RPO.

⚡
v2.0 CHANGE: PITR now critical requirement.
D29Backup Restoration Test — QuarterlyHigh

Backup restoration test MUST be performed quarterly with data validation.

D29aWAL ArchivingHigh

WAL MUST be archived to S3 or equivalent object storage for disaster recovery.

🆕
v2.0 ADDITION: WAL archiving to S3.
§ Part 6 — Security & Encryption (D30-D34c)
Purpose

Protect data from unauthorized access and ensure compliance.

PART 6 / D30-D34cSecurity & Encryption6 Critical · 2 High
D30Encryption at RestCritical

Database-level encryption at rest MUST be enabled for production. Use AWS KMS or equivalent.

D31Least Privilege Database RolesCritical

Minimum FOUR roles: app_user (CRUD), app_admin (elevated), migration_user (DDL), backup_user (read-only).

⚡
v2.0 CHANGE: Added app_admin role.
D32No Public Database AccessCritical

Production database MUST NOT have public IP address. Access only via VPC private subnet.

D33TLS/SSL Required — verify-fullCritical

All database connections MUST use TLS/SSL with sslmode=verify-full and certificate validation.

D34Secrets Management — Rotation Every 90 DaysCritical

Database credentials MUST NOT be hardcoded. Use AWS Secrets Manager. Rotate every 90 days.

D34aQuery Audit LoggingHigh

Production MUST log all DDL statements and queries from admin roles to a secure audit schema.

🆕
v2.0 ADDITION: Query audit logging for DDL.
D34bConnection Pooling — PgBouncerHigh

Production MUST use connection pooling (PgBouncer in transaction mode). pool_size = core_count × 2.

🆕
v2.0 ADDITION: Connection pooling required.
D34cData Masking for PIICritical

PII columns MUST have masking policies for non-admin application roles.

🆕
v2.0 ADDITION: PII data masking for GDPR/CCPA.
§ Part 7 — Migration & Seeding (D35-D38a)
Purpose

Safe, repeatable, reversible schema changes with zero downtime.

PART 7 / D35-D38aMigration & Seeding3 Critical · 2 High
D35Migration Naming — Timestamp PrefixCritical

Migration files MUST follow format: YYYYMMDDHHMMSS_description.sql (e.g., 20260408120000_add_users_table.sql).

D36Zero-Downtime MigrationsCritical

All migrations MUST be zero-downtime compatible using blue-green pattern. Document rollback for each step.

⚡
v2.0 CHANGE: Zero-downtime required for all migrations.
D37Destructive Migration ApprovalCritical

Destructive migrations (DROP, TRUNCATE) REQUIRE tech lead approval, justification, rollback plan, and label.

D38Seed Data — Idempotent, Realistic, ValidatedHigh

Seed data MUST be idempotent (upsert), realistic (Faker.js), and validated in CI.

D38aMigration Lock Timeout — 2 SecondsHigh

All migrations MUST set lock_timeout = '2s' to prevent blocking production traffic.

🆕
v2.0 ADDITION: lock_timeout prevents blocking.
§ Part 8 — Observability & Monitoring (D39-D42)
Purpose

Database health visibility, performance optimization, and proactive alerting.

PART 8 / D39-D42Observability & Monitoring1 Critical · 2 High · 1 Medium
D39Slow Query Logging — 100ms ThresholdCritical

Production MUST log all queries exceeding 100ms. Aggregate weekly, review top 10 slow queries.

🆕
v2.0 ADDITION: Slow query logging and review.
D40Deadlock MonitoringHigh

Deadlocks MUST be logged and monitored. Alert when rate exceeds 5 per minute or 10 per hour.

🆕
v2.0 ADDITION: Deadlock monitoring and alerting.
D41Connection Pool MetricsHigh

Monitor active connections, idle connections, waiting clients. Alert when waiting > 10 or active > 80% of max.

🆕
v2.0 ADDITION: Connection pool monitoring.
D42Table Bloat DetectionMedium

Monitor table and index bloat weekly. Alert when dead tuple ratio exceeds 20%.

🆕
v2.0 ADDITION: Bloat detection and alerting.
