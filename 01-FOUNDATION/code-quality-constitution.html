§ Part 1 — Code Formatting & Linting (CQ1–CQ5)
Purpose

Consistent, automated code style. No manual formatting debates. All style decisions are made by tools, not humans.

PART 1 / CQ1–CQ5Code Formatting & Linting3 Critical · 1 High · 1 Medium
CQ1Prettier MUST Be Configured and Run on All CodeCritical

Prettier configuration is mandatory. All code must be formatted before commit. No exceptions. Formatting debates are a tax on productivity — automate them away.

CQ2ESLint Strict Rules MUST Be ConfiguredCritical

ESLint with strict rule set (including security, best practices, and accessibility rules) is mandatory. Recommended: eslint-plugin-security, eslint-plugin-unicorn, eslint-plugin-jsx-a11y.

CQ3Linting MUST Pass Before CI PassesCritical

CI pipeline must fail if any linting error exists. Zero warnings allowed in production branches.

CQ4Pre-commit Hooks MUST Run (Husky + lint-staged)High

Pre-commit hooks must run Prettier and ESLint on staged files. Never commit unformatted code.

.husky/pre-commit
#!/bin/sh
npx lint-staged
CQ5Max Line Length: 100 CharactersMedium

Maximum line length is 100 characters. Exceptions allowed for long URLs or generated code with explicit comment.

§ Part 2 — TypeScript Strictness (CQ6–CQ10)
Purpose

Type safety, catch errors at compile time. TypeScript without strict mode is just JavaScript with extra steps.

PART 2 / CQ6–CQ10TypeScript Strictness4 Critical · 1 High
CQ6strict: true MUST Be EnabledCritical

TypeScript's strict: true mode is mandatory. This enables all strict type-checking options.

CQ7noImplicitAny: true MUST Be EnabledCritical

Implicit any types are forbidden. Every parameter and variable must have a defined type or be explicitly typed as unknown.

CQ8strictNullChecks: true MUST Be EnabledCritical

null and undefined must be handled explicitly. No more "undefined is not a function" at runtime.

CQ9any Type FORBIDDEN — Documented Exceptions OnlyCritical

The any type is forbidden. Use unknown with type guards or proper types. Exception requires ESLint disable comment with justification.

✅ Correct pattern
// Use unknown with type guard
function processData(data: unknown) {
  if (isValidData(data)) {
    // data is now properly typed
  }
}
CQ10@ts-ignore FORBIDDEN — Use @ts-expect-errorHigh

@ts-ignore is forbidden. Use @ts-expect-error with an explanation comment instead.

§ Part 3 — Code Review Process (CQ11–CQ16)
Review Focus
  • ✅ Correctness
  • ✅ Security
  • ✅ Performance
  • ✅ Maintainability
  • ✅ Test coverage
  • ❌ Formatting (automated)
  • ❌ Style (automated)
PART 3 / CQ11–CQ16Code Review Process2 Critical · 3 High · 1 Medium
CQ11Every PR MUST Have at Least One Approving ReviewCritical

No self-merging. Every pull request requires at least one approving review before merge. Branch protection must enforce this.

CQ12PR Author MUST Respond to All Comments Before MergeCritical

All review comments must be addressed (resolved, replied to, or marked as follow-up) before merging. Unresolved discussions block merge.

CQ13Review Focus: Correctness, Security, Performance, Maintainability, Test CoverageHigh

Reviewers focus on substance, not style. Style and formatting are automated.

CQ14Review SHOULD NOT Focus on Formatting or StyleMedium

Do not comment on formatting or style in code reviews. That's what Prettier and ESLint are for.

CQ15PRs MUST Be Acknowledged Within 24h, Reviewed Within 48hHigh

PRs must be acknowledged within 24 business hours (a simple "Looking at this today" counts). Full review within 48 business hours. Deep Work exception: "Looking EOD" comment counts as acknowledgement.

CQ16Cognitive Load > Line Count — 400-Line Guideline with ExceptionsHigh

PRs should target <400 lines. Exception: PRs with high cognitive load (complex logic changes) require tech lead approval regardless of line count. Low cognitive load PRs (renames, generated code) may exceed 400 lines without approval.

🧠
Cognitive Load Assessment: Rename refactor (any lines) → Auto-approve. Generated code (OpenAPI, migrations) → Auto-approve. Complex algorithm modification → Tech lead approval required.
§ Part 4 — Pull Request Standards (CQ17–CQ20)
PR Template Required Fields
  • 📝 What changed?
  • ❓ Why?
  • 🧪 Testing performed
  • 🤖 AI attribution (new)
  • 📦 Dependency changes
PART 4 / CQ17–CQ20Pull Request Standards1 Critical · 2 High · 1 Medium
CQ17PR Title MUST Follow Conventional CommitsHigh

PR titles must follow Conventional Commits format: feat:, fix:, docs:, style:, refactor:, perf:, test:, chore:.

CQ18PR Description MUST Include: What, Why, Testing Performed, Screenshots (if UI)High

Empty PR descriptions are forbidden. Every PR must explain what changed, why, and how it was tested.

CQ19PR MUST Link to Issue or TicketMedium

Every PR must reference a tracking issue or ticket. This provides context and traceability.

CQ20PR MUST Include Tests for New FunctionalityCritical

New features require new tests (unit, integration, or E2E depending on scope). Bug fixes require regression tests.

§ Part 5 — Documentation Requirements (CQ21–CQ24)
Purpose

Code that explains itself. Comments explain "why" not "what". Exported APIs have documentation.

PART 5 / CQ21–CQ24Documentation Requirements2 High · 2 Medium
CQ21Every Exported/Public Function MUST Have JSDoc/TSDoc CommentHigh

All exported functions, types, and interfaces must have documentation comments. This enables IDE IntelliSense and API documentation generation.

CQ22Complex Logic MUST Have Inline Comments Explaining "Why" (Not "What")High

Comments explain why code exists, not what it does (the code itself should be readable enough for that).

CQ23README MUST Exist in Every Major Package/ServiceMedium

Every package or service must have a README explaining its purpose, setup, and usage.

CQ24ADRs REQUIRED for Significant DecisionsMedium

Architecture Decision Records (ADRs) are required for significant technical decisions. Use Michael Nygard's format.

§ Part 6 — Dependency Management (CQ25–CQ28)
Justification Template
• Why is this dependency needed?
• What alternatives were considered?
• What is the bundle size impact?
• Is the license compatible?
PART 6 / CQ25–CQ28Dependency Management1 Critical · 2 High · 1 Medium
CQ25Dependencies MUST Be Pinned to Exact Versions (No ^ or ~)Critical

Use exact versions ("react": "18.2.0", not "^18.2.0"). Range versions lead to inconsistent builds and unexpected breakage.

CQ26Dependabot (or Equivalent) MUST Be EnabledHigh

Automated dependency updates are required. Dependabot or equivalent must be configured with weekly updates and security patches as immediate PRs.

CQ27Unused Dependencies MUST Be Removed — depcheck in CIHigh

depcheck must run in CI. Unused dependencies fail the build and must be removed.

CQ28New Dependencies MUST Be Justified in PR: Why, Alternatives, Bundle Impact, License CompatibilityMedium

Adding a dependency is a decision with long-term consequences. Justify every new dependency in the PR description and verify license compatibility.

§ Part 7 — Technical Debt Management (CQ29–CQ32)
TODO Format
// TODO(#123): Description @owner
PART 7 / CQ29–CQ32Technical Debt Management3 High · 1 Medium
CQ29TODO Comments MUST Have Issue Link and OwnerHigh

Every TODO comment must reference a tracking issue and assign an owner. TODOs without issues become permanent residents of the codebase.

CQ30Technical Debt MUST Be Tracked in Issue TrackerHigh

All technical debt must have corresponding issues with severity labels and priority.

CQ31Each Sprint MUST Allocate 20% Capacity to Tech Debt ReductionMedium

Protect time for paying down technical debt. 20% of sprint capacity is reserved for debt reduction, refactoring, and maintenance.

CQ32Refactoring PRs MUST Have Zero Functional ChangesHigh

Refactoring PRs must be pure refactors — no behavior changes, no new features, no bug fixes. Separate functional changes into different PRs.

§ Part 8 — Supply Chain Security (CQ33–CQ35) 🆕
Purpose

Proactive defense against dependency attacks and supply chain compromise. Prevent dependency confusion, verify package provenance, and manage flaky tests.

PART 8 / CQ33–CQ35Supply Chain Security2 Critical · 1 High
CQ33Package Provenance Verification — npm audit signatures in CICritical

All production dependencies MUST have verified provenance attestation. npm audit signatures or equivalent MUST run in CI. Fail the build if any package lacks valid signature.

.github/workflows/ci.yml
- name: Verify package signatures
  run: npm audit signatures
CQ34Dependency Confusion Prevention — Scoped Internal PackagesCritical

All internal/private packages MUST be scoped (@company/package). Registry configuration MUST prefer internal registry over public npm. .npmrc MUST be committed and verified.

.npmrc
@acme:registry=https://npm.acme.com
//npm.acme.com/:_authToken=${NPM_TOKEN}
always-auth=true
CQ35Flaky Test Quarantine ProtocolHigh

Any test that fails non-deterministically MUST be immediately quarantined (skipped in CI) and assigned an issue with HIGH priority. Quarantined tests MUST be fixed within the same sprint. Maximum 3 quarantined tests allowed per repository.

🚫
NEVER: "Just re-run CI until it passes" — 5 re-runs on same commit indicates a flaky test. Quarantine immediately.
§ Part 9 — AI-Generated Code Governance (CQ36–CQ39) 🆕
Purpose

Transparency, accountability, and quality control for AI-assisted development. AI writes the first draft — humans own the final product.

PART 9 / CQ36–CQ39AI-Generated Code Governance1 Critical · 2 High · 1 Medium
CQ36AI Code Attribution Required in PRHigh

Any PR containing AI-generated or AI-assisted code MUST include attribution: tool used (Copilot/Cursor/Claude/etc.), approximate % of AI contribution, and location of prompt context.

PR Description — AI Attribution
## AI Attribution
- Tool: Cursor (Claude 3.5 Sonnet)
- Contribution: ~70% of `/auth/login` handler logic
- Prompt context: `docs/prompts/2026-04-08-auth-flow.txt`
- Human modifications: Error handling, rate limiting logic
CQ37AI Code Review Checklist RequiredHigh

AI-generated code MUST pass an additional review checklist: (1) no hallucinated APIs/packages, (2) security patterns correct, (3) business logic aligns with requirements, (4) no subtle bugs in generated logic.

🤖
AI Review Checklist: Hallucination Check | Security Check | Business Logic Check | Edge Cases Check | Style Consistency | Prompt Context Saved
CQ38Prompt Context PreservationMedium

Prompts used to generate significant code (>50 lines or critical logic) MUST be preserved in version control alongside the code. Format: docs/prompts/YYYY-MM-DD-feature-name.md

CQ39Human Liability Clause — No "The AI Wrote It" DefenseCritical

The PR author retains FULL liability and accountability for AI-generated code. "The AI wrote it" is NOT an acceptable defense for bugs, security vulnerabilities, or production incidents. All AI-generated code is treated as if the author wrote it manually.

LIABILITY STATEMENT

"I understand that by submitting AI-generated code, I am certifying that I have reviewed, understood, tested, and take full responsibility for every line. In an incident, I will be the subject matter expert for this code, regardless of its origin."

🔧 Quality Gate Automation Script

scripts/quality-gate.sh
#!/bin/bash
# Runs all automated checks. If this passes, human reviewers focus on LOGIC, not STYLE.

set -e

echo "🔍 CODE QUALITY GATE v2.0"
echo "================================"

echo "📝 1/8: Prettier check..."
npx prettier --check "**/*.{ts,tsx,js,jsx,json,md}"

echo "🔎 2/8: ESLint check..."
npx eslint . --max-warnings 0

echo "🔷 3/8: TypeScript check..."
npx tsc --noEmit

echo "📦 4/8: Unused dependencies check..."
npx depcheck

echo "🔐 5/8: Package signature verification..."
npm audit signatures

echo "📄 6/8: License compatibility check..."
npx license-checker --onlyAllow "MIT;Apache-2.0;ISC;BSD-3-Clause;BSD-2-Clause"

echo "🧪 7/8: Test suite (excluding quarantined)..."
npm test -- --testPathIgnorePatterns=".*\\.quarantine\\..*"

echo "🏷️ 8/8: Commit message format check..."
npx commitlint --from HEAD~1 --to HEAD

echo ""
echo "✅ QUALITY GATE PASSED"
echo "Human reviewer: Focus on logic, security, and architecture only."
