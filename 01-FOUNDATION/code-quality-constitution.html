PART 1 / Q1–Q8 TypeScript Standards 5 Critical · 3 High · Both TS Stacks
Q1strict: true in tsconfig — No Exceptions, Both StacksCritical
BOTH TS STACKS

"strict": true is mandatory in tsconfig.json for both Next.js and Angular projects. This enables noImplicitAny, strictNullChecks, strictFunctionTypes, and all related strict checks. No per-file or per-directory overrides that weaken strictness are permitted. CI fails if tsconfig strict is disabled.

Q2No any — Use unknown With Type GuardsCritical
BOTH TS STACKS

The any type is forbidden in production code. Use unknown when the type is genuinely unknown, then narrow it with a type guard before use. ESLint rule @typescript-eslint/no-explicit-any: error is enforced in both repos. Existing any in auto-generated files is exempt — do not modify generated code.

❌ any disables type safety
function processData(data: any) {
  return data.value;  // no safety
}
✅ unknown + type guard
function processData(data: unknown) {
  if (isApiResponse(data))
    return data.value;  // type-safe
}
Q3Explicit Return Types on All Exported FunctionsCritical
BOTH TS STACKS

All exported functions, methods, and Arrow functions assigned to exported variables must have an explicit return type annotation. TypeScript inference alone is insufficient for public APIs — explicit types document intent and catch regressions. ESLint rule @typescript-eslint/explicit-module-boundary-types: error is enforced.

Next.js — API route handlers
Route handlers annotate return type as Promise<NextResponse<ApiResponse<T>>>. Custom hooks annotate their return tuple explicitly.
Angular — services and components
Service methods annotate return types as Observable<T> or Promise<T>. Component lifecycle hooks use void explicitly where no value is returned.
Q4No @ts-ignore or @ts-nocheck — Fix the TypesCritical
BOTH TS STACKS

// @ts-ignore and // @ts-nocheck are forbidden in any production file. If TypeScript reports an error that seems incorrect, fix the types — do not silence the compiler. The only exception is auto-generated files where the generator introduces suppress comments — these files are excluded from the ESLint rule.

Q5Interface Over Type Alias for Object ShapesCritical
BOTH TS STACKS

Use interface for object shapes that represent entities or contracts (component props, API response shapes, service contracts). Use type for unions, intersections, mapped types, and utility types. Consistent use of interface for shapes enables declaration merging and improves IDE tooling.

❌ type for object shape
type User = {
  id: string;
  email: string;
};
✅ interface for entity shape
interface User {
  id: string;
  email: string;
}
Q6No Non-Null Assertion Operator — Handle null ExplicitlyHigh
BOTH TS STACKS

The non-null assertion operator (!) is forbidden in production code. Handle null and undefined explicitly with null checks, optional chaining (?.), or nullish coalescing (??). Non-null assertions hide bugs — they tell the compiler to trust you, but that trust is often misplaced.

Q7Const Assertions and Readonly — Immutability by DefaultHigh
BOTH TS STACKS

Configuration objects and fixed data structures use as const to create literal types. Function parameters that should not be mutated are typed as Readonly<T>. Arrays that should not change use readonly T[]. Default to immutability — mutability is explicitly opted into, not the default.

Q8Enum Over Magic Strings — TypeScript Enums or as const ObjectsHigh
BOTH TS STACKS

Fixed sets of string values use TypeScript enum or as const objects — never raw string literals scattered through code. This applies to status values, event names, route constants, and role names. Keeps a single definition that propagates everywhere via the type system.

PART 2 / Q9–Q14 Python Standards FastAPI Backend · Angular Stack Only
Q9Type Hints on All Function Signatures — mypy Strict ModeCritical
PYTHON / FASTAPI

Every Python function must have complete type annotations on all parameters and the return type. mypy runs in strict mode in CI — --strict flag. Untyped functions fail the CI build. Use Pydantic models for complex data shapes — not raw dicts. -> None is explicit for procedures; -> Any is forbidden.

services/scholarship_service.py
# ❌ No type hints — mypy strict fails
async def find_matches(student_id, threshold):
    return []

# ✅ Full annotations — mypy strict passes
async def find_matches(
    student_id: str,
    threshold: float = 0.7
) -> list[ScholarshipMatch]:
    ...
Q10No Bare except — Always Catch Specific ExceptionsCritical
PYTHON / FASTAPI

Bare except: and except Exception: without re-raising are forbidden. Always catch specific exception types. If a broad catch is needed (e.g., top-level FastAPI exception handler), log the exception with full traceback, re-raise or wrap in an HTTPException, and never silently swallow it.

❌ Swallows all exceptions
try:
    result = await db_query()
except:          # bare except
    return None  # silent failure
✅ Typed, logged, re-raised
try:
    result = await db_query()
except DatabaseError as e:
    logger.error("DB query failed", exc_info=e)
    raise HTTPException(500, ...)
Q11Pydantic Models for All Request/Response Shapes — No Raw DictsCritical
PYTHON / FASTAPI

All FastAPI request bodies, response shapes, and internal data transfer objects use Pydantic v2 models. Never accept or return raw dict objects in endpoint handlers. Pydantic provides validation, serialization, and schema generation for OpenAPI — using raw dicts breaks all three.

Q12Ruff for Linting and Import Sorting — No flake8 or isortHigh
PYTHON / FASTAPI

Ruff is the single linting and import-sorting tool for Python. It replaces flake8, pylint, isort, and pycodestyle. Ruff configuration lives in pyproject.toml. Black handles formatting. Never install or run flake8, isort, or pylint in the FastAPI repo — Ruff handles it all faster.

ruff config
[tool.ruff] line-length = 88 (matches Black)
enabled rules
E, F, I (isort), N (naming), UP (pyupgrade), B (bugbear)
Q13Bandit Security Linter — Runs in CI, Blocks High/Critical FindingsHigh
PYTHON / FASTAPI

Bandit runs as part of every CI pipeline on the FastAPI codebase. High and Critical severity findings fail the build. Medium findings generate a warning and must be addressed before the next sprint. Findings are never silenced with # nosec without a documented justification in the PR description.

Q14pytest Coverage Minimum 80% — Fails CI Below ThresholdHigh
PYTHON / FASTAPI

pytest runs with --cov=app --cov-fail-under=80 in CI. Coverage dropping below 80% fails the build. New features must include tests that maintain or improve coverage. Coverage is measured on the app/ directory — test files, migrations, and generated code are excluded from the coverage count.

PART 3 / Q15–Q20 File & Module Structure 3 Critical · 3 High · All Three Stacks
Q15Maximum 200 Lines Per File — Split Larger FilesCritical
ALL STACKS

No production file exceeds 200 lines. Files approaching this limit must be refactored into smaller focused modules before the PR is merged. Generated files, migration files, and schema.prisma are exempt. ESLint max-lines rule enforces this in TypeScript. A custom Ruff rule enforces it in Python.

Q16Single Responsibility — One Primary Export Per ModuleCritical
ALL STACKS

Each file has one primary responsibility and one primary export. A component file exports one component. A service file exports one service class or hook. A utility file may export multiple related utility functions. Never mix unrelated concerns in one file — auth logic does not share a file with billing logic.

Q17No Circular Dependencies — Imports Flow One DirectionCritical
ALL STACKS

Circular imports between modules are forbidden. The import graph must be acyclic — dependency arrows flow in one direction only: UI → Services → Utils, never backwards. ESLint import/no-cycle rule detects and blocks circular imports in TypeScript. Python uses ruff circular import detection.

Q18Consistent Naming Conventions — Enforced by LinterHigh
ALL STACKS

Naming conventions are enforced by linter rules, not by manual review. TypeScript: camelCase functions/variables, PascalCase classes/types, kebab-case file names, SCREAMING_SNAKE_CASE constants. Python: snake_case functions/variables, PascalCase classes, SCREAMING_SNAKE constants. Angular components use the app- prefix selector convention.

Q19No Magic Numbers or Strings — Named Constants OnlyHigh
ALL STACKS

Numeric literals and string literals used in logic (not in display text or trivial comparisons like length === 0) must be named constants. Examples: MAX_RETRY_ATTEMPTS = 3, TOKEN_EXPIRY_MINUTES = 15, SIMILARITY_THRESHOLD = 0.7. Constants live in a constants.ts or constants.py file.

Q20Maximum 50 Lines Per Function — Extract Complex LogicHigh
ALL STACKS

No function exceeds 50 lines of code. Functions approaching this limit must be decomposed into smaller named functions that express the sub-steps clearly. Complex business logic chains become a readable orchestration function calling well-named helpers. Max nesting depth is 3 levels — flatten with early returns.

PART 4 / Q21–Q27 Linting & Formatting 4 Critical · 3 High · All Stacks
Q21ESLint + Prettier — Zero Warnings Tolerated in CICritical
BOTH TS STACKS

ESLint runs with --max-warnings 0 in CI. Any ESLint warning or error fails the build. Prettier is the single formatter — no manual formatting disputes. The shared .eslintrc and .prettierrc configs are the standard across all TypeScript repos. Never disable ESLint rules at the file level without a documented justification.

Q22Husky Pre-Commit Blocks — Commit Impossible Without Passing ChecksCritical
ALL STACKS

Husky (TypeScript repos) and pre-commit (Python repo) hooks run automatically on every commit attempt. A commit that fails any hook is blocked — the developer must fix the issue before committing. Never bypass hooks with --no-verify. If a hook incorrectly blocks valid code, fix the hook configuration — do not bypass it.

Q23TypeScript Must Compile Without Errors — tsc --noEmit in CICritical
BOTH TS STACKS

tsc --noEmit runs in CI as a separate check step. TypeScript compilation errors fail the build — even if the runtime behaviour appears correct. This catches type errors that ESLint may miss, particularly in complex generic types and conditional types. Both Next.js and Angular repos run this check independently.

Q24No Console.log in Production Code — Use Structured LoggerCritical
ALL STACKS

console.log, console.error, and console.warn are forbidden in committed TypeScript code. Use the centralised structured logger (Next.js: lib/logger.ts, Angular: core/services/logger.service.ts). ESLint rule no-console: error is enforced. Python: never use print() — always use the logging module with structured output.

Next.js
import { logger } from '@/lib/logger'
Uses pino or Winston — structured JSON logs forwarded to Better Stack.
Angular
LoggerService injectable — wraps console in dev, sends to Sentry in production. Never import console directly.
Python
import structlog — structured JSON output. logger = structlog.get_logger() at module level. Never use bare print().
Q25Import Order — Sorted by Group, Enforced by LinterHigh
ALL STACKS

Imports are grouped and sorted: (1) external packages, (2) internal absolute imports (@/), (3) relative imports. Each group is separated by a blank line. Order within groups is alphabetical. This is automatically enforced — ESLint import/order for TypeScript, Ruff I rules for Python. No manual ordering debates.

Q26No Unused Imports or Variables — Zero ToleranceHigh
ALL STACKS

Unused imports and unused variables are errors — not warnings — in both ESLint (TypeScript) and Ruff (Python). They indicate incomplete refactors, dead code paths, or forgotten cleanup. CI fails on any unused import. The only exemption is function parameters prefixed with _ (Python convention) or intentionally unused destructured values prefixed with _.

Q27Prettier Config — 2-Space Indent, 100-Char Line Width, Single QuotesHigh
BOTH TS STACKS

All TypeScript code is formatted by Prettier with these locked settings: tabWidth: 2, printWidth: 100, singleQuote: true, trailingComma: "es5", semi: true. The .prettierrc is shared across all TypeScript repos via the system-design-template repository. Never override these settings per-project.

PART 5 / Q28–Q35 Code Review Process 4 Critical · 4 High · All Stacks
Q28Two Approvals Required — Never Self-MergeCritical
ALL STACKS

Every PR requires exactly two approvals from reviewers other than the PR author before merging. The author cannot approve their own PR. The main branch is protected — direct pushes and self-merges are blocked by GitHub branch protection rules. No exceptions for "small" or "obvious" changes.

Q29Maximum 400 Lines Per PR — Split Larger ChangesCritical
ALL STACKS

Pull requests exceeding 400 lines of changed code (excluding generated files, package-lock.json, prisma/migrations/) must be split into smaller PRs before review. Large PRs are a review quality problem — reviewers lose focus and bugs slip through. A CI check flags PRs over 400 lines and requires a justification label to proceed.

Q30All CI Checks Must Pass Before Review Is RequestedCritical
ALL STACKS

A PR with failing CI checks must not be submitted for review. Fix CI failures before requesting reviewers. Reviewers may dismiss their reviews if CI breaks after approval — the author is responsible for keeping CI green. Draft PRs are used for work-in-progress — never open a real PR when CI is red.

Q31PR Description — What, Why, How, and Test EvidenceCritical
ALL STACKS

Every PR description must contain four sections: (1) What — what changed in plain English, (2) Why — the reason or problem being solved, (3) How — the technical approach taken, (4) Test Evidence — screenshot, test output, or curl response showing the change works. PRs without complete descriptions are returned to the author.

Q32Squash Merge Strategy — One Commit Per PR on MainHigh
ALL STACKS

All PRs are merged to main using squash merge. The squash commit message follows the conventional commit format: type(scope): description. Types: feat, fix, refactor, docs, test, chore. This keeps main history clean and readable — every commit on main represents one complete feature or fix.

Q33Review Within 24 Hours — Acknowledge or Defer Within 4 HoursHigh
ALL STACKS

Reviewers acknowledge a review request within 4 hours of receiving it — even if only to say when they will review. Full review is completed within 24 hours. PRs that sit unreviewed for 48 hours may be escalated. Review is a team responsibility — nobody's work is blocked by unacknowledged reviews.

Q34Comments Are Questions or Suggestions — Never DemandsHigh
ALL STACKS

Review comments are framed as questions or suggestions, never demands. Use prefixes: nit: for minor style suggestions that are non-blocking, suggestion: for improvements the reviewer thinks are worthwhile, question: for clarification needed, issue: for actual problems that must be fixed. This makes the review intent unambiguous.

Q35Cross-Constitution PRs Require Both Frontend and Backend ReviewerHigh
ALL STACKS

PRs that change the API contract, database schema, auth strategy, or shared types must include a reviewer from both the frontend and backend teams. The cross-constitution CI label check enforces this — PRs with the Frontend-Review-Required or Backend-Review-Required labels require at least one approval from each domain.

PART 6 / Q36–Q40 Documentation Standards 2 Critical · 3 High · All Stacks
Q36JSDoc/Docstring on All Public Functions — What It Does, Not HowCritical
ALL STACKS

Every exported function, class method, and API endpoint handler must have a JSDoc comment (TypeScript) or docstring (Python) describing what it does, its parameters, and its return value. Document the intent and contract — not the implementation. If the implementation is obvious from the signature, a one-line description is sufficient. Private helper functions need comments only when the logic is non-obvious.

Q37README in Every Feature Directory — Purpose, Inputs, OutputsCritical
ALL STACKS

Every feature directory (features/auth/, features/dashboard/, Python app/api/v1/) must contain a README.md describing: (1) the feature's purpose, (2) key files and their roles, (3) external dependencies. A new developer must be able to understand what a feature does by reading only its README and the code structure.

Q38Inline Comments on Non-Obvious Logic — The Why, Not the WhatHigh
ALL STACKS

Inline comments explain why code is written a particular way — not what it does (the code itself shows that). Comments like // loop through array add no value. Comments like // FastAPI B2 constraint: never expose this endpoint publicly or // similarity threshold per F14 — below 0.7 discarded add context that cannot be inferred from code alone.

Q39TODO and FIXME Comments — Must Include Ticket ReferenceHigh
ALL STACKS

TODO and FIXME comments are permitted only when they reference a GitHub issue number: // TODO(#142): Add pagination after MVP launch. Orphaned TODOs without issue references are stale and misleading — ESLint rule no-warning-comments warns on TODOs without a pattern matching #\d+. TODOs older than one sprint are escalated in code review.

Q40Environment Variables — Every Usage Commented with PurposeHigh
ALL STACKS

Every environment variable access (process.env.X, settings.X) must have a comment or the variable name itself must be self-documenting. The .env.example file in every repo documents every variable with: the variable name, a description, an example value, and whether it is required or optional.

Q41Angular ESLint Config — Enforces OnPush, Standalone, No Template FormsNew · Critical
ANGULAR STACK ONLY

The Angular ESLint configuration enforces: (1) @angular-eslint/prefer-on-push as an error — every component must declare ChangeDetectionStrategy.OnPush, (2) a custom rule blocking ngModel and FormsModule — template-driven forms are forbidden, (3) @angular-eslint/use-component-selector — all components must have a selector. Q43Angular Component Selector Prefix — app- for All ComponentsNew · High
ANGULAR STACK ONLY

All Angular component selectors use the app- prefix: app-login-form, app-scholarship-card, app-account-dashboard. The Angular ESLint rule @angular-eslint/component-selector is configured with prefix: "app" as an error. Q44No Empty Lifecycle Hooks — Remove Unused Lifecycle MethodsNew · High

Angular lifecycle hooks (ngOnInit, ngOnDestroy, ngOnChanges, etc.) that contain no code must be removed entirely. Empty lifecycle hooks add noise, confuse readers, and indicate incomplete implementation. The ESLint rule @angular-eslint/no-empty-lifecycle-method enforces this automatically. Implement the interface only when the hook has actual content.

§ Annex A — Forbidden Patterns (FP01–FP20)
⚠ FORBIDDEN PATTERNS — VIOLATION = BUILD FAILURE · ALL STACKS UNLESS MARKED
FP01 — any TYPE IN PRODUCTION CODE
Using TypeScript any type anywhere in production TypeScript files.
✓ Fix: Use unknown with type guard or a proper interface (Q2).
FP02 — @ts-IGNORE OR @ts-NOCHECK
Silencing TypeScript compiler errors with suppress comments instead of fixing the types.
✓ Fix: Fix the underlying type error (Q4).
FP03 — BARE except IN PYTHON
Catching all exceptions with bare except: or swallowing with except Exception: pass.
✓ Fix: Catch specific exception types, log, re-raise (Q10).
FP04 — RAW DICTS IN FASTAPI HANDLERS
Accepting dict as request body or returning dict instead of a Pydantic model.
✓ Fix: Pydantic v2 models for all request/response shapes (Q11).
FP05 — CONSOLE.LOG IN COMMITTED CODE
Committing console.log/warn/error statements or Python print() to any branch.
✓ Fix: Use the structured logger service (Q24).
FP06 — SELF-MERGE
Merging your own pull request, even with another approval already present.
✓ Fix: Always requires 2 approvals from others (Q28).
FP07 — BYPASSING PRE-COMMIT WITH --no-verify
Using git commit --no-verify to bypass Husky or pre-commit hooks.
✓ Fix: Fix the lint/format issue, never skip hooks (Q22).
FP08 — PR OVER 400 LINES WITHOUT LABEL
Opening a PR with more than 400 changed lines without the large-pr-justified label and explanation.
✓ Fix: Split into smaller PRs (Q29).
FP09 — MAGIC NUMBERS IN LOGIC
Raw numeric or string literals in business logic: if retries > 3, timeout = 30000.
✓ Fix: Named constants in constants file (Q19).
FP10 — CIRCULAR IMPORTS
Module A imports from Module B which imports from Module A — creates dependency cycles.
✓ Fix: Extract shared types to a third module (Q17).
FP11 — NON-NULL ASSERTION OPERATOR
Using value! (non-null assertion) instead of handling null/undefined explicitly.
✓ Fix: Optional chaining, nullish coalescing, or explicit guard (Q6).
FP12 — TODO WITHOUT TICKET REFERENCE
TODO/FIXME comments without a GitHub issue number: // TODO: fix this later.
✓ Fix: // TODO(#142): description with issue reference (Q39).
FP13 — STRICT: FALSE IN TSCONFIG
Disabling TypeScript strict mode in any tsconfig.json file across any repo.
✓ Fix: "strict": true always (Q1).
FP14 — FLAKE8 OR ISORT IN PYTHON [PYTHON]
Adding flake8, pylint, or isort as Python linting tools alongside Ruff.
✓ Fix: Ruff covers all of these — install only Ruff (Q12).
FP15 — KARMA/JASMINE IN ANGULAR [ANGULAR]
Running Angular unit tests with the legacy Karma test runner or Jasmine matchers.
✓ Fix: Vitest + Angular Testing Utilities (Q42).
FP16 — TEMPLATE FORMS IN ANGULAR [ANGULAR]
Importing FormsModule or using [(ngModel)] in any Angular production component.
✓ Fix: ReactiveFormsModule only — ESLint blocks FormsModule import (Q41, Frontend Rule 67).
FP17 — DEFAULT CHANGE DETECTION [ANGULAR]
Angular components without explicit ChangeDetectionStrategy.OnPush declaration.
✓ Fix: OnPush on every component — Angular ESLint enforces (Q41, Frontend Rule 71).
FP18 — EMPTY LIFECYCLE HOOKS [ANGULAR]
Implementing Angular lifecycle interfaces (OnInit, OnDestroy) with empty method bodies.
✓ Fix: Remove empty hooks — implement only when body has content (Q44).
FP19 — FILE OVER 200 LINES
Any production file (excluding generated, migration, schema) exceeding 200 lines of code.
✓ Fix: Split into smaller single-responsibility modules (Q15).
