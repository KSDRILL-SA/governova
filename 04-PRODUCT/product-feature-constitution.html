§ Part 1 — Ideation (P1-P4)
Purpose

Discover real problems worth solving. Features without problems are solutions in search of a disease.

PART 1 / P1-P4Ideation — Problem Discovery2 Critical · 2 High
P1Problem Before SolutionCritical

Every feature MUST start with a documented problem statement. No "feature because it's cool" without a problem to solve.

⚠️
The Question: "What problem does this solve for the user?" — If you cannot answer, do not build it.
P2User Research RequiredCritical

Major features (>1 week of work) MUST be validated with user research (interviews, surveys, data analysis). Not just internal assumptions.

P3Competitive AnalysisHigh

New features SHOULD include analysis of how competitors solve the same problem. Build differentiation, not parity.

P4One Feature, One ProblemHigh

Each feature MUST solve ONE specific problem. Features that try to solve multiple problems become bloated, confusing, and hard to measure.

§ Part 2 — Prioritization (P5-P8)
ICE Framework

Impact × Confidence × Ease = Score. Highest scores win.

PART 2 / P5-P8Prioritization — ICE Scoring2 Critical · 1 High · 1 Medium
P5ICE Scoring RequiredCritical

Every feature MUST be scored using ICE (Impact, Confidence, Ease) before sprint planning. Scores: 1-10 each, multiplied. Minimum score for v1: 125 (5×5×5).

ICE Scoring Template
# Feature: [Name]

Impact (1-10): _  # How much does this improve user experience/revenue?
Confidence (1-10): _  # How certain are we of the impact? (Data vs guess)
Ease (1-10): _  # How easy/quick is it to build? (10 = very easy)

ICE Score: Impact × Confidence × Ease = ___
P6Data-Driven PrioritizationCritical

Prioritization MUST use data (usage metrics, user feedback, revenue impact) not politics or "gut feeling." Confidence score of 1-3 requires validation before building.

P7Weekly Backlog GroomingHigh

Backlog MUST be reviewed weekly (30 min). Re-score features based on new data. Remove features that no longer meet ICE threshold.

P8Technical Debt vs FeaturesMedium

Technical debt reduction MUST compete on ICE score with new features. 20% capacity reserved for debt (Code Quality CQ31), but debt items must still justify their priority.

§ Part 3 — Definition (P9-P11)
PRD Required Fields

Problem · Success Metrics · User Stories · Acceptance Criteria · Technical Notes · Rollout Plan

PART 3 / P9-P11Definition — PRD & Specs2 Critical · 1 High
P9PRD Required for Features >1 WeekCritical

Features estimated >1 week MUST have a Product Requirements Document (PRD) approved before development starts.

PRD Template
# PRD: [Feature Name]

## Problem Statement
[What problem does this solve? Who has this problem? How do they solve it today?]

## Success Metrics
- [ ] Metric 1: [target]
- [ ] Metric 2: [target]

## User Stories
- As a [user], I want [goal] so that [benefit]

## Acceptance Criteria
- [ ] Criterion 1
- [ ] Criterion 2

## Technical Notes
[Architecture considerations, dependencies, constraints]

## Rollout Plan
[Feature flag? Beta users? Gradual rollout?]
P10Acceptance Criteria MUST Be TestableCritical

Every acceptance criterion MUST be testable (QA can verify pass/fail). "Looks good" or "feels fast" are NOT acceptable.

P11Technical Spec for Complex FeaturesHigh

Complex features (>3 days of backend work or architectural changes) MUST have a technical design document reviewed before coding.

§ Part 4 — Development (P12-P14)
MVP First

Build the smallest thing that could work. Add complexity only when validated.

PART 4 / P12-P14Development — Build & Test2 Critical · 1 High
P12Feature Flag Required for All FeaturesCritical

Every feature MUST be behind a feature flag (Backend B42, Frontend R65). Flag default = FALSE for new features.

⚠️
No flag, no merge. Feature flags are how we ship safely and rollback instantly.
P13Tests Required Before MergeCritical

Feature PRs MUST include tests (unit for logic, integration for API, E2E for critical paths) per Testing Constitution T5-T16.

P14Documentation Before LaunchHigh

User-facing features MUST have documentation (help center, tooltips, or onboarding) before launch.

§ Part 5 — Launch (P15-P17)
Rollout Phases

Internal → 1% → 10% → 50% → 100% (with monitoring after each)

PART 5 / P15-P17Launch — Rollout & Release1 Critical · 2 High
P15Launch Checklist RequiredHigh

Every feature launch MUST have a completed checklist: tests passing, docs updated, metrics configured, runbook created, feature flag ready.

P16Gradual Rollout RequiredCritical

Features MUST roll out gradually: internal testers → 1% users → 10% → 50% → 100%. Monitor metrics after each step. Rollback immediately if negative impact.

✅
Rollback is not failure. It is the system working as designed. Celebrate good rollbacks.
P17Launch CommunicationHigh

Features affecting users MUST have launch communication: changelog entry, email/Slack notification (if applicable), and support team briefing.

§ Part 6 — Measurement (P18-P20)
Metrics Dashboard

Usage · Engagement · Revenue · Performance · Support tickets

PART 6 / P18-P20Measurement — Success Metrics1 Critical · 2 High
P18Success Metrics Defined Before LaunchCritical

Every feature MUST have success metrics defined in the PRD. Metrics MUST be measurable and have targets.

Example Success Metrics
- Adoption: 30% of active users use feature in first month
- Engagement: Average 5 sessions/week per user
- Conversion: 15% of users upgrade after using feature
- Performance: Feature loads in <500ms p95
- Support: <5 support tickets about feature in first month
P19Weekly Feature ReviewHigh

New features MUST be reviewed weekly for first month: metrics vs targets, user feedback, technical issues. Document findings.

P20User Feedback CollectionHigh

Every feature MUST have a feedback mechanism (in-app survey, feedback button, or user interview outreach). (Frontend R42).

§ Part 7 — Iteration (P21-P22)
Build-Measure-Learn

The Lean Startup cycle. Every feature is a hypothesis to be tested.

PART 7 / P21-P22Iteration — Improve or Kill2 Critical
P21Kill Features That Don't Meet MetricsCritical

If feature does not meet success metrics after 30 days, it MUST be reviewed. Decision: iterate (with plan), kill (remove flag), or accept (document why). "Just leave it" is NOT an option.

⚠️
Killing a feature is success. You learned what not to build. Celebrate the learning, not the code.
P22Iteration Requires HypothesisCritical

Feature iterations MUST have a hypothesis: "We believe [change] will improve [metric] from X to Y." Measure before and after.

§ Part 8 — Deprecation (P23-P24)
Sunset Policy

Features die. Plan for it. Communicate it. Remove it cleanly.

PART 8 / P23-P24Deprecation — Sunset & Remove2 Critical
P23Deprecation Notice RequiredCritical

Deprecated features MUST have notice: minimum 30 days for internal, 90 days for external/API users (Backend B44). Include migration path or alternative.

P24Feature Removal CleanupCritical

When feature is fully deprecated, remove ALL related code: frontend components, API routes, database columns, feature flags, documentation. No dead code accumulation.
