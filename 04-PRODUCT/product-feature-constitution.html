§ Part 1 — Product Vision & Philosophy (PF1–PF6)
KSDRILL SA Mission
"Build what should already exist, with the precision, care, and permanence it deserves."
Product Principles
  • 1 Real problem, real people
  • 2 Primary workflow first
  • 3 Design before code
  • 4 Sequential — one at a time
  • 5 African roots, global impact
PART 1 / PF1–PF6 Product Vision & Philosophy 4 Critical · 2 High · All Systems
PF1Every Platform Solves a Real Problem Felt by Real People — Not a Technology ProblemCritical
ALL SYSTEMS

Every KSDRILL SA platform must solve a problem that real people experience in their daily lives — not a technology problem, not an engineering problem, and not a problem invented to justify a technology choice. FundsLink exists because students are excluded from funding. Maphophe exists because villages have no governance infrastructure. Reserve Bank exists because people save inconsistently. SyncUp exists because creator negotiations are unstructured. The problem must be documented before the solution is designed.

PF2The Primary User Workflow Is Sacred — Everything Else Is SecondaryCritical
ALL SYSTEMS

Every platform has one primary user workflow — the sequence of steps a user must complete to receive the core value. This workflow is the product. Everything else is a feature. The primary workflow must work flawlessly before any secondary feature is built. A beautifully designed admin panel on a broken primary workflow is a worse product than a plain interface with a working primary workflow.

FundsLink
Student applies → receives matched funding
Maphophe
Resident submits request → sees status update
Reserve Bank
User deposits → sees balance and interest
SyncUp
Creator pitches → receives negotiated response
PF3Sequential Build — One System Fully Before the Next BeginsCritical
ALL SYSTEMS

KSDRILL SA builds one flagship system at a time. FundsLink MVP must ship before Reserve Bank development begins. No parallel platform development. The build order is locked: FundsLink Academy (Q2 2026) → Maphophe Community System (Q3 2026) → KSDRILL Reserve Bank (Q4 2026) → SyncUp (Q1 2027). This is not random scheduling — each system builds engineering confidence and user feedback loops before the next begins.

PF4Design-First — Full Architecture Locked Before the First Line of CodeCritical
ALL SYSTEMS

No platform begins coding until the full system design is locked: architecture, database schema, module definitions, interface designs, and constitutional registration. The design phase is not optional or abbreviated. "We'll figure it out as we build" produces systems that cannot be maintained. All four flagship systems are fully designed — the build phase implements the design.

PF5African Context Is a Design Constraint — Not an AfterthoughtHigh
ALL SYSTEMS

KSDRILL SA builds for South African users first. This means: Maphophe is optimised for low-bandwidth rural connections (PWA offline-ready, minimum data usage). FundsLink is designed for students without reliable internet (fast load times, form-saving). Reserve Bank addresses the South African savings behaviour gap. These are not accessibility add-ons — they are primary design requirements validated before v1 ships.

PF6GrowthCore Solutions Is a Separate Entity — No Product OverlapHigh
ALL SYSTEMS

KSDRILL SA and GrowthCore Solutions are separate companies with separate missions. KSDRILL SA builds platforms that solve real-world challenges. GrowthCore Solutions delivers client web development, marketing, and analytics services. No KSDRILL SA system is built as a GrowthCore client project. No GrowthCore client project uses KSDRILL SA constitutional frameworks without explicit authorisation. Sprint work never overlaps between the two entities.

§ Part 2 — Feature Governance (PF7–PF13)
Feature Decision Flow
  • 1st Problem statement written
  • 2nd 5 gate questions answered
  • 3rd Stack + DB impact assessed
  • 4th OpenAPI contract drafted
  • 5th Sprint slot assigned
  • 6th Build begins
Feature Group Hierarchy
  • G1 Core primary workflow
  • G2 Supporting primary workflow
  • G3 Secondary features
  • G4 Nice-to-have
  • v1 Groups 1+2 only
  • v2+ Groups 3+4
PART 2 / PF7–PF13 Feature Governance 4 Critical · 3 High · All Systems
PF75 Gate Questions — Every Feature Must Pass All Five Before Code Is WrittenCritical
ALL SYSTEMS

Every feature proposed for any platform — regardless of how small or "obvious" it seems — must pass all five gate questions before being added to a sprint. Failing any gate defers the feature to v2. There are no exceptions for "quick wins" or "obviously needed" features. The gate questions are the constitutional check against scope creep.

Q1
User WorkflowDoes a real user need this to complete the primary workflow?
Q2
RemovabilityDoes removing this feature break the primary workflow or core value?
Q3
BuildabilityCan this be designed, built, and tested within 2–4 weeks?
Q4
Backend ReadyDoes the OpenAPI contract exist? Is the DB schema defined?
Q5
ValidatedHas a real user (not the builder) confirmed they need this?
PF8v1 Contains Maximum 6 Features — Hard Limit, Not a GuidelineCritical
ALL SYSTEMS

Every platform ships v1 with a maximum of 6 features (where authentication counts as one feature). If more than 6 features pass all 5 gate questions, the lowest-impact features are cut to v2. This is a hard limit — not a target. A v1 with 4 features that are flawless outperforms a v1 with 8 features that are half-finished.

FundsLink v1 max
Auth + Profile + Application + AI Match + Status = 5
Maphophe v1 max
Auth + Announcements + Service Requests + Status = 4
Reserve Bank v1 max
Auth + Account + Deposits + Goals + Interest View = 5
SyncUp v1 max
Auth + Profiles + Pitch + Negotiation Engine = 4
PF9Groups 1+2 Only in v1 — No Secondary Features Before Primary Workflow ShipsCritical
ALL SYSTEMS

v1 ships only Group 1 (core primary workflow) and Group 2 (directly supporting the primary workflow) features. Group 3 (secondary features: admin dashboards, analytics, bulk operations) and Group 4 (nice-to-have: customisation, advanced settings) are deferred to v2+. A single admin dashboard in v1 is a distraction that delays the primary workflow shipping.

PF10Feature Flags for All New Features — Ship Dark, Enable When ReadyCritical
ALL SYSTEMS

Every new feature beyond the initial v1 set ships behind a feature flag stored in the database. The feature is deployed but disabled — it goes live only when the flag is enabled. This decouples deployment from release, enables instant kill switches, and allows staged rollouts to specific user groups. Feature flags are never hardcoded — always stored in the FeatureFlag PostgreSQL table with a default of false.

PF11Stack Impact Must Be Assessed Before Feature ApprovalHigh
ALL SYSTEMS

Before any feature is approved, its impact on the platform stack must be assessed and documented: Does it require a new database table or collection? Does it add a new endpoint (does it push the count toward the v1 limit)? Does it require a new background job? Does it require new env vars? Features that expand the stack complexity beyond v1 limits are deferred.

Next.js Stack (Maphophe · SyncUp)
Check against: Next.js API route count (max 15), Prisma table additions, BullMQ job additions. No new external service integrations in v1.
Angular Stack (FundsLink · Reserve Bank)
Check against: FastAPI endpoint count (max 15), Prisma + MongoDB schema additions, Railway service count, LangChain chain additions (FundsLink).
PF12No Feature That Requires a Different Framework — Stack Is LockedHigh
ALL SYSTEMS

A feature proposal that requires switching or adding a framework is automatically deferred. FundsLink cannot add React components. Maphophe cannot add a FastAPI backend. SyncUp cannot add Angular forms. The framework assignment for each system is locked by the Backend Constitution (B1) and Team & Process Constitution (T4). Features must fit the existing stack — the stack does not change to fit the feature.

PF13Feature Proposals Written in Plain Language — No Technical JargonHigh
ALL SYSTEMS

Feature proposals are written as user stories in plain language: "As a [user type], I need to [action] so that [outcome]." Technical implementation details belong in the OpenAPI contract and Prisma schema — not in the feature proposal. A feature that cannot be described in one plain-language sentence is not well enough understood to build.

§ Part 3 — MVP Definitions Per System (PF14–PF20)
MVP Definition Principle
MVP is not minimum — it is the minimum that delivers real value. A user must be able to complete the primary workflow start to finish without hitting a dead end or error that prevents completion.
Universal MVP Gates
  • ✓ Primary workflow complete E2E
  • ✓ Auth working + RBAC enforced
  • ✓ Error states handled gracefully
  • ✓ Feedback mechanism live
  • ✓ Mobile-first at 320px
  • ✓ All CI checks passing
  • ✓ Staging validated first
PART 3 / PF14–PF20 MVP Definitions 3 Critical · 4 High · System-Specific
PF14MVP Is Defined Before Build Begins — Done Criteria Written, Not AssumedCritical
ALL SYSTEMS

The definition of done for v1 is written and approved before the first sprint begins. "Done" is not "feature complete" — it is "the primary user workflow works end-to-end in production, validated by at least 3 real users." The definition of done is documented in the system's GitHub repository README and reviewed at every sprint retrospective.

PF15FundsLink v1 Done — Student Can Apply and Receive a Matched Funding ResultCritical
ANGULAR STACK — FUNDSLINK

FundsLink v1 is done when: A student can create an account, complete their academic profile, submit an application, and receive at least one AI-matched funding opportunity — all without hitting an unhandled error. The AI matching must return results (minimum 1 match above 0.7 similarity) for at least 80% of test applications run during staging validation. Admin portal, funder dashboards, and bulk application management are v2 features.

PF16Reserve Bank v1 Done — User Can Create Account, Deposit, and See Balance + InterestCritical
ANGULAR STACK — RESERVE BANK

Reserve Bank v1 is done when: A user can create an account, make a deposit, see their balance update correctly, see their projected interest calculation, and set a savings goal. Financial data integrity must be verified: sum of all deposits must equal account balance for 100% of test accounts. Lock periods, automated deposit schedules (BullMQ), and interest compounding run correctly in staging. Investment features, multiple account types, and social savings are v2.

PF17Maphophe v1 Done — Resident Can Submit Request and Ward Admin Can RespondHigh
NEXT.JS STACK — MAPHOPHE

Maphophe v1 is done when: A resident can create an account, submit a service request with a category and description, and see its status change as the ward admin reviews it. A ward admin can see all submitted requests, update a request status, and post a response. The PWA must function offline for request submission (data syncs when connectivity returns). Voting, announcements, and ward reporting are v2.

PF18SyncUp v1 Done — Creator Can Send Pitch and Receive Structured ResponseHigh
NEXT.JS STACK — SYNCUP

SyncUp v1 is done when: A creator can create a profile, discover another creator, send a structured pitch using a template, and receive a response within the 10-message negotiation limit. The negotiation must auto-close when the limit is reached or when both parties agree. Creator profiles must be SEO-indexed. Drop-based subscriptions, DRM-protected content, and advanced privacy controls are v2.

PF19Staging Validation Required — Real User Testing Before Production LaunchHigh
ALL SYSTEMS

Before any platform launches to production, the v1 primary workflow must be validated by at least 3 real users (not the builders) in the staging environment. Their feedback is collected, critical blockers are fixed, and the validation is repeated. A platform validated only by its builders is not validated — it is assumed. The 3 users must represent the actual target user group.

PF20No Admin Panel in v1 — Self-Service Primary Workflow OnlyHigh
ALL SYSTEMS

Admin dashboards, analytics panels, bulk operations, and platform management interfaces are v2 features for all systems. v1 validates the primary user workflow — admin tools validate that the platform can be managed at scale, which is a v2 problem. The only admin capability in v1 is the minimum needed to support the primary workflow (e.g., ward admin responding to requests on Maphophe).

§ Part 4 — User Feedback (PF21–PF25)
Feedback Requirements
  • ✓ Live from day 1
  • ✓ Rating 1–5 + comment
  • ✓ Tied to primary workflow
  • ✓ Reviewed weekly
  • ✓ Drives v2 priorities
PART 4 / PF21–PF25 User Feedback & Validation 3 Critical · 2 High · All Systems
PF21Feedback Mechanism Live at v1 Launch — Not a v2 FeatureCritical
ALL SYSTEMS

Every platform ships a user feedback mechanism active from the first day of production. Minimum viable feedback: a persistent button accessible from every page that captures a 1–5 star rating and an optional comment, stored in the database with the user's id and the page they were on. Feedback is not a v2 feature — it is the primary data source for v2 prioritisation.

PF22Feedback Reviewed Weekly — Actions Documented MonthlyCritical
ALL SYSTEMS

User feedback is reviewed every week without exception. Monthly, a summary of feedback themes is written and three product improvement actions are documented in the system's GitHub. These actions are prioritised against existing roadmap items using the same 5 gate questions as new features. Feedback that sits unreviewed for more than two weeks is a product failure.

PF23User Interviews — Minimum 3 Real Users Interviewed Before v2 PlanningCritical
ALL SYSTEMS

Before any v2 feature planning begins for a platform, a minimum of 3 real users who have used the v1 platform are interviewed. The interviews are recorded and summarised in writing. v2 features that do not appear in user interview themes are deprioritised regardless of how obvious they seem to the builder. What seems obvious to the builder is often irrelevant to the user.

PF24Quantitative Metrics — Active Users, Completion Rate, Error Rate Tracked WeeklyHigh
ALL SYSTEMS

Three quantitative metrics are tracked for every platform from launch: (1) Weekly active users (WAU), (2) Primary workflow completion rate (% of users who start the primary flow and complete it), (3) Error rate (% of requests returning 4xx or 5xx). These metrics are reviewed weekly alongside qualitative feedback. A declining completion rate is a product emergency — not a metric to ignore.

PF25Feedback Drives v2 — Features Not Requested by Users Are Lowest PriorityHigh
ALL SYSTEMS

v2 feature prioritisation is driven by user feedback data first, then by strategic product direction, then by technical debt. A feature that no user has requested is not automatically excluded — but it must justify itself against user-requested features for sprint slots. "I think users would want this" is not evidence. "Three users in interviews said they need this" is evidence.

PART 5 / PF26–PF30 Roadmap Governance 3 Critical · 2 High · All Systems
PF26Roadmap Items Are Hypotheses — Validated or Invalidated by User DataCritical
ALL SYSTEMS

Every item on the product roadmap is a hypothesis about what users need — not a commitment. Hypotheses are validated by user interviews, feedback data, and usage metrics. A roadmap item that survives 3 months without user validation evidence is removed from the roadmap or promoted to "investigate with users" status. Roadmaps are living documents — not immutable plans.

PF27Scope Creep Is Actively Managed — Any Feature Added Mid-Build Requires Owner ApprovalCritical
ALL SYSTEMS

Adding any feature to a sprint that was not in the sprint plan requires explicit written approval from Maluleke Kurhula Success. "While I'm in this area of code, I'll just add X" is the most common source of scope creep. The constitutional framework exists precisely to prevent this. The cost of mid-sprint scope additions is always higher than it appears — they delay the primary workflow shipping, create untested code paths, and undermine sprint predictability.

PF28Platform Confidentiality — Additional Platforms Protected Until Constitutional RegistrationCritical
ALL SYSTEMS

Platforms beyond the four flagship systems that are in development or design phase are protected under company confidentiality until they are registered in the Constitutional Order and publicly announced. No details of unannounced platforms are shared externally. This protects competitive positioning and allows design work to proceed without premature market exposure.

PF29Quarterly Constitutional Review Applies to This Constitution TooHigh
ALL SYSTEMS

This constitution — like all 10 — is reviewed quarterly. The review asks: Are the MVP definitions still accurate? Do any gate questions need updating based on what we've learned? Are the feature group definitions serving us? Constitutional amendments to this document require owner approval and affect all future systems. Past systems' v1 definitions remain locked — only future systems benefit from updates.

PF30This Constitution Is Last — It Can Only Be Applied After All Others Are in PlaceHigh
ALL SYSTEMS

The Product & Feature Constitution is Constitution 10 of 10 because product decisions are only meaningful when the team, code, infrastructure, auth, database, testing, and incident response frameworks are already in place. Building a product feature on a system without the other nine constitutions active is building on sand. This constitution is the crown jewel — it governs what gets built — but it sits on the foundation of the other nine.

§ Annex A — Forbidden Patterns (FP01–FP16)
⚠ FORBIDDEN PATTERNS — VIOLATION = SCOPE CREEP · CONSTITUTIONAL BREACH
FP01 — ADMIN PANEL IN v1
Building an admin dashboard, analytics panel, or bulk operations interface as part of v1.
✓ Fix: Admin tools are v2 features. v1 = primary user workflow only (PF20).
FP02 — MORE THAN 6 v1 FEATURES
Shipping v1 with more than 6 features — including counting auth separately from the core workflow.
✓ Fix: Hard limit of 6 features in v1 — cut the lowest-impact to v2 (PF8).
FP03 — FEATURE WITHOUT 5 GATE QUESTIONS
Adding a feature to a sprint without answering and passing all 5 gate questions.
✓ Fix: All 5 gates must pass before sprint assignment (PF7).
FP04 — MID-SPRINT SCOPE ADDITION WITHOUT APPROVAL
Adding any feature to an active sprint without written approval from the owner.
✓ Fix: Owner approval required in writing before any mid-sprint addition (PF27).
FP05 — PARALLEL PLATFORM DEVELOPMENT
Starting development of a second platform before the first platform's v1 has shipped.
✓ Fix: Sequential build — one system fully before the next (PF3, T1).
FP06 — BUILDING BEFORE DESIGN IS LOCKED
Writing code for a system before its architecture, database schema, and interface design are locked.
✓ Fix: Design-first — full architecture locked before first line of code (PF4).
FP07 — NO FEEDBACK MECHANISM AT LAUNCH
Launching a platform to production without a live user feedback mechanism collecting ratings.
✓ Fix: Feedback button with 1–5 rating active from day 1 (PF21).
FP08 — v2 WITHOUT USER INTERVIEWS
Beginning v2 feature planning without completing at least 3 real user interviews on the v1 platform.
✓ Fix: 3 user interviews required before v2 planning begins (PF23).
FP09 — FRAMEWORK CHANGE MID-BUILD
Proposing to add or switch a frontend/backend framework mid-build because a feature "needs it."
✓ Fix: Stack is locked. Features fit the stack — not the reverse (PF12).
FP10 — FEATURE WITHOUT USER STORY
Adding a feature to a sprint without a plain-language user story in the format "As a [user], I need to..."
✓ Fix: Every feature has a one-sentence user story before approval (PF13).
FP11 — FINANCIAL FEATURE WITHOUT INTEGRITY CHECK
Shipping a Reserve Bank feature without verifying financial data integrity in staging (sum deposits == balance).
✓ Fix: Financial integrity check required before every Reserve Bank deploy (PF16).
FP12 — PRODUCTION LAUNCH WITHOUT STAGING VALIDATION
Launching any platform to production before 3 real users validate the primary workflow in staging.
✓ Fix: 3 real-user staging validations required before production (PF19).
FP13 — ROADMAP ITEM WITHOUT EXPIRY
Keeping a roadmap item with no user validation evidence for more than 3 months without action.
✓ Fix: Unvalidated roadmap items are removed or moved to "investigate" (PF26).
FP14 — FEATURE FLAG HARDCODED
Hardcoding a feature flag value in code instead of storing it in the FeatureFlag PostgreSQL table.
✓ Fix: All flags in FeatureFlag table with default false (PF10, B42).
FP15 — UNANNOUNCED PLATFORM DISCLOSED
Sharing details of an unregistered, unannounced KSDRILL SA platform with external parties.
✓ Fix: Confidentiality until Constitutional Order registration and public announcement (PF28).
FP16 — GROUP 3/4 FEATURES IN v1
Including Group 3 (secondary features) or Group 4 (nice-to-have) features in the v1 sprint plan.
✓ Fix: v1 = Groups 1+2 only. Groups 3+4 are deferred to v2+ (PF9).
