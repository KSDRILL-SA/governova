# Handoff — 2026-08-22

**The session that stopped adding standards and started asking whether the thing works when
somebody else installs it.** It did not. Two defects made the published `0.2.0` close to
unusable for an adopter, and both were invisible from a source checkout.

Read §8 first if you only read one section. It is the work order.

---

## 1. The finding that reframes everything

`governova` **is on PyPI** — `0.1.0` and `0.2.0`, the latter uploaded 2026-08-20. That was
established mid-session after being wrongly asserted otherwise, which is worth recording: the
check was `grep pypi README.md`, and the README never mentioned it. **Verify by asking the
registry, not the documentation.**

**The published `0.2.0` contains both defects below.** Anyone who ran `pip install governova`
between 2026-08-20 and the next release got them.

### 1a. `governova enforce .` reported the user's dependencies

The first command a new adopter types. Measured on a clean install into an empty project
containing exactly one real violation:

```
constitutional enforcement FAILED (51 blocking)
```

**Fifty of those 51 came from inside `.venv/Lib/site-packages/`.** `_candidate_files` expanded
a directory argument with a bare `rglob("*")` that never consulted `SKIP_DIRS`.

The exclusions existed. They were applied on the *other* branch of that same function — the one
used when no path is given, which is what CI uses, because **CI never passes a path**. So the CI
route was correct and the human route was not, and nothing noticed for as long as both existed.

This is worse than an ordinary false positive: every one of those 50 findings was *true* about
the line it cited. They were simply not the reader's code and could not be edited.

After: **1 finding**, and it is the user's.

### 1b. No installed user could ever be issued a Governova Score

`_constitutional_coverage` looked for `root / "compiled" / "constitution.json"` — a path that
exists only inside a Governova checkout. Every adopter got `no compiled index`.

`ADR-012` names that factor as **the one that reaches quorum**. Without it an installed
Governova sits permanently at 30% assessed, below the 50% threshold, and withholds the headline
number. The product's central metric was structurally unobtainable for everyone not running
from source.

`resolve_index_path` already existed and answers exactly this, in four ordered sources: explicit
path, `GOVERNOVA_CONSTITUTION`, a working-tree index found by walking up, the copy bundled in
the wheel. **Six surfaces bypassed it** — score, board report, dashboard, guardian, handoff,
hosted API — so each degraded differently once installed, and the environment override was
honoured by some commands and silently ignored by the rest. An organisation pointing Governova
at its own amended corpus got their constitution for `enforce` and ours for `govscore`.

Fixing only the score would have left five. `test_no_surface_hard_codes_the_checkout_relative_index`
asserts the mechanism across all of them.

### The first-run loop, verified against a built wheel

```
governova enforce .   ->  1 finding, the project's own
governova onboard     ->  a profile proposal, honest about what it cannot detect
governova govscore    ->  Governova Score: 60/100 [D]
```

The last line previously read "no score is issued", permanently, for every user.

## 3. Two things learned about writing rules

**Coverage counts standards, not rules.** The first batch shipped six rules and moved three
standards, because two sat on `S2.12`. Every batch since is one rule per distinct unevidenced
standard, and the rate went to 100%.

**Check for an existing claim before writing.** Four rules were written and dropped this
session because an existing rule already reported the same line: `AP-S2.27a` duplicated
`AP-S2.28f`, `S9.10` duplicated `AP-S1.68a`, and rules for deep imports and `console.log` were
already covered. Two more — `S2.20` and `S6.22` — were deliberately left unbound because a line
scanner cannot support the distinction their standards draw.

The repository's own `test_no_line_produces_findings_from_two_standards` caught `AP-S2.76a`
grading two standards before it landed. **Trust that guard; it works.**

## 4. `D-28` — a limit on how far rules can go

Because test files are correctly skipped, a standard about test *code* — `S7.3` asserting on
private state, `S7.10` mocking the thing under test, `S7.11` testing only the happy path of a
protected endpoint — **can never be evidenced by a rule**, however well written. Those need
probes, which read test files deliberately as evidence rather than scanning them as source.

`#246`'s count of rule-reachable standards is therefore slightly optimistic.

## 5. `D-29` — the same commit scores differently in CI and locally

Found by the README test, which passed locally and failed in CI. One commit, three
environments: **113** in a full checkout, **114** in a shallow clone of the same branch, **112**
in CI. The headline is 80 (B) in all three — the swing moves the weighted total by 0.04 and
rounds away, which is luck rather than design.

`+1` is explained. `actions/checkout@v7` defaults to `fetch-depth: 1`, and `_probe_squash_merge`
finds no merge commit in a one-commit history, so it returns **satisfied** for a repository that
genuinely carries one (`6debca9`, `D-18`). Wrong and confident, which is the worst combination —
and the same failure the `unknown`-never-`satisfied` discipline exists to prevent, arriving
through the environment instead of through the code.

**CI's 112 is not explained.** It is lower than both local numbers, so something else is moving
in the opposite direction. Ruled out by measurement: path separators (already normalised), line
endings (`splitlines` handles CRLF), and markdown (not in `TEXT_EXTENSIONS`). Not yet checked:
whether a rule fires on Linux but not Windows, and whether the analyser-backed standards differ.

`#324` carries the diagnosis order. **Do not fix anything before the cause is known** — the
tempting move is `fetch-depth: 0`, which hides the symptom while leaving every adopter's CI
wrong, since we do not control their checkout.

Consequence for now: the README states the score, which is reproducible, and does not state the
evidenced count, which is not. `test_the_readme_does_not_quote_an_unreproducible_count` holds
that line and is where the decision to publish the count again gets recorded.

Certified requires constitutional coverage ≥ 44 — **262 evidenced standards**. There are
**113**. At this session's best rate that is roughly 150 more rules.

That is real work and it is **not launch-blocking**. It is also the shape of the trap: a metric

**What is finished:** the engine. CLI, MCP server, CI enforcer, IDE extension, dashboard, board

**What is not:** distribution. Four of eight surface directories are empty plans
(`pr-guardian-bot`, `slack-teams-bot`, `web-dashboard`, `jetbrains-plugin`). And `D-09`: the
Cloud is written and **runs nowhere**.

## 7. The Cloud decision, and why it was deferred

KSDRILL-SA is now a registered company with a business bank account. That unlocks **receiving
money** — Stripe/Paystack onboarding, contracts, liability. It does not change deployment
readiness, and the two were kept separate deliberately.

**The deciding fact:** there is no database client anywhere in the codebase. `platform/cloud/prisma/`
holds a schema and a README — no migrations. The credit ledger is a Python list in RAM
(`self._entries`), as are organisations and memberships.

So deploying today means a customer buys credits, the process restarts, and the balance is
gone. `#255` calls the ledger financial code. For a newly registered company that is not an
incomplete feature; it is an incident.

**Decision: defer the paid Cloud to v2, ship the free engine now.** The engine runs complete and
offline forever by `ADR-010 §5.1`, so this costs nothing and removes deployment, a database, a
domain and `D-25`/`D-26`/`D-27` from the v1 path. The Cloud code stays in the repository,
unadvertised. `test_the_readme_does_not_promise_a_cloud_that_runs_nowhere` holds that line.

**One nuance worth remembering:** Stage 4, the hosted read API, is read-only and stateless by
construction and has no persistence problem. It could be deployed with no database at all —
the caveat being that it serves one repository which must be on the server's disk. That makes
it a demo, not multi-tenant SaaS. If a prospect appears before `D-27` is done, that is the
piece to deploy.

## 8. THE WORK ORDER

### Step 1 — Release `0.2.1`. **This is L4 and it is yours.**

Everything is prepared on `main`: version bumped in `scripts/pyproject.toml`, changelog written.
Publishing is OIDC Trusted Publishing — **no token exists or is needed**. Tag and push:

```bash
git tag v0.2.1
git push origin v0.2.1
```

`.github/workflows/release.yml` re-runs every gate against the exact commit before anything
reaches PyPI. **Do this first.** The currently published `0.2.0` is the broken one, and it is
what you would install to govern Xikimm xa Mali.

### Step 2 — Govern Xikimm xa Mali. **This is the real work.**

The first adopter, and the first time Governova governs something that is not Governova.
Everything before this was the tool grading its own author.

```bash
pip install --upgrade governova
cd <xikimm-xa-mali>
governova enforce .
governova onboard
governova govscore
```

**Record what happens, especially what goes wrong.** Every previous encounter with a codebase
Governova did not write produced a finding worth more than a week of rule-writing — `express`'s
20 false positives from `test/` produced the ignore list; the four-repository sweep produced
`ADR-012`; this session's install produced §1. Expect the same and treat it as the point of the
exercise rather than an interruption to it.

Specifically worth watching: whether `onboard` detects the stack, whether the findings are
*actionable* rather than merely true, and whether the Score is a number you would show someone.

### Step 3 — Wire the database (`D-27`).

Migrations, a client, and rewriting `governova_org` and `governova_ledger` against them. The
invariants are already expressed in `schema.prisma` — composite keys, unique constraints — so
this is transcription rather than design. Days, not hours.

Do this **before** any hosting decision. It is what makes the Cloud safe to deploy rather than
merely possible.

### Step 4 — Then decide on hosting.

With a working database, and hopefully with what Step 2 taught.

## 9. Standing rules that cost time when forgotten

- **Regenerate every number before trusting it, including the ones in this file.** The README
  advertised `78 (C)` and "61 of 596" while the engine computed `80 (B)` and 113.
  `test_readme_states_the_score_the_engine_computes` now fails CI on that drift.
- **`uv` is not on PATH.** `C:\Users\kurhu\AppData\Local\Python\pythoncore-3.14-64\Scripts`
- **The full suite takes ~7–10 minutes.** Run it in the background; do not poll it.
- **A closing keyword near `#NNN` in a commit or PR body closes that issue**, even inside a
  quotation or a negation. Check `gh issue list` after every merge.
- **Never run `ruff format` repo-wide.** CI runs `ruff check` only.
- **Measure a new rule through `iter_source_files`, never `scan_text` on a file walk.**
  `scan_text` does not consult the ignore list, and a sweep using it reported a file the
  scanner never reads.
- **L4 is human-only**: ratifying law, amending the constitution, tagging a release.
