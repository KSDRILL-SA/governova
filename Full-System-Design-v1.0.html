Deployment Order — Breaking Changes

5 Scenarios
Scenario A — Adding New Endpoint SAFE
1
Backend deploys new endpoint (returns 200)
2
Frontend deploys (calls new endpoint)
Backend already ready when frontend calls
Scenario B — Removing Endpoint SAFE
1
Frontend deploys (stops calling endpoint)
2
Backend removes endpoint (after 6-month deprecation — B44)
Frontend no longer calls when backend removes
Scenario C — Breaking Response Shape SAFE
1
Backend deploys /v2 endpoint with new shape
2
Frontend deploys (calls /v2)
3
Backend deprecates /v1 (Sunset header, 6 months)
Versioned API prevents breaking existing clients
Scenario D — New Error Code MITIGATE
1
Backend deploys (may return new error code)
2
Frontend deploys (error handler updated — Rule 62)
Risk: frontend shows raw error code until Step 2
Add error mapping BEFORE backend deploys, or use feature flag
Scenario E — Changing Rate Limit Tiers MITIGATE
1
Backend deploys new rate limit (may return 429 more often)
2
Frontend deploys updated retry-after handling (Rule 63)
Risk: 429 handling suboptimal until Step 2 completes
Rule 63 already requires robust 429 handling — any valid Retry-After header should be handled gracefully. Update countdown logic before backend tightens limits.

§ 09

Final Refinements & Recommendations

Added in Unified v1.0
Observability
Distributed Tracing
The X-Request-ID chain (Rule 61 + B29) is good for support, but add OpenTelemetry span correlation across Next.js → FastAPI → OpenAI for performance profiling. One trace ID should span the entire AI call chain — essential once production traffic hits.
Extends: Rule 61, B29, B41
Security
CSRF Token on Mutations
B45 covers HTTP-only cookies and CORS, but add an explicit CSRF double-submit cookie pattern on all state-changing API routes. SameSite=Lax alone is insufficient for cross-origin subdomains. Pair with a per-session CSRF token stored in a readable cookie + X-CSRF-Token header.
Extends: B45, B37
Resilience
Graceful AI Degradation
B36 defines circuit breaker but doesn't specify the degraded UX. When FastAPI or OpenAI is down, the frontend should show a static fallback (cached last answer, or "AI unavailable — try again shortly") rather than a generic error, giving users a path forward without support tickets.
Extends: B36, Rule 28, Rule 62
Data Integrity
Optimistic Update Rollback
TanStack Query supports optimistic updates — when the mutation fails, roll back with a toast notification matching the error code mapping (Rule 62). Without this, users see data that was never saved. Add a rollback pattern to the API client layer for all POST/PATCH mutations.
Extends: Rule 28, Rule 62, B30
Performance
Streaming Response UI
F10 defines streaming in FastAPI, and Rule 64 covers WebSocket. Document the exact streaming contract: use SSE (Server-Sent Events) for one-way AI responses, WebSocket only for true bidirectional chat. SSE is simpler to implement and debug, and Rule B22 already restricts WebSocket to /ws/chat only.
Extends: F10, Rule 64, B22
DX & Testing
Contract Testing (Pact)
OpenAPI validation in CI (ci-backend.yml) catches schema drift, but add consumer-driven contract tests with Pact. This ensures the frontend's actual usage of the API is tested against what the backend produces — catching the gap between spec and implementation before production.
Extends: B7, B10, B11, Rule 30
