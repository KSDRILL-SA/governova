PART 1 / I1–I8Deployment Platforms6 Critical · 2 High · Both Stacks
I1Vercel for All Next.js Deployments — Full-Stack UnifiedCritical
NEXT.JS STACK

All Next.js systems (Maphophe, SyncUp) deploy to Vercel. The frontend, API routes, and edge functions live in one unified deployment. Vercel handles automatic preview deployments for every PR, production deployment on main branch push, and environment variable management. No custom server setup is used — Vercel's Next.js integration is the deployment strategy.

I2Railway for FastAPI — Angular Stack Backend ExclusivelyCritical
ANGULAR STACK

All FastAPI backends (FundsLink, Reserve Bank) deploy to Railway. Railway provides: Python runtime, managed PostgreSQL, managed MongoDB, managed Redis, zero-downtime deploys, and environment variable management. Never deploy FastAPI to Vercel serverless functions — Python cold starts and long-running connections are incompatible with serverless architecture.

I3Angular Frontend on Vercel — Separate Project From FastAPICritical
ANGULAR STACK

The Angular frontend (FundsLink, Reserve Bank) deploys as a separate Vercel project from the FastAPI backend. Angular is a static SPA build — Vercel serves it perfectly. The two Vercel + Railway deployments are coordinated: FastAPI deploys first on breaking API changes, then Angular. Angular's environment.prod.ts points to the Railway FastAPI URL.

I4Preview Deployments on Every PR — Both StacksCritical
BOTH STACKS

Every PR generates an automatic preview deployment. Next.js: Vercel preview URL. Angular: Vercel preview URL for the frontend. For Angular stack PRs that change the API, Railway staging environment is updated. Preview deployments enable E2E test runs against the actual preview URL before merge.

I5Three Environments — Development, Staging, ProductionCritical
BOTH STACKS

Every system has three isolated environments: (1) Development — local docker-compose, (2) Staging — auto-deployed from main on every merge, used for E2E tests and final review, (3) Production — manually promoted from staging after explicit approval. Code never goes directly from development to production. Each environment has its own database, secrets, and URL.

I6Zero-Downtime Deploys — Rolling or Blue-GreenCritical
BOTH STACKS

Production deployments must not cause downtime. Vercel deploys atomically with instant rollover. Railway deploys use rolling restarts with a minimum 1 healthy replica before killing the old one. Database migrations (run before the service starts — I&B55) must be backward-compatible with the previous version to support rolling deploys.

I7Deployment Rollback — One Command, Under 5 MinutesCritical
BOTH STACKS

Any production deployment must be rollbackable within 5 minutes using a single command or UI action. Vercel: one-click rollback to previous deployment. Railway: redeploy previous build. Database rollbacks follow the migration rollback plan (Database Constitution D19). Rollback procedures are tested in staging quarterly.

I8ChromaDB on Railway — Separate Service, Persistent VolumeHigh
ANGULAR STACK — FUNDSLINK ONLY

ChromaDB runs as a separate Railway service with a persistent volume mount. The volume ensures embedding data survives service restarts and redeployments. The FastAPI service connects to ChromaDB via its Railway internal URL — not via public internet. ChromaDB's Railway service has no public port exposure.

CI Pipeline Steps
  • 1st Lint + format check
  • 2nd Type check (tsc / mypy)
  • 3rd Unit + integration tests
  • 4th Coverage gate
  • 5th Critical E2E tests
  • 6th Security scan

PART 2 / I9–I16CI/CD Pipeline6 Critical · 2 High · All Stacks
I9GitHub Actions for All CI — Separate Workflow Per StackCritical
ALL STACKS

All CI/CD pipelines run on GitHub Actions. Each repository has its own workflow files: ci.yml (runs on PR), deploy-staging.yml (runs on main merge), deploy-production.yml (manually triggered). Angular stack repos have two workflows each — one for the Angular frontend repo, one for the FastAPI repo.

I10CI Runs in Under 5 Minutes — Parallelise TestsCritical
ALL STACKS

The PR CI pipeline completes in under 5 minutes. Achieve this via: parallel job matrix (lint, typecheck, tests run simultaneously), test file sharding for large test suites, and Docker layer caching for builds. A CI run taking over 10 minutes is treated as a performance bug and must be fixed within one sprint.

I11Automatic Staging Deploy on main Merge — No Manual Staging DeploysCritical
ALL STACKS

Every merge to main automatically deploys to staging. For Angular systems: Railway (FastAPI) deploys first, then Vercel (Angular) deploys. The staging deployment is the canonical test bed for final QA and E2E validation before production. Never manually deploy to staging by pushing directly — always go through CI.

I12Production Deploy Is Manual and Gated — Explicit Approval RequiredCritical
ALL STACKS

Production deployments are triggered manually via GitHub Actions workflow_dispatch with an environment: production protection rule requiring explicit owner approval. No automatic production deploys. The production deploy workflow only runs after staging has been validated and approval is granted. This prevents accidental production deploys.

I13Dependency Caching in CI — npm ci and pip install CachedCritical
ALL STACKS

All CI pipelines cache dependency installations using GitHub Actions cache action keyed on lock file hash. TypeScript: cache ~/.npm keyed on package-lock.json hash. Python: cache ~/.cache/pip keyed on requirements.txt hash. Uncached CI runs are 3× slower — caching is mandatory, not optional.

I14Prisma Migrations Validated in CI — prisma migrate diff on Every PRCritical
ALL STACKS

PRs that change schema.prisma automatically run prisma migrate diff in CI to detect schema drift and validate the migration. The CI step fails if the migration is missing or inconsistent with the schema change. This prevents deploying a schema change without a corresponding migration.

I15Build Artefacts Cached Between CI Steps — Docker Layer CacheHigh
ALL STACKS

Docker builds in CI use --cache-from and GitHub Container Registry as the cache source. Build steps that haven't changed (dependency layer, base image) are reused from cache. This reduces build times from 5+ minutes to under 1 minute for incremental changes.

I16Angular CI Deploys Coordinated — FastAPI First, Angular SecondHigh
ANGULAR STACK

The Angular stack staging deploy GitHub Actions workflow orchestrates the deploy sequence: (1) trigger Railway FastAPI deploy and wait for health check, (2) only if FastAPI deploy succeeds, trigger Vercel Angular deploy. If FastAPI deploy fails, Angular deploy is skipped. This prevents Angular calling endpoints that don't exist yet.

PART 3 / I17–I23Docker & Local Development5 Critical · 2 High · All Stacks
I17docker-compose up — Full Stack in One CommandCritical
ALL STACKS

docker-compose up starts the complete local development environment. A new developer clones the repo, copies .env.example to .env, fills in the values, and runs docker-compose up — the full stack is running. No manual service installation, no per-machine configuration. This is enforced by a CONTRIBUTING.md that has no manual setup steps beyond these two.

I18Multi-Stage Dockerfiles — Development and Production StagesCritical
ALL STACKS

All Dockerfiles use multi-stage builds with at least two stages: development (with hot reload, dev dependencies) and production (minimal image, no dev tools). The production image must be under 500MB. Base images pin to exact version tags — never :latest.

I19No Root User in Docker Containers — Non-Root User RequiredCritical
ALL STACKS

All Docker containers run as a non-root user. Add USER node (Node.js) or USER appuser (Python) to the Dockerfile after installing dependencies. Running as root in production containers is a security vulnerability — container escape attacks gain full host access when running as root.

I20Health Checks in docker-compose — All Services Declare healthcheckCritical
ALL STACKS

Every service in docker-compose.yml declares a healthcheck block. Application services use their /health endpoint. Databases use built-in healthcheck commands. Services with depends_on use condition: service_healthy — not service_started. This ensures services don't start until their dependencies are truly ready.

I21Pinned Base Images — Never :latest TagCritical
ALL STACKS

All base images in Dockerfiles and docker-compose pin to exact version: node:20.11.1-alpine3.19, python:3.11.8-slim-bookworm. The :latest tag is forbidden — it causes non-deterministic builds when upstream images update. Dependabot or Renovate handles base image version bumps automatically.

I22.dockerignore — Exclude node_modules, .env, __pycache__High
ALL STACKS

Every repo has a .dockerignore file that excludes: node_modules/, .env* (all env files), __pycache__/, .pytest_cache/, coverage/, .git/, and *.test.ts. These exclusions reduce Docker build context size and prevent secrets from being baked into images.

I23Volume Mounts for Local Dev — Source Code Hot ReloadsHigh
ALL STACKS

Development docker-compose mounts source code as a volume for hot reload. Next.js: ./:/app:delegated with node_modules excluded via anonymous volume. FastAPI: ./:/app:ro with --reload uvicorn flag. Angular: ng serve with --poll for Docker volume change detection.

PART 4 / I24–I30Environment Configuration5 Critical · 2 High · All Stacks
I24.env Files Never Committed — .env.example Is the ContractCritical
ALL STACKS

No .env, .env.local, .env.production, or any file containing actual secret values is committed to any repository. The .env.example file contains all required variable names with placeholder values and descriptions. .gitignore blocks all .env* files. A pre-commit hook scans for common secret patterns and blocks commits containing them.

I25Vercel Environment Variables for Next.js — Railway Secrets for FastAPICritical
ALL STACKS

Production secrets are stored in the deployment platform's secret manager. Next.js systems: Vercel Environment Variables (scoped per environment). Angular FastAPI: Railway Secrets. Never store production secrets in GitHub Secrets unless needed for CI — prefer pulling them from the deployment platform at runtime.

I26Environment Validation at Startup — Fail Fast on Missing VariablesCritical
ALL STACKS

Application startup validates all required environment variables before accepting requests. Next.js: use a lib/env.ts Zod schema that validates process.env at module load. FastAPI: use a Pydantic Settings class with model_config = ConfigDict(env_file=".env"). Missing required variables crash the startup with a clear error message.

I27Separate Environment Variables Per Stage — No Shared SecretsCritical
ALL STACKS

Development, staging, and production each have completely separate secrets — separate database credentials, separate API keys, separate JWT secrets. Never use production database credentials in staging or development. This prevents accidental data mutation in production during testing and limits blast radius of a secret leak.

I28Node.js Version Pinned in package.json and .nvmrcCritical
BOTH TS STACKS

The Node.js version is pinned in package.json engines.node field and in .nvmrc. Vercel uses the engines.node field to set the runtime version. All developers use the same version via nvm. Version mismatches between local, CI, and production are a common source of bugs — eliminate them at the configuration level.

I29CORS Origins from Environment Variable — Never HardcodedHigh
ALL STACKS

CORS allowed origins are read from the CORS_ORIGINS environment variable as a comma-separated list. Never hardcode domain names in application code. This allows staging to permit preview deployment URLs while production permits only the production domain — controlled per environment without code changes.

I30Python Version Pinned in pyproject.toml and .python-versionHigh
ANGULAR STACK

Python version is pinned in pyproject.toml [tool.poetry.dependencies] python = "^3.11" and in a .python-version file for pyenv. Railway uses the .python-version file to set the runtime. This ensures consistent Python version across local development, CI, and Railway deployment.

  • Disk >85% → alert
PART 5 / I31–I38Monitoring & Alerts4 Critical · 4 High · All Stacks
I31Sentry Installed and Configured Before Launch — Source Maps UploadedCritical
ALL STACKS

Sentry error tracking is configured before any system goes live. Next.js: @sentry/nextjs with automatic source map upload on every Vercel build. Angular: @sentry/angular with source maps. FastAPI: sentry-sdk[fastapi] with traces_sample_rate=0.1 for performance monitoring. Without source maps, Sentry stack traces are unreadable.

I32Better Stack Uptime Checks — All Public Endpoints MonitoredCritical
ALL STACKS

Better Stack monitors all public-facing URLs with 1-minute check intervals. For each system: the frontend URL, the /health API endpoint, and any critical API paths. Downtime alerts go to WhatsApp within 2 minutes. Monthly uptime reports are reviewed in the sprint retrospective.

I33Structured Logging — JSON Format, All ServicesCritical
ALL STACKS

All services emit structured JSON logs. Every log entry includes: timestamp, level, service, message, requestId (when applicable). Next.js: pino or Winston with JSON formatter. FastAPI: structlog with JSON renderer. Logs are searchable in Vercel Log Drain and Railway Log Explorer.

I34Performance Budgets — LCP, FCP, TTI Monitored via Vercel AnalyticsCritical
BOTH TS STACKS

Vercel Analytics tracks Core Web Vitals in production. Alerts trigger when: LCP exceeds 2.5s, FCP exceeds 3s, TTI exceeds 3.5s on mobile. These match the performance targets in the Frontend Constitution. Vercel Speed Insights is enabled on all frontend projects. Performance regressions are treated as bugs.

I35Railway Metrics — CPU, Memory, Response Time DashboardsHigh
ANGULAR STACK

Railway's built-in metrics dashboard tracks CPU usage, memory consumption, and request volume for all FastAPI services. Alerts are configured for: CPU >80% for 5 minutes, memory >80%, response time p95 >500ms. Prometheus metrics endpoint is exposed at /metrics for custom dashboards.

I36Error Rate Alerting — >1% Error Rate Triggers Immediate AlertHigh
ALL STACKS

Sentry is configured to alert when the error rate for any endpoint exceeds 1% over a 5-minute window. Alerts go to the owner immediately. Error rate spikes are treated as potential incidents — investigated within 30 minutes. The Sentry issue dashboard is reviewed at the start of every sprint.

I37Database Connection Pool Monitoring — Alert on Pool ExhaustionHigh
ALL STACKS

PostgreSQL connection pool usage is monitored. Alert when pool utilisation exceeds 80%. This is an early warning for connection leaks or traffic spikes that will soon cause connection timeouts. Railway's managed Postgres exposes connection count metrics. Next.js systems using Vercel Postgres have built-in pool monitoring.

I38Deployment Success Notifications — WhatsApp on Every Production DeployHigh
ALL STACKS

A GitHub Actions step at the end of every successful production deploy sends a notification including: system name, version deployed, deploy duration, and a link to the deployment. Failed deployments send an immediate alert. This creates an audit trail of all production changes and ensures awareness of active deployments.

PART 6 / I39–I46Infrastructure Security5 Critical · 3 High · All Stacks
I39Dependency Vulnerability Scanning — npm audit and Safety in CICritical
ALL STACKS

CI runs npm audit --audit-level=high (TypeScript repos) and pip-audit (Python repo) on every PR. High and Critical severity vulnerabilities fail the build. Dependabot is enabled on all repos and auto-creates PRs for dependency updates. Critical security patches are merged and deployed within 48 hours of discovery.

I40Secret Scanning — trufflehog Blocks Commits Containing SecretsCritical
ALL STACKS

TruffleHog or GitHub's native secret scanning runs on every push to scan for committed secrets (API keys, credentials, tokens). GitHub's secret scanning is enabled at the organisation level. A pre-commit hook also runs a local scan before any commit. A detected secret triggers immediate rotation — not just removal from history.

I41All Internal Services on Private Network — No Public Internet ExposureCritical
ANGULAR STACK

On Railway, internal services (PostgreSQL, MongoDB, Redis, ChromaDB) are on Railway's private network — they have no public TCP port. FastAPI connects to them via Railway's private network URLs (postgres.railway.internal). Only the FastAPI HTTP port is publicly accessible, via Railway's public domain with TLS termination.

I42Docker Image Scanning — Snyk or Trivy on Every BuildCritical
ALL STACKS

Container images are scanned for OS-level vulnerabilities using Snyk or Trivy in CI. High/Critical OS vulnerabilities in the base image or installed packages fail the build. This is separate from dependency scanning — OS vulnerabilities in the Alpine or Debian base image must also be addressed.

I43GitHub Actions Permissions — Least Privilege on All WorkflowsCritical
ALL STACKS

All GitHub Actions workflows declare explicit permissions: blocks with the minimum required permissions. Default: contents: read. Workflows that deploy add deployments: write. Workflows that create PRs add pull-requests: write. The global default in GITHUB_TOKEN permissions is set to read-all at the organisation level.

I44TLS Everywhere — HTTPS Only, HSTS Header SetHigh
ALL STACKS

All public endpoints are served over HTTPS only. Vercel and Railway handle TLS termination automatically. HTTP requests are redirected to HTTPS. The Strict-Transport-Security header is set with max-age=31536000; includeSubDomains on all responses. Internal service-to-service communication on Railway private network may use plain HTTP.

I45Rate Limiting at Infrastructure Level — Vercel and Railway EdgeHigh
ALL STACKS

In addition to application-level rate limiting (Backend Constitution B26), infrastructure-level rate limiting is configured at Vercel Edge (Next.js) and Railway (FastAPI). Infrastructure rate limiting handles volumetric DDoS before requests reach application code. Application rate limiting handles per-user and per-endpoint limits.

I46Quarterly Security Review — Audit All Secrets and AccessHigh
ALL STACKS

Every quarter, review and rotate: all API keys and secrets, all database passwords, all JWT signing keys, all third-party integration tokens. Review GitHub organisation member access and remove stale access. Audit Railway and Vercel team member permissions. Document the review outcome in the GitHub constitutional governance issue.

§ Annex A — Forbidden Patterns (FP01–FP18)
⚠ FORBIDDEN PATTERNS — VIOLATION = SECURITY OR DEPLOYMENT FAILURE
FP01 — FASTAPI ON VERCEL
Deploying any Python/FastAPI service to Vercel serverless functions.
✓ Fix: FastAPI on Railway exclusively (I2).
FP02 — :LATEST DOCKER TAG
Using :latest for any base image in Dockerfiles or docker-compose.
✓ Fix: Pinned exact version tags always (I21).
FP03 — ROOT USER IN CONTAINERS
Docker containers running as root in any environment including development.
✓ Fix: USER directive in Dockerfile after dep install (I19).
FP04 — .ENV FILES COMMITTED
Any .env, .env.local, or .env.production file committed to any repository.
✓ Fix: .gitignore + .env.example pattern (I24).
FP05 — AUTOMATIC PRODUCTION DEPLOY
GitHub Actions automatically deploying to production on main branch push.
✓ Fix: Manual workflow_dispatch with environment protection (I12).
FP06 — SHARED SECRETS ACROSS ENVIRONMENTS
Using the same database URL or API key in staging and production.
✓ Fix: Separate secrets per environment — no sharing (I27).
FP07 — NO HEALTH CHECKS IN DOCKER-COMPOSE
Services in docker-compose without healthcheck declarations.
✓ Fix: Every service declares healthcheck block (I20).
FP08 — HARDCODED CORS ORIGINS
Domain names hardcoded in application code instead of CORS_ORIGINS env var.
✓ Fix: CORS_ORIGINS from environment variable only (I29).
FP09 — NO SENTRY BEFORE LAUNCH
Launching any system publicly without Sentry error tracking configured.
✓ Fix: Sentry installed and source maps uploaded pre-launch (I31).
FP10 — INTERNAL SERVICES PUBLICLY EXPOSED
PostgreSQL, MongoDB, Redis, or ChromaDB accessible from the public internet. [Angular]
✓ Fix: All databases on Railway private network only (I41).
FP11 — SKIPPING DEPENDENCY AUDIT
Merging a PR where npm audit or pip-audit found High/Critical vulnerabilities.
✓ Fix: CI fails on high/critical vulnerabilities — fix before merge (I39).
FP12 — DIRECT DEPLOY TO PRODUCTION BYPASSING STAGING
Deploying code to production that has not been deployed to staging first.
✓ Fix: Three environments enforced — staging is the gate (I5, I12).
FP13 — CONSOLE.LOG IN DOCKERFILE
Any debugging or print statement in Dockerfile RUN commands.
✓ Fix: Silent builds — redirect output to /dev/null if needed.
FP14 — NO ROLLBACK PLAN FOR PRODUCTION DEPLOY
Deploying to production without a documented and tested rollback procedure.
✓ Fix: Rollback must complete in under 5 minutes (I7).
FP15 — UNENCRYPTED HTTP IN PRODUCTION
Any production endpoint serving over HTTP instead of HTTPS.
✓ Fix: TLS on all public endpoints — Vercel + Railway enforce this (I44).
FP16 — GITHUB ACTIONS WILDCARD PERMISSIONS
Workflow files without explicit permissions block — uses default write-all.
✓ Fix: Explicit permissions block with least privilege (I43).
FP17 — UNCACHED CI DEPENDENCIES
CI pipelines that reinstall all npm/pip packages from scratch on every run.
✓ Fix: Cache node_modules and pip packages in GitHub Actions (I13).
FP18 — MISSING .DOCKERIGNORE
Docker builds without .dockerignore — copies node_modules and .env files into image.
✓ Fix: .dockerignore required on every repo (I22).
