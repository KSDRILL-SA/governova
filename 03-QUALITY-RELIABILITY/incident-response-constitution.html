All users blocked from primary workflow

PART 1 / IR1–IR8 Severity Framework 5 Critical · 3 High · Both Stacks
IR1Every Incident Is Classified — SEV0 Through SEV3 Within 5 Minutes of DetectionCritical
BOTH STACKS

The first action on detecting any production issue is classification. Within 5 minutes of detection, the engineer assigns a severity level (SEV0–SEV3) based on the definitions above. Classification determines the response SLA, incident commander, and communication requirements. If uncertain between two levels, always classify at the higher severity — it can be downgraded once more information is available.

IR2Incident Declaration — GitHub Issue Opened Within 10 Minutes, Tagged incidentCritical
BOTH STACKS

Every SEV0 and SEV1 incident triggers a GitHub Issue in the affected system's repository within 10 minutes of declaration. The issue is tagged incident and sev0 or sev1. The issue title follows the format: [SEV0] Platform outage — auth service down. The issue body records: detection time, classification time, symptoms observed, affected systems, and initial hypothesis.

IR3Incident Commander — Single Point of Coordination, Assigned Within 15 MinutesCritical
BOTH STACKS

Every SEV0 and SEV1 incident has a single designated Incident Commander within 15 minutes. The Incident Commander makes all decisions, coordinates the response, owns communication, and signs off on resolution. No decision-by-committee during an active incident — one person is in charge. The Incident Commander does not necessarily do the technical work.

IR4SEV0 Response — Restore Service First, Root Cause SecondCritical
BOTH STACKS

For SEV0 incidents, the priority order is: (1) Restore service to users as fast as possible — rollback, failover, hotfix, whatever works fastest. (2) Document what was done. (3) Investigate root cause after service is restored. Never delay a rollback to investigate why something broke — restore first, understand second.

IR5Reserve Bank Financial Incidents — Zero-Tolerance, Immediate FreezeCritical
ANGULAR STACK — RESERVE BANK

Any incident involving financial data integrity — incorrect balances, failed deposits, interest miscalculation, or transaction duplication — is automatically SEV0 regardless of user impact scale. The incident commander immediately freezes all deposit and withdrawal operations via a feature flag. No financial operations resume until the data integrity issue is fully resolved and verified.

!
Financial incident protocol: The feature flag DEPOSITS_ENABLED and WITHDRAWALS_ENABLED are set to false as the first action. No exceptions. A freeze that turns out to be unnecessary is better than processed incorrect transactions.
IR6FundsLink AI Incidents — Degrade Gracefully, Show Static FallbackHigh
ANGULAR STACK — FUNDSLINK

When the LangChain/ChromaDB AI matching service fails, FundsLink degrades gracefully — the circuit breaker (B36) triggers and users see a static "AI matching temporarily unavailable — apply manually" screen. This is not a platform outage (SEV2, not SEV0). The static application flow must always be available as a fallback for the AI-powered flow.

IR7Status Updates Every 30 Minutes — Active SEV0 and SEV1 IncidentsHigh
BOTH STACKS

During active SEV0 and SEV1 incidents, the incident commander publishes a status update every 30 minutes on the GitHub issue. The update contains: current status, what was tried, what is being tried now, next update time. Updates that say "still investigating" without new information are acceptable — absence of updates is not.

IR8Incident Resolution — Declared by Incident Commander After 15-Minute Stability WindowHigh
BOTH STACKS

An incident is resolved only when: (1) the service is restored and functioning correctly for all users, (2) the fix has been stable for at least 15 minutes, (3) monitoring shows no anomalies, (4) the incident commander formally declares resolution in the GitHub issue. Never declare resolution optimistically — wait for the 15-minute stability window.

§ Part 2 — Detection & Alerting (IR9–IR14)
Alert Stack
  • Sentry Error rate + new issues
  • Better Stack Uptime + latency
  • Railway FastAPI + DB health
  • Vercel Deploy + edge errors
  • GitHub CI failure notifications
Alert Thresholds
  • Error rate >1% → SEV1 alert
  • p95 latency >500ms → warn
  • p95 latency >2s → SEV2 alert
  • Uptime <99.9% → SEV1 alert
  • DB conn pool >80% → warn
PART 2 / IR9–IR14 Detection & Alerting 3 Critical · 3 High · Both Stacks
IR9Sentry Error Rate Alerts — 1% Error Rate Triggers SEV1 EvaluationCritical
BOTH STACKS

Sentry is configured with an alert rule: if the error rate on any endpoint exceeds 1% of requests over a 5-minute window, a SEV1 evaluation alert is sent via email and GitHub notification. A new unique Sentry issue (not previously seen in production) triggers an immediate SEV2 alert. New issues touching auth, financial, or data integrity paths trigger SEV1 immediately.

IR10Better Stack Uptime — 1-Minute Check Interval, 3 Failures = SEV0 AlertCritical
BOTH STACKS

Better Stack monitors the /health endpoint of every production service every 60 seconds. Three consecutive health check failures trigger a SEV0 alert sent to the incident commander immediately. The /health endpoint must return a 200 with database connectivity status — a degraded database triggers the alert even if the app is technically up.

Next.js Stack
Monitor: Vercel deployment URL /api/health. Checks: Next.js app UP + PostgreSQL connectivity. Alert on 3 failures in 3 minutes.
Angular Stack
Monitor: Railway FastAPI URL /health. Checks: FastAPI UP + PostgreSQL + MongoDB + ChromaDB (FundsLink). Alert on 3 failures in 3 minutes.
IR11Railway Metrics Alerts — FastAPI CPU/Memory and DB Connection PoolCritical
ANGULAR STACK

Railway is configured with metric alerts: (1) FastAPI container CPU above 85% for 5 minutes → SEV2 alert, (2) Memory above 90% for 5 minutes → SEV1 alert (likely memory leak), (3) PostgreSQL connection pool above 80% utilisation → SEV2 warning, (4) Railway service restart detected → immediate SEV1 alert for investigation.

IR12Vercel Deploy Failure Alerts — CI/CD Pipeline Failures Notified ImmediatelyHigh
BOTH STACKS

Vercel deploy failures on the main branch trigger an immediate GitHub notification and email to the owner. A failed production deploy is treated as a SEV2 incident — the previous deployment remains live, but the failed deployment must be investigated and fixed in the current sprint. Deploy failures are never silently ignored.

IR13Latency Degradation — p95 Above 2s on Any Critical Endpoint Is SEV2High
BOTH STACKS

Better Stack tracks p95 response time for all critical endpoints (auth, primary feature, financial operations). p95 above 500ms triggers a warning. p95 above 2 seconds on any critical endpoint sustained for more than 5 minutes is classified as SEV2 and triggers an incident response. The threshold is tighter for financial endpoints — 1 second p95 triggers SEV2.

IR14On-Call Awareness — Owner Notified of All SEV0 and SEV1 Alerts 24/7High
BOTH STACKS

SEV0 and SEV1 alerts are delivered via email AND WhatsApp to Maluleke Kurhula Success regardless of time of day. Better Stack and Sentry are configured with mobile notifications for critical alerts. SEV2 and below are email-only and reviewed during working hours. The alert delivery chain is tested monthly — a silent alerting system is a broken alerting system.

IR17Auth System Down — Session Invalidation or JWT FailureCritical
BOTH STACKS

Auth system failures are auto-classified SEV0. Response: (1) Check if the failure is in the NextAuth session database (Next.js) or JWT signing key availability (Angular/FastAPI). (2) For Next.js: check PostgreSQL session table accessibility. (3) For Angular: check Railway Secrets accessibility for JWT_PRIVATE_KEY. (4) If JWT secret is the cause, rotate it and redeploy — all users will need to re-login, which is acceptable.

Next.js — NextAuth Failure
Check PostgreSQL Session table accessible. Check NEXTAUTH_SECRET env var present. Rollback last Vercel deploy if recent.
Angular — JWT Failure
Check JWT_PRIVATE_KEY in Railway Secrets. Check FastAPI /health for auth dependency. If key rotated, all sessions invalidated — users re-login.
IR18Database Down — PostgreSQL or MongoDB UnavailableCritical
BOTH STACKS

Database unavailability is SEV0. The /health endpoint failure indicates DB issue. Response: (1) Check Railway PostgreSQL service status dashboard. (2) If Railway DB is down: check Railway status page for platform-wide incident. If Railway platform issue — wait and monitor. (3) If connection pool exhausted: restart the application service to reset connections. (4) If migration failed mid-run: check the _prisma_migrations table for failed migration and fix or roll back.

IR19FundsLink AI Service Down — LangChain or ChromaDB FailureHigh
ANGULAR STACK — FUNDSLINK

AI service failure is SEV1. Circuit breaker (B36) should have already degraded the frontend to static mode. Response: (1) Verify circuit breaker is open and users see the static fallback (not a broken screen). (2) Check ChromaDB container health on Railway. (3) Check LangChain API rate limits or outage. (4) Restart ChromaDB container if needed. (5) Manually reset circuit breaker once service recovers. AI failure is not a financial or data integrity issue — the manual application path remains available.

IR20Performance Degradation — Latency Above SLA ThresholdsHigh
BOTH STACKS

p95 above 2s sustained for 5+ minutes is SEV2. Response: (1) Check slow query logs in PostgreSQL and MongoDB. (2) Identify the slowest endpoint in Sentry performance traces. (3) Check if a new deploy introduced an unindexed query. (4) Scale Railway service tier if under-provisioned. (5) Check for N+1 query patterns in recent code changes. Hotfix with a targeted index or query optimisation if identified.

IR21BullMQ Job Failures — Scheduled Jobs Failing (Reserve Bank / SyncUp)High
BOTH STACKS WHERE APPLICABLE

BullMQ job failures (deposit schedules on Reserve Bank, negotiation timers on SyncUp) are SEV1 if they affect financial operations, SEV2 otherwise. Response: (1) Check Redis connection health. (2) Check BullMQ dashboard for failed job queue depth. (3) Check for stalled workers. (4) If Redis is down: restart Railway Redis service. (5) Manually retry stalled jobs after worker recovery. Financial jobs (deposits, interest runs) that failed must be audited — each missed job logged in AuditLog.

IR22Vercel Edge Function Errors — Next.js Middleware FailureHigh
NEXT.JS STACK

Vercel edge function errors surface as 500 responses or auth bypasses. Response: (1) Check Vercel function logs in dashboard. (2) If middleware is throwing: rollback to previous Vercel deployment (one click). (3) If environment variables are missing: add missing vars in Vercel project settings and redeploy. (4) Never debug Vercel edge issues in production — rollback first, fix in staging.

IR23Railway Service Crash — FastAPI Container Restart LoopHigh
ANGULAR STACK

A FastAPI service entering a restart loop on Railway is SEV1. Response: (1) Check Railway deployment logs for the crash reason. (2) If OOM: scale service memory tier in Railway settings. (3) If missing env var: add it in Railway Secrets and redeploy. (4) If startup error: check Prisma migrate step completed before uvicorn start. (5) If the issue is unclear: rollback to previous Railway deployment immediately, debug from there.

IR24Data Inconsistency Across Databases — PostgreSQL / MongoDB Sync FailureHigh
ANGULAR STACK

Cross-database sync failures (D48–D50) where a PostgreSQL write succeeded but MongoDB failed are SEV1. Response: (1) The incident is already logged in Sentry via IR49 (D49 rule). (2) Identify affected entity IDs from the Sentry error. (3) Manually replay the failed MongoDB write using the PostgreSQL record as source of truth. (4) Verify sync with an integrity check query. (5) Investigate why the automatic retry queue did not recover the sync.

§ Part 4 — Rollback Procedures (IR25–IR32)
Rollback Decision Tree
  • Q1 Did a deploy happen in last 30m?
  • → Yes Rollback first
  • → No Check DB + config
  • Q2 Is the DB involved?
  • → Yes Restore backup path
  • → No Hotfix path
Rollback Times (Target)
  • Vercel <2 min (1-click)
  • Railway <5 min (UI or CLI)
  • DB migration <15 min (tested)
  • Full restore <30 min (from backup)
PART 4 / IR25–IR32 Rollback Procedures 4 Critical · 4 High · Stack-Specific
IR25Vercel Rollback — One-Click, Completes in Under 2 MinutesCritical
BOTH STACKS — FRONTEND

Vercel stores all previous deployments. Rolling back is one click: Vercel Dashboard → Deployments → select last known good deployment → "Promote to Production". Target: under 2 minutes. This is the fastest resolution path for any deploy-caused incident. Every engineer must know this procedure by memory — it is tested in monthly drills.

Path
Vercel Dashboard → Project → Deployments → last good → "Promote to Production"
Time target
Under 2 minutes from decision to live
When to use
Any SEV0/SEV1 incident where a deploy occurred in the last 30 minutes
IR26Railway Rollback — Previous Deployment, Under 5 MinutesCritical
ANGULAR STACK — FASTAPI

Railway stores the last 20 deployments. Rolling back: Railway Dashboard → Service → Deployments → select previous deployment → "Redeploy". Target: under 5 minutes. If the current deployment caused a database migration, the rollback does not undo the migration — apply a corrective migration separately (never modify a deployed migration file per D53).

!
Migration caveat: Rolling back a Railway deployment does not roll back applied Prisma migrations. If the migration itself is the problem, run a corrective migration — not a code-only rollback. Coordinate with the database rollback runbook (IR28).
IR27Hotfix Deploy — Emergency PR With Bypassed Review Requires Post-Incident DocumentationCritical
BOTH STACKS

When a rollback is not possible and a hotfix is required for SEV0 resolution, the normal 2-approval review requirement is reduced to 1 approval. The hotfix PR must be small, targeted, and merged as quickly as possible. After resolution, a post-incident PR is opened to: (1) add a test that catches the bug, (2) document why the hotfix was necessary, (3) get the full 2-approval review that was bypassed.

IR28Database Migration Rollback — Corrective Migration, Not File ModificationCritical
BOTH STACKS

When a database migration causes an incident, the fix is always a new corrective migration — never editing the deployed migration file (D53). The corrective migration must be tested in staging first, even during an active incident. If staging cannot be tested quickly, the DBA (Maluleke) approves direct production application with a verbal review substitute documented in the incident issue.

IR29Feature Flag Kill Switch — Any Feature Can Be Disabled Without a DeployHigh
BOTH STACKS

Every major feature ships behind a feature flag stored in the database (B42). In an incident, the flag can be set to false via a database update — disabling the feature for all users without a deployment. This is the fastest path for feature-specific SEV1 incidents. The feature flag admin endpoint (/api/admin/features) is ADMIN-only and RBAC-protected.

IR30Database Backup Restore — Tested Procedure, Under 30 MinutesHigh
BOTH STACKS

Database restoration from backup is a documented, tested procedure that completes in under 30 minutes. Railway managed PostgreSQL and MongoDB backups can be restored from the Railway dashboard. The restore procedure is documented in the system-design-template wiki and tested monthly in staging. A restore that has never been tested is not a backup — it is a hope.

IR31Post-Rollback Verification — Health Check + Smoke Test Before Declaring StableHigh
BOTH STACKS

After any rollback (code or database), run the following verification sequence before declaring the incident resolved: (1) /health endpoint returns 200 with all dependencies green, (2) Manually perform the primary user workflow that was affected (smoke test), (3) Sentry error rate returns to pre-incident baseline, (4) Wait 15 minutes of stability before formal declaration (IR8).

IR32Rollback Drills — Monthly Practice, Results DocumentedHigh
BOTH STACKS

Rollback procedures are practiced monthly in the staging environment: (1) Deploy a deliberately broken version, (2) Execute the Vercel/Railway rollback procedure, (3) Time the process and document the result. If a rollback takes longer than the target time, investigate and improve the procedure. Drill results are logged in system-design-template under docs/drills/.

  • SEV3 GitHub issue only
Message Principles

PART 5 / IR33–IR38 Incident Communication 2 Critical · 4 High · Both Stacks
IR33User Communication — Honest, Plain Language, Within 15 Minutes of SEV0 DeclarationCritical
BOTH STACKS

SEV0 incidents affecting users require a public-facing communication within 15 minutes of declaration. The message uses plain language: "We are aware of an issue with [feature] and are working to fix it. We will update you by [time]." Never communicate technical details, blame, or root cause in user-facing messages. Update every 30 minutes until resolution.

IR34Reserve Bank User Notification — Personal Communication for Financial IncidentsCritical
ANGULAR STACK — RESERVE BANK

Any financial incident that affected a user's account — even if corrected — requires a personal notification to that user after resolution. The notification explains: what happened, when it happened, that it has been corrected, and what the user's current balance is. This is sent via email to every affected account holder. Generic platform-wide notices are insufficient for financial incidents.

IR35Internal Incident Channel — GitHub Issue Is the Single ThreadHigh
BOTH STACKS

All incident-related communication happens in the GitHub issue — not in WhatsApp messages, DMs, or emails that others cannot see. WhatsApp is for alert delivery and acknowledgement only. The GitHub issue is the complete record: timeline, decisions, actions taken, people involved. Anyone joining the incident mid-way can read the GitHub issue and be fully caught up.

IR36No Speculation in Public Communication — Only Confirmed FactsHigh
BOTH STACKS

User-facing incident communication contains only confirmed facts. Never speculate about root cause, timeline for resolution, or impact scope until confirmed. "We believe the issue may be caused by X" is forbidden — wait until you know. Under-promise and over-deliver on resolution timelines — give a conservative estimate and beat it.

IR37Resolution Announcement — What Happened + What Was Fixed + PreventionHigh
BOTH STACKS

The resolution announcement for SEV0 and SEV1 incidents tells users three things in plain language: (1) what the problem was, (2) what was done to fix it, (3) what is being done to prevent recurrence. This is posted in the same GitHub issue and sent to users if they were notified during the incident. The announcement is written by the incident commander, not automated.

IR38No Blame in Post-Incident Communication — Blameless CultureHigh
BOTH STACKS

All incident communication — internal and external — is blameless. The goal is to understand what failed in the system, not who made a mistake. Post-mortems focus on process improvements and system hardening. Blame language in a post-mortem or incident communication is a violation of this rule and will be removed from the record.

  • Format GitHub Wiki page
  • Length Min 1 page
  • Actions Min 2 action items
  • Owner Incident commander
Post-Mortem Sections

PART 6 / IR39–IR44 Post-Mortem Process 4 Critical · 2 High · Both Stacks
IR39Post-Mortem Required — Every SEV0 and SEV1 Within 48 HoursCritical
BOTH STACKS

A post-mortem document is written for every SEV0 and SEV1 incident within 48 hours of resolution. There are no exceptions — not even for incidents resolved quickly. The post-mortem is published in the system-design-template GitHub Wiki under incident-reports/YYYY-MM-DD-title.md. It is linked from the GitHub incident issue. Writing a post-mortem for a fast recovery is especially valuable — it captures what went right.

IR40Root Cause Analysis — Five Whys Technique, Not Surface-LevelCritical
BOTH STACKS

Post-mortems use the Five Whys technique to identify root causes — not surface symptoms. "The deploy failed" is a symptom. "There was no staging verification step" is a root cause. The post-mortem does not stop asking "why" until it reaches a process or system factor that, if changed, would prevent recurrence. Surface-level post-mortems are sent back for revision.

IR41Action Items — Minimum Two, With Owner and Completion SprintCritical
BOTH STACKS

Every post-mortem produces a minimum of two concrete action items. Each action item has: (1) a clear description of what will be done, (2) an owner (named person), (3) a target sprint for completion. Action items are added as GitHub Issues tagged post-mortem-action. They are reviewed at the start of every sprint until closed. A post-mortem with no actionable improvements is incomplete.

IR42Constitutional Amendment Trigger — If Incident Reveals a Missing RuleCritical
BOTH STACKS

If a post-mortem reveals that an incident occurred because no rule governed the situation that caused it, a constitutional amendment is proposed as one of the action items. The incident is the evidence that a gap exists in the system. Every SEV0 post-mortem must explicitly answer the question: "Is there a constitutional rule that, if it had existed, would have prevented this incident?"

IR43Post-Mortem Review — Completed in Next Sprint Planning SessionHigh
BOTH STACKS

The post-mortem is reviewed in the next sprint planning session. The team reads the document together (or reviews it asynchronously before the session), confirms the action items, assigns sprint slots for each, and confirms the root cause analysis is complete. Post-mortems that are written and never reviewed are wasted effort.

IR44Recurring Incidents — Pattern Recognition Triggers Systemic ReviewHigh
BOTH STACKS

If the same root cause category appears in three or more post-mortems within a quarter, it triggers a systemic architectural review — not just another action item. Three incidents with the same root cause indicate a systemic problem that individual fixes cannot solve. The systemic review produces a constitutional amendment or architectural change addressing the pattern at its source.

§ Annex A — Forbidden Patterns (FP01–FP16)
⚠ FORBIDDEN PATTERNS — VIOLATION DURING AN ACTIVE INCIDENT = ESCALATION
FP01 — INVESTIGATING BEFORE RESTORING
Spending time on root cause analysis during an active SEV0 when a rollback is available and faster.
✓ Fix: Restore service first — rollback Vercel or Railway. Investigate after (IR4).
FP02 — NO INCIDENT DECLARATION
Investigating a production issue privately without opening a GitHub incident issue or notifying the commander.
✓ Fix: Open GitHub issue within 10 minutes of SEV0/1 detection (IR2).
FP03 — FINANCIAL OPS NOT FROZEN
Continuing to process deposits or withdrawals when a Reserve Bank financial data integrity issue is suspected. [Angular]
✓ Fix: Freeze DEPOSITS_ENABLED + WITHDRAWALS_ENABLED flags as first action (IR5).
FP04 — DEBUGGING IN PRODUCTION
Adding debug logging, test endpoints, or temporary code to production during an incident instead of rolling back.
✓ Fix: Rollback to last known good. Debug in staging (IR25, IR26).
FP05 — SILENT ALERT SYSTEM
Allowing monitoring alerts to go unacknowledged — Better Stack, Sentry, or Railway alerts with no response SLA.
✓ Fix: SEV0/1 alerts go to WhatsApp + email. Tested monthly (IR14).
FP06 — SPECULATION IN USER COMMS
Publishing "we think the issue might be X" in user-facing communication before root cause is confirmed.
✓ Fix: Only confirmed facts in user communication (IR36).
FP07 — BLAME IN POST-MORTEM
Naming individuals as the cause of an incident in the post-mortem document or incident communication.
✓ Fix: Blameless post-mortems — focus on process and system failures (IR38).
FP08 — POST-MORTEM SKIPPED
Resolving a SEV0 or SEV1 without writing a post-mortem — even if the fix was fast and simple.
✓ Fix: Post-mortem required for all SEV0 and SEV1 within 48 hours (IR39).
FP09 — SURFACE-LEVEL ROOT CAUSE
Post-mortem root cause is "the deploy failed" or "there was a bug" — not the underlying process gap.
✓ Fix: Five Whys technique — keep asking why until process gap is found (IR40).
FP10 — ACTION ITEMS WITHOUT OWNERS
Post-mortem action items listed without a named owner and target sprint — they will never be completed.
✓ Fix: Every action item has an owner and sprint target (IR41).
FP11 — MODIFYING MIGRATION TO FIX INCIDENT
Editing a deployed migration file to fix a database incident instead of creating a corrective migration.
✓ Fix: Always a new corrective migration — never edit deployed files (IR28, D53).
FP12 — INCIDENT IN WHATSAPP ONLY
Managing an incident entirely through WhatsApp messages with no GitHub issue as the canonical record.
✓ Fix: GitHub issue is the single thread — WhatsApp for alerts only (IR35).
FP13 — UNTESTED ROLLBACK PROCEDURES
Discovering during a SEV0 that the rollback procedure has never been tested in staging.
✓ Fix: Monthly rollback drills in staging — documented results (IR32).
FP14 — NO FEATURE FLAG KILL SWITCH
Shipping a major feature without a feature flag — no way to disable it without a full deploy during an incident.
✓ Fix: All major features behind feature flags (IR29, B42).

Declaring an incident resolved before the 15-minute stability window has passed — incident reopens shortly after.
