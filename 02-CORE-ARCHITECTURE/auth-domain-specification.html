PART 0 / A1–A4 Auth Strategy Selection 4 Critical · Foundation for All Auth Rules
A1One Auth Strategy Per Stack — Never Mix NextAuth and JWT on the Same SystemCritical
BOTH STACKS

Next.js systems (Maphophe, SyncUp) use NextAuth.js exclusively. Angular systems (FundsLink, Reserve Bank) use JWT via FastAPI exclusively. Never implement JWT on a Next.js system or NextAuth on an Angular system. Mixing auth strategies on one platform is forbidden — it creates two session verification paths and doubles the attack surface.

!
v3.0 change: v2.0 only specified NextAuth rules. v3.0 adds Part 2 (Rules A13–A20) covering the JWT strategy for Angular systems. Both strategies are now fully governed. The separation is absolute — no crossover.
A2All Auth Data in PostgreSQL — Never MongoDB, Never Redis Primary StoreCritical
BOTH STACKS

All authentication data — user records, password hashes, sessions, refresh tokens, reset tokens, email verification codes — lives in PostgreSQL. MongoDB is never used for auth data. Redis may cache token validation results for performance but is never the primary store — PostgreSQL is authoritative.

A3Password Hashing — bcrypt Minimum Cost Factor 12Critical
BOTH STACKS

All passwords are hashed using bcrypt with a minimum cost factor of 12. Never use MD5, SHA-1, SHA-256, or any non-adaptive hashing algorithm for passwords. Never store plain text or reversibly encrypted passwords. The cost factor is a configuration value — never hardcoded in application code.

Next.js Stack
bcryptjs with saltRounds = parseInt(process.env.BCRYPT_ROUNDS). NextAuth handles hashing for credential provider automatically.
Angular Stack
passlib with bcrypt scheme in FastAPI. CryptContext(schemes=["bcrypt"], bcrypt__rounds=int(settings.BCRYPT_ROUNDS)).
A4Auth Endpoints — Rate Limited, Brute-Force ProtectedCritical
BOTH STACKS

All authentication endpoints (login, register, password reset, token refresh) are rate limited to 10 attempts per IP per 15 minutes. After 5 consecutive failed login attempts for the same email, lock the account for 15 minutes and send a security notification email. Rate limit counters are stored in Redis with TTL — not in PostgreSQL.

Rate limit
10 attempts / IP / 15 min
Account lock
5 failed attempts → 15 min lockout
Counter store
Redis with TTL (not PostgreSQL)
On lock
Security email + AuditLog entry

PART 1 / A5–A12 NextAuth.js Strategy Maphophe · SyncUp · Next.js Stack Only
A5NextAuth with Prisma Adapter — Database Sessions OnlyCritical
NEXT.JS STACK ONLY

NextAuth.js is configured with the Prisma Adapter and session: { strategy: "database" }. Never use JWT session strategy on Next.js systems — this would bypass database session invalidation. The Prisma Adapter manages the User, Session, Account, and VerificationToken tables automatically.

auth.ts — NextAuth configuration
export const { handlers, auth, signIn, signOut } = NextAuth({
  adapter: PrismaAdapter(prisma),
  session: { strategy: "database" },      // never "jwt" on NJ stack
  pages: { signIn: "/login" },
  callbacks: {
    async session({ session, user }) {
      session.user.id   = user.id;         // add id to session
      session.user.role = user.role;       // add role to session
      return session;
    }
  }
});
A6HTTP-Only Cookies — Never localStorage for Session TokensCritical
NEXT.JS STACK ONLY

NextAuth session cookies must be set as HTTP-only, Secure (production), and SameSite=Lax. Never store session tokens in localStorage or sessionStorage — these are accessible to JavaScript and vulnerable to XSS. NextAuth handles cookie configuration automatically when session.strategy: "database" is set.

A7Route Protection — Middleware Checks Session on Every Protected RouteCritical
NEXT.JS STACK ONLY

A Next.js middleware function runs on every request to protected routes and calls auth() to verify the session. Unauthenticated requests redirect to /login with a callbackUrl query parameter. Never rely solely on client-side route guards — the middleware is the authoritative check.

middleware.ts
export { auth as middleware } from "@/auth";

export const config = {
  matcher: ["/((?!api|_next/static|_next/image|favicon.ico|login|register).*))"]
};
A8Session Callback — Expose Only id, email, role, nameCritical
NEXT.JS STACK ONLY

The NextAuth session callback must explicitly set which user fields appear in the session object. Only expose: id, email, role, name. Never include password_hash, reset_token, created_at, or internal fields. The session object is accessible client-side — treat it as a public document.

A9Session Lifetime — 30 Days from Environment VariableHigh
NEXT.JS STACK ONLY

Session max age is configured via SESSION_MAX_AGE_SECONDS environment variable, defaulting to 2592000 (30 days). Never hardcode session lifetime in code. Expired sessions are cleaned up by a daily cron job that deletes rows from the Session table where expires < NOW().

A10OAuth Providers — Through NextAuth Only, Never Custom ImplementationHigh
NEXT.JS STACK ONLY

If OAuth login (Google, GitHub, etc.) is needed on a Next.js system, it is implemented exclusively through NextAuth provider configuration. Never build a custom OAuth flow. NextAuth handles PKCE, state parameters, token exchange, and account linking — do not replicate this logic.

A11CSRF Protection — NextAuth Built-In, Never DisabledCritical
NEXT.JS STACK ONLY

NextAuth provides built-in CSRF protection for all auth form actions via a double-submit CSRF token. Never disable or bypass this protection. Never expose the NextAuth secret in client-side code. The NEXTAUTH_SECRET environment variable must be a cryptographically random string of minimum 32 bytes.

A12Email Verification — Required Before Account ActivationHigh
NEXT.JS STACK ONLY

New accounts created with email/password credentials are inactive until email verification is completed. A verification token is generated, stored in the VerificationToken table, and emailed to the user. Tokens expire after 24 hours. Unverified accounts cannot access protected routes.

PART 2 / A13–A20 · NEW JWT Auth Strategy FundsLink Academy · Reserve Bank · Angular Stack Only
+
New in v3.0: Part 2 (Rules A13–A20) is entirely new. The Angular stack uses JWT authentication issued by FastAPI. All 8 rules here are additions to the system. Rules A5–A12 (NextAuth) do not apply to Angular systems. Rules A13–A20 do not apply to Next.js systems.
A13FastAPI Issues JWT on Successful Login — RS256 SignedNew · Critical
ANGULAR STACK ONLY

On successful login, FastAPI issues two tokens: an access token (15-minute lifetime) and a refresh token (7-day lifetime). Both are signed using RS256 (RSA asymmetric signing) with the private key stored in Railway Secrets. The public key is used for verification — never expose the private key. The payload contains: sub (user cuid), role, email, iat, exp, jti (unique token ID).

auth/jwt.py — token creation
def create_tokens(user: User) -> TokenPair:
    now = datetime.utcnow()
    access_payload = {
        "sub":   user.id,           # PostgreSQL cuid
        "role":  user.role.value,
        "email": user.email,
        "iat":   now,
        "exp":   now + timedelta(minutes=15),
        "jti":   str(uuid4()),      # unique id for revocation
    }
    access_token  = jwt.encode(access_payload, settings.JWT_PRIVATE_KEY, "RS256")
    refresh_token = create_refresh_token(user.id)  # 7-day, stored in DB
    return TokenPair(access_token=access_token, refresh_token=refresh_token)
A14Refresh Token in HttpOnly Cookie — Access Token in Response BodyNew · Critical
ANGULAR STACK ONLY

The refresh token is set as an HttpOnly, Secure, SameSite=Strict cookie — never in the response body or localStorage. The access token is returned in the response body only and stored in Angular memory (a service variable) — never in localStorage or sessionStorage. This separates the long-lived token (cookie, XSS-proof) from the short-lived one (memory, CSRF-proof).

❌ Both tokens in localStorage
localStorage.setItem('access', token)
localStorage.setItem('refresh', refresh)
// XSS attack steals both tokens
✅ Correct split storage
// FastAPI sets HttpOnly cookie:
response.set_cookie("refresh_token", ..., httponly=True)
// Angular stores access in memory only:
this.accessToken = response.access_token;
A15Angular HTTP Interceptor — Attaches Bearer Token to Every RequestNew · Critical
ANGULAR STACK ONLY

A single Angular HTTP Interceptor attaches the Authorization: Bearer <access_token> header to all outgoing FastAPI requests. The interceptor also handles 401 responses by triggering silent token refresh (using the HttpOnly cookie). After a successful refresh, it retries the original request. This is the only place in the Angular codebase where auth headers are set.

Silent Token Refresh Flow
1
Request sent with expired access token
Interceptor attaches stale Bearer token → FastAPI returns 401
2
Interceptor catches 401
Calls POST /auth/refresh — HttpOnly cookie auto-attached by browser
3
FastAPI validates refresh token
Issues new access token + rotates refresh token → old refresh token revoked
4
Interceptor stores new access token
Retries original request with new Bearer token → returns response to component
5
Refresh also fails (refresh token expired)
Interceptor calls AuthService.logout() → redirects to /login
A16Refresh Token Rotation — New Pair on Every Refresh, Old Token RevokedNew · Critical
ANGULAR STACK ONLY

On every token refresh, FastAPI issues a new access token AND a new refresh token, and immediately revokes the old refresh token by deleting its record from the RefreshToken PostgreSQL table. If the same refresh token is used twice (replay attack), both tokens are revoked and the user is logged out. This detects token theft.

Table
RefreshToken — id, user_id, token_hash, expires_at, revoked_at
On replay detected
Revoke ALL active refresh tokens for user → force re-login
A17FastAPI JWT Validation — Depends() on Every Protected EndpointNew · Critical
ANGULAR STACK ONLY

Every protected FastAPI endpoint uses Depends(get_current_user) as a dependency. The get_current_user dependency decodes and validates the JWT, checks the user exists in PostgreSQL, and verifies the account is active (not soft-deleted). Never manually decode JWTs inside endpoint handlers.

auth/dependencies.py
async def get_current_user(
    token: str = Depends(oauth2_scheme),
    db: AsyncSession = Depends(get_db)
) -> User:
    payload = jwt.decode(token, settings.JWT_PUBLIC_KEY, ["RS256"])
    user_id: str = payload.get("sub")
    user = await db.get(User, user_id)
    if not user or user.deleted_at:
        raise HTTPException(status_code=401, detail="AUTH_UNAUTHORIZED")
    return user

# Usage on every protected endpoint:
async def get_account(current_user: User = Depends(get_current_user)):
    ...
A18Logout — Revoke Refresh Token and Clear CookieNew · Critical
ANGULAR STACK ONLY

On logout, FastAPI: (1) reads the refresh token from the HttpOnly cookie, (2) marks it as revoked in the RefreshToken table, (3) clears the cookie by setting it to an expired date. Angular: clears the in-memory access token. The jti claim of the access token is added to a short-lived Redis deny-list for the remaining 15 minutes of its lifetime.

A19Angular Route Guards — AuthGuard Checks Token Validity Before Route ActivationNew · Critical
ANGULAR STACK ONLY

All protected Angular routes use canActivate: [AuthGuard]. The AuthGuard checks: (1) access token is present in memory, (2) token is not expired (check exp claim client-side). If the token is expired, it attempts a silent refresh before deciding. On failure, it redirects to /login with ?returnUrl= query param. This is the client-side gate — FastAPI is the authoritative gate.

A20JWT Secrets in Railway Secrets — Never in Code or .env FilesNew · Critical
ANGULAR STACK ONLY

The RS256 private key (JWT_PRIVATE_KEY), public key (JWT_PUBLIC_KEY), and bcrypt rounds (BCRYPT_ROUNDS) are stored exclusively in Railway Secrets. Never commit these values to any file in any repository. The .env.example file lists the required variable names with placeholder comments — never actual values.

A22Ownership Checks — Users Can Only Access Their Own ResourcesCritical
BOTH STACKS

For all resource endpoints that return or modify user-owned data, the service layer must verify that the authenticated user's id matches the resource's user_id or owner_id. Role alone is not sufficient — ownership must be verified even for users with elevated roles (except ADMIN). Never rely on the frontend to enforce ownership.

❌ No ownership check
# Returns any account by id
async def get_account(account_id: str):
    return await Account.get(account_id)
✅ Ownership enforced
async def get_account(account_id: str,
    user = Depends(get_current_user)):
  account = await Account.get(account_id)
  if account.user_id != user.id:
    raise forbidden()
A23RBAC Middleware Applied at Route Level — Not Inside Business LogicCritical
BOTH STACKS

Role checks happen at the route/handler entry point, not inside service layer functions. The route handler's Depends() (FastAPI) or middleware (Next.js) is the enforcement layer. Business logic functions assume the caller is already authorised. This prevents auth bypass when the same business logic is called from different entry points.

Next.js Stack
Check session.user.role at the top of the API route handler before any business logic. Middleware enforces authentication; handler enforces authorisation.
Angular Stack
Depends(require_role(Role.ADMIN)) on the route decorator. A separate require_role dependency factory wraps get_current_user with role checks.
A24Least Privilege Default — New Users Start with Minimum RoleCritical
BOTH STACKS

All new user accounts default to the minimum role for the platform: USER on Next.js systems, STUDENT on FundsLink, ACCOUNT on Reserve Bank. Role elevation requires an explicit admin action. The role field in the Prisma schema uses @default(USER) — never @default(ADMIN).

A25Role Changes Logged — AuditLog Entry on Every Role ModificationHigh
BOTH STACKS

Every role change (escalation, de-escalation, admin assignment) creates an AuditLog entry containing: target user id, old role, new role, actor admin id, IP address, and timestamp. Role changes without an audit log entry are a policy violation. The audit log is append-only — never update or delete role change entries.

PART 4 / A26–A30 Security Baseline 4 Critical · 1 High · Both Stacks
A26HTTPS Only — All Auth Traffic, No HTTP Fallback in ProductionCritical
BOTH STACKS

All authentication traffic in production goes over HTTPS only. HTTP requests to auth endpoints are rejected with a 301 redirect to HTTPS. The Strict-Transport-Security header is set with max-age=31536000; includeSubDomains. Vercel and Railway both enforce HTTPS — never disable this in configuration.

A27CORS — Locked to Known Origins, No Wildcard in ProductionCritical
BOTH STACKS

CORS allowed origins are a specific list of known domains from environment variables — never * in production. FastAPI (Angular stack) reads CORS_ORIGINS env var as a comma-separated list. Next.js uses next.config.js headers. Preflight requests to unlisted origins receive a 403.

Next.js Stack
CORS configured in next.config.js headers. Access-Control-Allow-Origin: https://maphophe.co.za — exact domain only.
Angular Stack
FastAPI CORSMiddleware(allow_origins=settings.CORS_ORIGINS.split(",")). Production list: Angular Vercel domain only.
A28Password Reset — Time-Limited Token, One-Time UseCritical
BOTH STACKS

Password reset tokens are: (1) cryptographically random 32-byte strings, (2) hashed before storage (never stored in plain text), (3) valid for 1 hour only, (4) invalidated immediately on use. The reset endpoint does not confirm whether an email exists (prevents user enumeration). Always respond with "if this email exists, a reset link was sent."

A29Security Headers — Set on All ResponsesCritical
BOTH STACKS

All HTTP responses must include security headers: X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: same-origin, Content-Security-Policy (appropriate for the platform), Strict-Transport-Security. Configured in Vercel headers config (Next.js) and FastAPI middleware (Angular).

A30Password Strength Validation — Minimum Requirements Enforced Both SidesHigh
BOTH STACKS

Passwords must meet: minimum 8 characters, at least one uppercase letter, one number, one special character. Common passwords (top 10,000 list) are rejected. These checks run on both the frontend (immediate UX feedback) and the backend (authoritative enforcement). The password policy is configured via environment variable — not hardcoded.

§ Part 5 — Audit & Governance (A31–A34)

  • ✓ Email verification
  • ✓ Role change

PART 5 / A31–A34 Audit & Governance 4 Critical · Both Stacks
A31All Auth Events Logged to AuditLog — Append-OnlyCritical
BOTH STACKS

Every authentication event is written to the AuditLog PostgreSQL table immediately. The log captures: event type, user id (if known), IP address, user agent, timestamp, and outcome (success/failure). AuditLog rows are never updated or deleted — only inserted. The AuditLog table has no deleted_at column.

A32Security Incident Alert — Brute Force and Token Replay Trigger Immediate AlertCritical
BOTH STACKS

Two events trigger immediate security alerts to the platform admin: (1) more than 10 failed login attempts from a single IP in 5 minutes (brute force indicator), (2) a refresh token replay detected (token theft indicator). Alerts are sent via email and logged in Sentry. The affected account is temporarily locked pending review.

A33Session Invalidation on Password Change — All Existing Sessions RevokedCritical
BOTH STACKS

When a user changes their password, all existing sessions and refresh tokens for that user are immediately revoked. The user must log in again on all devices. This prevents an attacker who has stolen a session from remaining authenticated after the user secures their account.

Next.js Stack
Delete all rows from Session table where userId = id after password update. NextAuth sessions are invalidated automatically.
Angular Stack
Set revoked_at = now() on all RefreshToken rows for the user. Add all active jti values to Redis deny-list for remaining access token lifetimes.
A34Cross-Constitution Governance — Auth Changes Require Backend + Frontend ReviewCritical
ALL 10 CONSTITUTIONS

Any change to auth strategy, token lifetimes, RBAC roles, cookie configuration, or session management requires a PR label of both Backend-Review-Required: Yes and Frontend-Review-Required: Yes. Auth changes touch every layer of the system — changes without cross-constitution review are rejected in CI. Auth strategy changes additionally require a documented security review before merging.

§ Annex A — Forbidden Patterns (FP01–FP18)
⚠ FORBIDDEN PATTERNS — VIOLATION = SECURITY INCIDENT · BOTH STACKS UNLESS MARKED
FP01 — JWT ON NEXT.JS STACK
Implementing JWT authentication on Maphophe or SyncUp instead of NextAuth.js.
✓ Fix: NextAuth.js with database sessions (A1, A5).
FP02 — NEXTAUTH ON ANGULAR STACK
Using NextAuth.js on FundsLink or Reserve Bank instead of FastAPI JWT.
✓ Fix: FastAPI JWT with RS256 signing (A1, A13).
FP03 — REFRESH TOKEN IN LOCALSTORAGE
Storing the JWT refresh token in localStorage or sessionStorage — XSS-accessible. [Angular]
✓ Fix: Refresh token in HttpOnly cookie only (A14).
FP04 — ACCESS TOKEN IN HTTPONLY COOKIE
Storing the short-lived JWT access token in an HttpOnly cookie — blocks JavaScript access for refresh. [Angular]
✓ Fix: Access token in Angular memory service (A14).
FP05 — SESSION STRATEGY: JWT IN NEXTAUTH
Setting NextAuth session: { strategy: "jwt" } — bypasses database session invalidation. [Next.js]
✓ Fix: Always use strategy: "database" (A5).
FP06 — NO TOKEN ROTATION ON REFRESH
Issuing the same refresh token repeatedly instead of rotating to a new pair. [Angular]
✓ Fix: Issue new access + refresh on every refresh call (A16).
FP07 — PLAIN TEXT OR SHA PASSWORD STORAGE
Storing passwords in plain text, base64, MD5, SHA-1, or SHA-256 — all non-adaptive algorithms.
✓ Fix: bcrypt with minimum cost factor 12 (A3).
FP08 — NO RATE LIMIT ON AUTH ENDPOINTS
Login, register, and password reset endpoints without rate limiting — enables brute force.
✓ Fix: 10 attempts / IP / 15 min with Redis counter (A4).
FP09 — AUTH DATA IN MONGODB
Storing user credentials, sessions, or refresh tokens in MongoDB instead of PostgreSQL.
✓ Fix: All auth data in PostgreSQL exclusively (A2).
FP10 — ROLE HARDCODED AS STRING
Comparing roles using string literals: if role == "admin" instead of Prisma enum.
✓ Fix: Always reference Role enum constants (A21).
FP11 — NO OWNERSHIP CHECK ON RESOURCES
Returning or modifying any user-owned resource without verifying the requester is the owner.
✓ Fix: Check user.id === resource.user_id in service layer (A22).
FP12 — CORS WILDCARD IN PRODUCTION
Setting Access-Control-Allow-Origin: * on any production endpoint.
✓ Fix: Explicit origin allowlist from env var (A27).
FP13 — PASSWORD RESET TOKEN IN PLAIN TEXT
Storing password reset tokens as plain text strings in the database — exposes them to DB reads.
✓ Fix: Hash reset tokens before storage, send raw to email (A28).
FP14 — USER ENUMERATION ON RESET ENDPOINT
Password reset endpoint returning different responses for known vs unknown email addresses.
✓ Fix: Always respond "if email exists, link was sent" (A28).
FP15 — SESSIONS NOT REVOKED ON PASSWORD CHANGE
Allowing existing sessions to remain valid after a password change event.
✓ Fix: Revoke all sessions / refresh tokens on password change (A33).
FP16 — JWT PRIVATE KEY IN CODE OR .ENV
Committing JWT signing keys to any file in the repository — even .env.example with actual values. [Angular]
✓ Fix: JWT keys in Railway Secrets exclusively (A20).
FP17 — SENSITIVE CLAIMS IN JWT PAYLOAD
Including password_hash, PII, or internal notes in the JWT claims — payload is base64-decodable. [Angular]
✓ Fix: Only sub, role, email, iat, exp, jti in JWT (A13).
FP18 — AUTH CHANGE WITHOUT CROSS-CONST REVIEW
Merging any change to auth strategy, token lifetimes, or RBAC without dual PR review labels.
✓ Fix: Backend-Review-Required + Frontend-Review-Required labels (A34).
