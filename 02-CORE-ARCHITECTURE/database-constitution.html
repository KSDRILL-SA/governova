PART 1 / D1–D8 Database Strategy & Assignment 5 Critical · 3 High · Both Stacks
D1Three-Database Separation — One Purpose Per Database TypeCritical
BOTH STACKS

Three distinct database types serve three distinct purposes. PostgreSQL for structured relational data with ACID guarantees. MongoDB for flexible document data without rigid schemas (Angular stack only). ChromaDB for vector embeddings and semantic similarity (FundsLink only). Data that belongs to one type must never be stored in another.

!
Hardest violation to fix: Once financial data gets into MongoDB or embeddings get into PostgreSQL, untangling it in production is expensive and risky. Enforce at schema design time — never at migration time.
D2PostgreSQL Is the System of Record — All Entities Originate HereCritical
BOTH STACKS

Every core entity (user, student, funder, resident, account holder, creator) is first created and owned by PostgreSQL. MongoDB documents and ChromaDB embeddings may reference these entities but are subordinate. If PostgreSQL and MongoDB ever conflict on the same entity, PostgreSQL wins.

D3Financial Data in PostgreSQL Only — Never MongoDBCritical
BOTH STACKS

All financial data — account balances, transaction amounts, deposit schedules, interest rates, lock periods — must live exclusively in PostgreSQL. MongoDB's eventual consistency and lack of native ACID multi-document transactions make it structurally unsuitable for financial records. This rule is absolute with no exceptions.

❌ Never — Financial in MongoDB
deposits_collection {
  amount: 5000,        // financial
  balance: 12500,      // financial
  interest_rate: 0.05  // financial
}
✅ Correct — Financial in PostgreSQL
deposits table (Prisma) {
  id, amount, balance,
  interest_rate,
  created_at, deleted_at
}
D4Authentication Data in PostgreSQL OnlyCritical
BOTH STACKS

All authentication and identity data — user credentials, password hashes, JWT refresh tokens, reset tokens, email verification tokens, sessions — must live in PostgreSQL. Authentication requires ACID consistency to prevent race conditions in token validation and session management.

D5Cross-Database References Use PostgreSQL cuid — Not ObjectIDsCritical
ANGULAR STACK ONLY

When a MongoDB document or ChromaDB embedding references a user or entity that exists in PostgreSQL, the reference field stores the PostgreSQL cuid string. Never use a MongoDB ObjectID as a cross-database foreign reference. This keeps PostgreSQL as the unambiguous system of record and simplifies join queries at the application layer.

MongoDB reference field
student_id: str stores PostgreSQL cuid e.g. clx7...
ChromaDB metadata
{"user_id": "clx7..."} in document metadata
D6Database Selection Decision Must Be Documented at Design TimeHigh
BOTH STACKS

Every new data entity must have its database destination documented in the system design before schema work begins. The design doc must answer: relational joins needed? ACID required? Schema fixed or dynamic? AI-generated content? The answer determines the database. No ad-hoc database decisions at implementation time.

D7No Direct Database Access from Frontend — Always Through BackendHigh
BOTH STACKS

The browser never connects directly to PostgreSQL, MongoDB, or ChromaDB. All database access goes through the backend service layer — Next.js API routes (Next.js stack) or FastAPI (Angular stack). No client-side Prisma, no client-side MongoDB driver, no direct ChromaDB HTTP calls from Angular.

D8Soft Delete on All Databases — Never Hard Delete in ProductionHigh
BOTH STACKS

No production record is ever permanently deleted. PostgreSQL uses deleted_at DateTime? via Prisma. MongoDB uses deletedAt: Date via Beanie. ChromaDB documents are archived, not deleted. All queries default-filter records where deleted_at IS NULL. Hard deletes require a documented admin process and are never triggered by user actions.

PART 2 / D9–D24 PostgreSQL & Prisma 10 Critical · 6 High · Both Stacks
D9Prisma Schema Is the Single Source of Truth — All Changes Through MigrationsCritical
BOTH STACKS

The Prisma schema file is the authoritative definition of all PostgreSQL tables. All schema changes go through prisma migrate dev (development) or prisma migrate deploy (production). No manual SQL DDL changes. No ad-hoc ALTER TABLE. Raw SQL is allowed only for complex aggregates or recursive CTEs, with a comment explaining why Prisma is insufficient.

D10Required Fields on Every Table — id, created_at, updated_at, deleted_atCritical
BOTH STACKS

Every Prisma model must define four base fields: id String @id @default(cuid()), created_at DateTime @default(now()), updated_at DateTime @updatedAt, deleted_at DateTime?. A Prisma schema linter in CI fails the build if any model is missing these fields.

schema.prisma — base model pattern
model User {
  id         String    @id @default(cuid())
  created_at DateTime  @default(now())
  updated_at DateTime  @updatedAt
  deleted_at DateTime?              // soft delete

  // domain fields below
  email      String    @unique
  role       Role      @default(USER)
}
D11No SELECT * — Explicit select on Every Prisma QueryCritical
BOTH STACKS

Every prisma.model.findMany(), findFirst(), and findUnique() must include an explicit select object listing only the fields required. Never call these methods without a select clause. This prevents accidental exposure of sensitive fields and reduces payload size.

❌ Exposes password_hash, tokens
prisma.user.findMany()
// returns ALL columns including secrets
✅ Only safe fields returned
prisma.user.findMany({
  select: { id: true, email: true,
            name: true, role: true },
  where: { deleted_at: null }
})
D12All Queries Filter deleted_at: null by DefaultCritical
BOTH STACKS

Every query on a soft-deletable model must include where: { deleted_at: null } unless explicitly fetching deleted records for admin purposes. Implement a Prisma middleware that automatically appends this filter to all queries, preventing accidental inclusion of soft-deleted records.

D13Foreign Key Indexes — Every FK Field Has an IndexCritical
BOTH STACKS

Every foreign key field in the Prisma schema must have an explicit @@index or @index annotation. Unindexed foreign keys cause full table scans on join queries. The Prisma schema linter in CI checks that all FK fields have indexes defined.

D14Pagination on All List Queries — No Unbounded ResultsCritical
BOTH STACKS

Every query that returns a list of records must include take and skip (or cursor-based pagination). Default page size is 20 records. Maximum page size is 100 records. Never return an unbounded result set regardless of how few records currently exist — the data will grow.

D15Transactions for Multi-Step Writes — prisma.$transaction()Critical
BOTH STACKS

Any operation that writes to multiple tables must use prisma.$transaction([]). Never issue sequential writes without a transaction wrapper when partial failure would leave the database in an inconsistent state. This is especially critical for Reserve Bank deposit operations, FundsLink application submissions, and SyncUp pitch-to-subscription flows.

reserve-bank: deposit + balance update
// Both writes succeed or both roll back
await prisma.$transaction([
  prisma.deposit.create({ data: depositData }),
  prisma.account.update({
    where: { id: accountId },
    data: { balance: { increment: amount } }
  })
]);
D16Never Expose Sensitive Fields — Explicit Exclusion ListCritical
BOTH STACKS

The following fields must never appear in any API response: password_hash, reset_token, refresh_token, two_factor_secret, deleted_at, internal_notes. The explicit select rule (D11) is the enforcement mechanism — never select these fields.

D17Audit Log on Every State ChangeHigh
BOTH STACKS

Every write operation that changes state (create, update, soft delete) must be accompanied by an audit log entry in the AuditLog table. The log captures: entity type, entity id, action, actor id, IP address, and timestamp. Implemented as a Prisma middleware or FastAPI service layer decorator.

D18Connection Pooling — PgBouncer or Prisma Accelerate in ProductionHigh
BOTH STACKS

Production PostgreSQL connections must go through a connection pooler. Next.js stack on Vercel uses Prisma Accelerate or a PgBouncer-enabled connection string. Angular stack on Railway uses Railway's built-in connection pooling. Direct unbuffered connections in serverless/edge environments exhaust the PostgreSQL connection limit under load.

Next.js Stack (Vercel)
Use Prisma Accelerate or PgBouncer URL. Set connection_limit=1 in Prisma datasource for serverless environments.
Angular Stack (Railway)
Railway managed Postgres includes PgBouncer. Use the Railway pooled connection URL in FastAPI DATABASE_URL env variable.
D19Migration Rollback Plan — Every Migration Has a Down MigrationHigh
BOTH STACKS

Every production migration must have a documented rollback strategy before it is deployed. For additive migrations (add column, add table), document the ALTER TABLE DROP COLUMN or DROP TABLE equivalent. For data migrations, document the reverse transform. The rollback plan is reviewed and approved in the same PR as the migration.

D20Zero-Downtime Migrations — Additive First, Remove LaterCritical
BOTH STACKS

Schema changes that could cause downtime must be performed in phases. Phase 1: add the new column/table as optional (deploy, verify). Phase 2: backfill data. Phase 3: make required and remove the old column in a follow-up deploy. Never rename or drop a column in the same migration that adds the replacement.

D21No Raw SQL for Standard CRUD — Prisma ORM OnlyHigh
BOTH STACKS

Standard create, read, update, and soft delete operations must use Prisma ORM methods. prisma.$queryRaw and prisma.$executeRaw are permitted only for: complex aggregates, recursive CTEs, or queries that Prisma cannot express. Every raw SQL usage requires a comment: // RAW SQL: [reason Prisma is insufficient].

D22Enum Types in Prisma — Never Free-Text Status FieldsCritical
BOTH STACKS

Status, type, and role fields with a fixed set of values must be defined as Prisma enum types, never as free-text string fields. This enforces valid values at the schema level and generates TypeScript enums for type safety throughout the codebase.

❌ Free-text status — no safety
status String  // "pending"? "PENDING"? "Pending"?
✅ Enum — enforced at schema level
enum ApplicationStatus {
  PENDING APPROVED REJECTED WITHDRAWN
}
status ApplicationStatus @default(PENDING)
D23Database Backups — Automated Daily, Verified WeeklyHigh
BOTH STACKS

Production PostgreSQL databases must have automated daily backups configured. Railway managed Postgres includes automated backups — verify the retention period is set to minimum 7 days. Perform a test restore from backup weekly in the staging environment to confirm backup integrity.

D24Seed Data — Separate from Migrations, IdempotentCritical
BOTH STACKS

Seed data (test users, default roles, sample records) lives in prisma/seed.ts — never in migrations. Seed scripts must be idempotent: running them multiple times produces the same result without errors or duplicates. Production seeds contain only system defaults — never test data.

PART 3 / D25–D38 · NEW MongoDB & Beanie ODM Angular Stack Only — FundsLink · Reserve Bank
+
New in v3.0: Part 3 is entirely new. MongoDB + Beanie is the document database for the Angular stack. All 14 rules in this section are new. Rules D25–D38 are additive to the overall system — they do not replace or override any PostgreSQL rules. Both databases operate simultaneously on Angular systems.
D25Beanie ODM for All MongoDB Access — No Raw Motor or PyMongoNew · Critical
ANGULAR STACK ONLY

All MongoDB access must go through Beanie ODM (Pydantic-based async ODM for Motor). Never use the raw Motor async driver or PyMongo synchronous driver directly in production code. Beanie provides schema validation, type safety, and consistent query patterns that match the rest of the FastAPI/Pydantic ecosystem.

models/scholarship_match.py — Beanie document model
from beanie import Document, Indexed
from pydantic import Field
from datetime import datetime
from typing import Optional, List

class ScholarshipMatch(Document):
    student_id: Indexed(str)             # PostgreSQL cuid ref (D5)
    match_score: float
    matched_scholarships: List[str]      # scholarship ids
    ai_reasoning: str                    # AI-generated content
    created_at: datetime = Field(default_factory=datetime.utcnow)
    updated_at: datetime = Field(default_factory=datetime.utcnow)
    deleted_at: Optional[datetime] = None  # D35: soft delete

    class Settings:
        name = "scholarship_matches"
        use_state_management = True
D26Every Document Schema Defined Before Collection UseNew · Critical
ANGULAR STACK ONLY

A Beanie document class must be defined and registered at FastAPI startup before any document is written to a collection. Never write to a MongoDB collection without a corresponding Beanie schema. Collections without schemas are read-only legacy data — new writes always require a schema.

D27Required Fields on Every Document — created_at, updated_at, deleted_atNew · Critical
ANGULAR STACK ONLY

Every Beanie document model must include: created_at: datetime (auto-set), updated_at: datetime (auto-updated), deleted_at: Optional[datetime] = None. These mirror the PostgreSQL required fields (D10) and ensure consistent temporal tracking across both databases.

D28Cross-Database Reference Field Naming ConventionNew · High
ANGULAR STACK ONLY

Fields in MongoDB documents that reference PostgreSQL entities follow the naming convention {entity}_id: str — e.g., student_id, account_id, funder_id. The value stored is always the PostgreSQL cuid string. Type annotation is Indexed(str) (Beanie indexed field) to enable efficient lookups.

D29Explicit Indexes on All Query FieldsNew · Critical
ANGULAR STACK ONLY

Every MongoDB field used in a query predicate must have an explicit index defined in the Beanie schema using Indexed(type) or @@index. Collection scans are forbidden in production. CI includes a query plan analyser that fails on COLLSCAN in the slow query log.

Single field index
student_id: Indexed(str)
Compound index
@pymongo.operations.IndexModel([("student_id", 1), ("match_score", -1)])
D30Pagination on All MongoDB List Queries — No Unbounded FindsNew · High
ANGULAR STACK ONLY

Every MongoDB query returning a list must use .limit(n).skip(offset) or Beanie's built-in pagination. Default limit is 20. Maximum limit is 100. Never call Document.find_all() without a limit in production queries. Unbounded queries are forbidden.

D31AI-Generated Content Validation — Pydantic Before StorageNew · Critical
ANGULAR STACK ONLY

All AI-generated content (LangChain outputs, scholarship reasoning, eligibility explanations) must be validated through a Pydantic model before being stored in MongoDB. Never store raw LangChain output strings directly. Define a structured output schema for each AI task and validate the response before persistence.

❌ Raw LangChain string stored
await ScholarshipMatch.insert({
  ai_reasoning: langchain_response  # unvalidated
})
✅ Validated through Pydantic first
validated = AIReasoningSchema.parse(
  langchain_response
)
await ScholarshipMatch.insert(validated)
D32MongoDB Connection Pooling — Motor Async Client at StartupNew · High
ANGULAR STACK ONLY

The MongoDB Motor async client initialises once at FastAPI startup and is reused across all requests. Never create a new Motor client per request. Configure the connection pool with a minimum of 5 and maximum of 20 connections. Store the client in FastAPI application state.

D33No Multi-Document Transactions for Financial Data — Use PostgreSQLNew · Critical
ANGULAR STACK ONLY

MongoDB 4.x supports multi-document ACID transactions, but they are to be avoided for financial data. If an operation requires multi-document atomicity on financial data, that data belongs in PostgreSQL. MongoDB transactions are permitted only for coordinating writes to multiple document collections of non-financial, non-critical data.

D34Collection Naming — snake_case Plural NounsNew · Medium
ANGULAR STACK ONLY

MongoDB collection names use snake_case plural nouns defined in the Beanie Settings.name. Examples: scholarship_matches, application_logs, ai_reasoning_cache. Never use camelCase, PascalCase, or singular nouns for collection names.

D35Soft Delete on MongoDB — deletedAt, Never Hard DeleteNew · Critical
ANGULAR STACK ONLY

MongoDB documents follow the same soft delete pattern as PostgreSQL. Set deleted_at = datetime.utcnow() instead of calling document.delete(). All queries include deleted_at=None in the filter. Implement a Beanie before-find hook that automatically appends this filter to all standard queries.

D36MongoDB Backups — Automated Daily via Railway or mongodumpNew · High
ANGULAR STACK ONLY

Production MongoDB instances must have automated daily backups. Use Railway's managed MongoDB backup feature or a scheduled mongodump to object storage. Minimum retention period is 7 days. Perform a test restore monthly in staging to verify backup integrity.

D37Environment-Specific MongoDB URIs — Never Shared Across EnvironmentsNew · Critical
ANGULAR STACK ONLY

Development, staging, and production MongoDB instances are completely separate. The production MONGODB_URI must never be used in development or CI environments. Each environment has its own database cluster, access credentials, and Railway service. Cross-environment data contamination is a critical security violation.

D38MongoDB Schema Versioning — Version Field on Evolving DocumentsNew · High
ANGULAR STACK ONLY

Document schemas that are expected to evolve over time must include a schema_version: int = Field(default=1) field. When the schema changes, increment the version. Migration scripts read the version field to apply the correct transformation. This enables backward-compatible reads of older documents alongside new ones.

PART 4 / D39–D46 ChromaDB — Vector Storage FundsLink Academy Only · RAG Pipeline
D39ChromaDB in Separate Container — Never Co-LocatedCritical
ANGULAR STACK — FUNDSLINK ONLY

ChromaDB runs as a standalone container separate from the FastAPI application container. Never bundle ChromaDB inside the FastAPI container. The ChromaDB HTTP client in FastAPI connects to this separate container via a service URL. This isolation allows ChromaDB to be scaled, restarted, and maintained independently.

D40AI Service Has Read-Only Access to ChromaDBCritical
ANGULAR STACK — FUNDSLINK ONLY

The FastAPI AI service connects to ChromaDB in read-only mode. Embedding ingestion (adding new scholarship documents) is a separate admin-triggered process — never a real-time user-triggered operation. The ChromaDB access token used by the AI service has query-only permissions.

D41Similarity Threshold — Minimum 0.7, Empty Result if None QualifyCritical
ANGULAR STACK — FUNDSLINK ONLY

All ChromaDB similarity queries must specify a minimum distance threshold equivalent to a similarity score of 0.7. Results below this threshold are discarded before returning. If no results meet the threshold, return an empty array with a clear "no matches found" message — never return low-confidence results to users.

D42ChromaDB Metadata Uses PostgreSQL cuids as ReferencesCritical
ANGULAR STACK — FUNDSLINK ONLY

Document metadata stored in ChromaDB must use PostgreSQL cuid strings to reference scholarships and funders. Format: {"scholarship_id": "clx7...", "funder_id": "clx8..."}. Never store user PII (names, emails, ID numbers) in ChromaDB metadata — only system identifiers.

D43Embedding Ingestion Is Admin-Triggered — Not User-TriggeredHigh
ANGULAR STACK — FUNDSLINK ONLY

Adding new scholarship documents to ChromaDB (embedding ingestion) is triggered by an admin action — never automatically on every scholarship record creation. Ingestion runs as a batch process: admin approves scholarship → triggers ingestion pipeline → ChromaDB updated. This prevents unbounded real-time embedding generation.

D44ChromaDB Collections Named by Domain — One Collection per ConcernHigh
ANGULAR STACK — FUNDSLINK ONLY

ChromaDB collections are named by domain concern: scholarships, bursaries, seta_funds. Never use a single catch-all collection. One collection per distinct document type enables independent scaling, versioning, and re-indexing of each funding category.

D45ChromaDB Backup — Weekly Export to Object StorageHigh
ANGULAR STACK — FUNDSLINK ONLY

ChromaDB data must be exported weekly to object storage (S3 or equivalent). Embeddings can be regenerated from source documents but regeneration is expensive. A weekly backup prevents full regeneration after data loss. Store the backup alongside the source document IDs so the collection can be rebuilt without re-running the full ingestion pipeline.

D46No User PII in ChromaDB — Identifiers OnlyCritical
ANGULAR STACK — FUNDSLINK ONLY

ChromaDB must never store personally identifiable information: no names, emails, ID numbers, addresses, or financial details. Only system-generated identifiers (PostgreSQL cuids) and non-personal metadata (scholarship type, funding amount category, academic field) are stored in ChromaDB. PII belongs in PostgreSQL with proper access controls.

PART 5 / D47–D58 Cross-Database & Migrations Both Stacks · Coordination + Safety
D47Migrations Run Before Service Starts — Always, on Every DeployCritical
BOTH STACKS

prisma migrate deploy runs and must succeed before the application server starts accepting requests. This is enforced in the Railway start command (Angular stack) and Vercel deploy hook (Next.js stack). A migration failure aborts the deploy — the previous version stays live. Never start a service with a pending migration.

D48Cross-Database Sync Must Be Explicit and TestedCritical
BOTH STACKS

Every operation that writes to more than one database must have an integration test that verifies the sync. No silent cross-database writes. If a PostgreSQL write must trigger a MongoDB write or a ChromaDB re-embedding, the trigger mechanism and its failure mode must be documented, logged, and covered by an integration test before deployment.

D49Cross-Database Failure Is Logged and Alertable — Never Silently IgnoredCritical
BOTH STACKS

If a cross-database sync operation fails (e.g., PostgreSQL write succeeds but MongoDB write fails), the failure must be: (1) logged as a structured error with the entity IDs involved, (2) captured in Sentry, (3) trigger a retry queue entry. Never allow inconsistent state to go undetected.

D50PostgreSQL Is Always Written First in Cross-DB OperationsHigh
BOTH STACKS

In any operation that writes to multiple databases, PostgreSQL is written first. MongoDB and ChromaDB writes follow. If the PostgreSQL write fails, the entire operation aborts with no writes to other databases. PostgreSQL is the system of record — other databases are derived from it, not the other way around.

D51Additive-First Migration Strategy — No Destructive Changes in One StepHigh
BOTH STACKS

All schema changes follow the expand-contract pattern: Phase 1 — add new column/field (optional). Phase 2 — deploy code that writes to both old and new. Phase 3 — backfill old data to new structure. Phase 4 — deploy code that reads only new. Phase 5 — drop old column. Each phase is a separate deploy verified in staging before going to production.

D52Staging Environment Mirrors Production Database Structure ExactlyHigh
BOTH STACKS

The staging environment must have the same database schema as production at all times. Every migration is applied to staging first, verified, then applied to production. Staging must use the same database provider (Railway Postgres, Railway MongoDB) — not SQLite or in-memory substitutes.

D53Never Modify a Production Migration File After DeploymentCritical
BOTH STACKS

Prisma migration files in prisma/migrations/ are immutable once deployed to any environment. Never edit, rename, or delete a migration file that has been applied. If a deployed migration has a bug, create a new corrective migration — never modify the existing one. Prisma tracks migration checksums and will refuse to apply modified migrations.

D54Database Connection Errors Are Non-Fatal on Startup — Retry with BackoffHigh
BOTH STACKS

If a database connection fails on application startup, the service retries with exponential backoff (1s, 2s, 4s, 8s — max 5 retries) before aborting. This handles Railway and Vercel cold starts where the database may not be immediately ready. After 5 failed retries, the service exits with a non-zero code to trigger a deployment retry.

D55Environment Variable Validation — Fail Fast on Missing DB ConfigCritical
BOTH STACKS

At application startup, validate all required database environment variables are present before attempting any connection. Missing DATABASE_URL, MONGODB_URI, or CHROMA_URL must cause an immediate startup failure with a clear error message. Never start the service with undefined database configuration.

D56Query Performance Budget — p95 Under 150ms for Standard QueriesHigh
BOTH STACKS

Standard CRUD queries (single record fetch, paginated list) must complete within 150ms at p95. Queries consistently exceeding this threshold require an index review. Enable slow query logging: PostgreSQL log_min_duration_statement = 100, MongoDB operationProfiling.slowOpThresholdMs = 100. Alert on any query exceeding 500ms.

D57No Schema Changes During Traffic Hours — Off-Peak Migrations OnlyCritical
BOTH STACKS

Production schema changes (Prisma migrations, MongoDB index creation) are deployed outside peak traffic hours. For South African systems, peak hours are 07:00–22:00 SAST. Schedule migrations for 00:00–04:00 SAST. Emergency migrations during traffic hours require approval and a documented rollback plan that can execute in under 5 minutes.

D58Database Health Check in /health Endpoint — Both Databases on Angular StackHigh
BOTH STACKS

The /health endpoint must verify connectivity to all databases used by the service. Next.js stack: check PostgreSQL. Angular stack: check PostgreSQL AND MongoDB AND ChromaDB (FundsLink only). A service whose database connectivity fails its health check is removed from load balancing until connectivity is restored.

§ Annex A — Forbidden Patterns (FP01–FP20)
⚠ FORBIDDEN PATTERNS — VIOLATION = BUILD FAILURE · BOTH STACKS UNLESS MARKED
FP01 — SELECT * IN PRISMA
Calling findMany(), findFirst(), or findUnique() without an explicit select clause on any model.
✓ Fix: Explicit select with only required fields (D11).
FP02 — FINANCIAL DATA IN MONGODB
Storing transaction amounts, account balances, interest rates, or deposit records in MongoDB.
✓ Fix: All financial data in PostgreSQL only (D3).
FP03 — HARD DELETE IN PRODUCTION
Calling prisma.model.delete() or document.delete() on production records instead of setting deleted_at.
✓ Fix: Soft delete with deleted_at timestamp (D8, D35).
FP04 — PII IN CHROMADB
Storing names, emails, ID numbers, or any personal data in ChromaDB metadata or document content.
✓ Fix: Only PostgreSQL cuid identifiers in ChromaDB (D46).
FP05 — MONGODB WITHOUT BEANIE SCHEMA
Direct Motor or PyMongo calls writing to a collection without a corresponding Beanie document class. [Angular]
✓ Fix: All MongoDB access through defined Beanie schemas (D25).
FP06 — AUTHENTICATION DATA IN MONGODB
Storing password hashes, JWT secrets, refresh tokens, or session data in MongoDB collections.
✓ Fix: All auth data in PostgreSQL exclusively (D4).
FP07 — UNINDEXED MONGODB QUERY FIELDS
Querying a MongoDB field without an explicit index defined — causes collection scans in production. [Angular]
✓ Fix: Indexed(type) annotation on all query fields (D29).
FP08 — RAW AI OUTPUT STORED WITHOUT VALIDATION
Storing LangChain/LLM output strings directly in MongoDB without Pydantic schema validation. [Angular]
✓ Fix: Validate through AIReasoningSchema.parse() first (D31).
FP09 — MIGRATION MODIFIED AFTER DEPLOY
Editing, renaming, or deleting a Prisma migration file that has been applied to any environment.
✓ Fix: Create a new corrective migration instead (D53).
FP10 — SIMILARITY RESULTS BELOW 0.7 RETURNED
Returning ChromaDB query results with a score below the 0.7 similarity threshold to users. [FundsLink]
✓ Fix: Filter at threshold, return empty if none qualify (D41).
FP11 — CHROMADB CO-LOCATED WITH FASTAPI
Running ChromaDB inside the FastAPI application container instead of as a separate service. [FundsLink]
✓ Fix: Separate ChromaDB container with HTTP client (D39).
FP12 — UNBOUNDED LIST QUERIES
Prisma findMany() or MongoDB find() without a limit — returns all records regardless of table size.
✓ Fix: Always include take/skip (Prisma) or limit/skip (Mongo) (D14, D30).
FP13 — DIRECT DB ACCESS FROM FRONTEND
Browser-side Prisma, MongoDB driver, or direct ChromaDB HTTP calls from Angular or React code.
✓ Fix: All DB access through backend service layer (D7).
FP14 — MULTI-STEP WRITE WITHOUT TRANSACTION
Sequential Prisma writes to multiple tables without a prisma.$transaction() wrapper.
✓ Fix: Wrap all multi-table writes in prisma.$transaction() (D15).
FP15 — FREE-TEXT STATUS FIELDS
String fields for status, type, or role with no enum constraint — allows invalid values.
✓ Fix: Define Prisma enum types for all fixed-value fields (D22).
FP16 — MIGRATION BEFORE STAGING VERIFICATION
Applying a Prisma migration directly to production without first running and verifying it in staging.
✓ Fix: Staging first, production second — always (D52).
FP17 — MONGODB OBJECTID AS CROSS-DB REFERENCE
Using MongoDB ObjectID as the reference to PostgreSQL entities instead of the PostgreSQL cuid. [Angular]
✓ Fix: Use PostgreSQL cuid string as the reference field value (D5, D28).
FP18 — SCHEMA CHANGE DURING PEAK HOURS
Running production migrations between 07:00 and 22:00 SAST without emergency approval.
✓ Fix: Schedule migrations for 00:00–04:00 SAST (D57).
FP19 — MISSING DELETED_AT FILTER
Queries that can return soft-deleted records because the where: { deleted_at: null } filter is absent.
✓ Fix: Prisma middleware + Beanie hook auto-appends this filter (D12, D35).
FP20 — PRODUCTION DB URI IN DEVELOPMENT
Using the production DATABASE_URL or MONGODB_URI in a local development or CI environment. [Angular]
✓ Fix: Separate env credentials per environment — never share (D37).
