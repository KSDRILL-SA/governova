---

> *"How work enters a repository is itself governed. The process is part of the product."*

This standard is **world-class by design and universal by intent**: it is followed identically by a solo developer and by a 200-person organisation. Only the *approval and merge authority* changes by mode — never the process.

---

## §1 — The Workflow Order

Every unit of work follows this exact order:

```
BRANCH  →  ISSUE  →  PR  →  MERGE
```

1. **Branch first.** Create the working branch off the integration branch before anything else, so all work is isolated from the first keystroke.
2. **Issue.** Open the tracking issue describing the work, with full metadata (§4). The branch and issue are linked.
3. **PR.** Open the pull request from the branch, linking the issue with `Closes #N`, carrying the same metadata (§5).
4. **Merge.** Merge per the mode policy (§6).

> Rationale for branch-first: work frequently begins exploratory. Branching first guarantees nothing ever lands on the integration branch unbranched, and the issue is written with the actual shape of the work already visible.

---

## §2 — The No-AI-References Rule (Zero Tolerance)

**No AI references appear anywhere in the GitHub surface of a Governova repository.** This is absolute and applies to:

| Surface | Rule |
|---------|------|
| Commit messages & bodies | No AI tool names, no `Co-Authored-By:` AI trailers, no "generated by" lines |
| Commit/PR co-authors & contributors | Human identities only — no AI bot/agent accounts (e.g. no `Cursor Agent`) |
| PR titles & bodies | No AI tool names or generation notices |
| Issue titles & bodies | Same |
| Branch names | No AI tool names |
| File names | No AI tool names (a filename is a reference) |

All authorship is attributed to the **human author**. Governova governs AI development; its own history must stand as human-authored, professional, and clean.

> This is a hard rule, not a style preference. A commit, PR, branch, or co-author that carries an AI reference is a violation and is corrected before merge — or, if already merged, scrubbed by history rewrite (see `protocols/git-workflow.md`).

> Note on document *content*: the constitutions legitimately describe an AI engineer relay as governed subject matter. The rule above governs the **GitHub metadata surface** (commits, PRs, branches, co-authors, filenames) — not the governed content of the standards themselves.

## §3 — Branch Naming

Kebab-case, typed prefix, concise description. No AI references.

| Type | Pattern | Example |
|------|---------|---------|
| Feature | `feature/{desc}` or `feature/{issue}-{desc}` | `feature/19-stack-matrix` |
| Fix | `fix/{desc}` | `fix/login-validation` |
| Refactor | `refactor/{desc}` | `refactor/four-layer-architecture` |
| Docs | `docs/{desc}` | `docs/operating-practices-governance` |
| Chore | `chore/{desc}` | `chore/ci-cache` |
| Hotfix | `hotfix/{desc}` | `hotfix/token-expiry` |

Integration branch is `main` unless a repository declares otherwise in its CONSTITUTION-INDEX.

## §4 — Issue Requirements (Full Metadata, Always)

Every issue carries **all** of the following before work is considered tracked:

| Field | Requirement |
|-------|-------------|
| **Type** | `Task` · `Bug` · `Feature` (repo/org issue types) |
| **Milestone** | The active milestone the work belongs to |
| **Project** | The governing project board |
| **Labels** | At least one technical/area label (e.g. `documentation`, `enhancement`, `security`) |
| **Assignee** | Solo: self-assign. Team: the owning engineer |
| **Body** | Goal · Scope · Acceptance criteria |

An issue missing any of these is incomplete and is corrected before its PR merges.

---

## §5 — Pull Request Requirements

| Field | Requirement |
|-------|-------------|
| **Links issue** | `Closes #N` in the body (auto-closes the issue on merge) |
| **Metadata** | Same milestone, project, labels, assignee as its issue |
| **Body** | What it does · How verified · Acceptance checklist |
| **Clean history** | No AI references (§2); conventional commits |
| **Green checks** | All required status checks pass (where configured) |

---

## §6 — Merge & Assignment Policy by Mode

The framework supports **both** modes. The process above is identical; only authority differs.

| Concern | Solo mode | Team mode |
|---------|-----------|-----------|
| **Assignment** | Self-assign | Owning engineer assigned by lead/triage |
| **Review** | Documented AI/self review (S10.27); no human gate required | Human review required; 2 human approvals (S1.30) |
| **Merge authority** | **Auto-merge** for speed once checks pass; founder may merge manually for sensitive changes | **Human-only** merge after approvals |
| **Strategy** | Squash | Squash |
| **Branch cleanup** | Delete on merge | Delete on merge |

> **Auto-merge availability.** GitHub-native auto-merge requires a repository plan/visibility that permits it. Where unavailable, solo mode uses an immediate squash-merge by the founder as the equivalent "speed" path. Sensitive changes (constitutional amendments, security, production) are **always** merged deliberately by a human regardless of mode.

## §7 — Conventional Commits

```
type: short imperative description (#issue)
```

Types: `feat` · `fix` · `docs` · `refactor` · `test` · `chore` · `perf`. Bodies explain the *why*, never name an AI tool.

## §8 — Constitutional Mapping

This protocol operationalises, and is governed by:

- **C1 — Engineering Standards** — Git discipline, PR process, conventional commits, sprint governance.
- **C10 — AI Collaboration** — the relay, and the boundary that AI never holds L4 merge authority on a sensitive change.

Proposed backing standards (pending C0 §8 ratification) are tracked in `governance/changelog/amendments-log.md`:

| Proposed ID | Title |
|-------------|-------|
| `S1.99` (ratified 2026-06-21) | Branch → Issue → PR → Merge workflow order, mandatory full issue/PR metadata |
| `S1.100` (ratified 2026-06-21) | No-AI-references rule across the GitHub metadata surface |
| `S10.40` (ratified 2026-06-21) | Mode-based merge authority — solo auto-merge / team human-only; AI never merges sensitive changes |

Until ratified, this document is **operational guidance** with the force of an active protocol; the standards above are proposals for Founder (L4) ratification.
