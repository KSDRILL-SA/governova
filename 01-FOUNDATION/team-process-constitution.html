§ Part 1 — Build Philosophy (T1–T5)
Core Principles
  • 1st Design before code
  • 2nd One system at a time
  • 3rd Constitution governs all
  • 4th Ship MVP, then iterate
  • 5th No forward dependencies
PART 1 / T1–T5Build Philosophy5 Critical · Foundation of Everything
T1Sequential Build — One Flagship System Fully Before the Next BeginsCritical
KSDRILL SA

KSDRILL SA builds one flagship system at a time. FundsLink Academy must ship its MVP before Reserve Bank development begins. Reserve Bank must ship before SyncUp begins. No parallel platform development. This is the deliberate strategic choice — deep execution over broad ambition. The build order is: FundsLink (Q2 2026) → Maphophe (Q3 2026) → Reserve Bank (Q4 2026) → SyncUp (Q1 2027).

T2Design-First — Full System Design Locked Before First Line of CodeCritical
KSDRILL SA

Every system goes through four phases in order: (1) Architecture design — full platform architecture and user flows, (2) Database and module design, (3) Interface design, (4) Development. No code is written before the architecture is locked. This rule is the foundation of the entire constitutional approach.

Phase 1
Architecture + user flows — locked
Phase 2
DB schema + module structure — locked
Phase 3
Interface designs — locked
Phase 4
Development begins — constitution governs
T3The 10 Constitutions Govern All Technical DecisionsCritical
KSDRILL SA

No technical decision — stack choice, database selection, auth strategy, deployment platform, testing framework — is made outside the constitutional framework. If a decision is not covered by an existing constitution, a constitutional amendment is proposed and approved before the decision is made. "We'll figure it out as we go" is forbidden.

T4Stack Assignment Is Locked — No Mid-Build Framework ChangesCritical
KSDRILL SA

The framework assignment for each system is locked: FundsLink and Reserve Bank use Angular + FastAPI. Maphophe and SyncUp use Next.js. Once a system's stack is assigned and build begins, the stack cannot be changed without a full constitutional amendment. Mid-build stack changes destroy architectural integrity and timeline.

T5MVP First — Ship the Primary Workflow, Nothing MoreCritical
KSDRILL SA

The MVP for each system ships when the primary user workflow is complete and working end-to-end. No admin panels, no analytics dashboards, no secondary features in v1. The definition of done for v1 is defined in the Product & Feature Constitution. Scope creep is an active threat — the constitution is the defence.

§ Part 2 — Sprint & Planning (T6–T10)
Sprint Structure
  • Length 2 weeks
  • Monday Sprint planning
  • Wednesday Mid-sprint check
  • Friday Sprint review + retro
  • Max 6 tickets per sprint
Ticket Definition of Done
  • ✓ Feature works end-to-end
  • ✓ Tests written and passing
  • ✓ CI fully green
  • ✓ PR reviewed + merged
  • ✓ Deployed to staging
PART 2 / T6–T10Sprint & Planning3 Critical · 2 High
T6Two-Week Sprints — Fixed Cadence, No ExtensionsCritical

Sprints are exactly two weeks long. They do not extend because a ticket is not done. Incomplete tickets move to the next sprint with a documented reason. Sprint cadence is the heartbeat of the build — consistency matters more than any individual ticket.

T7Sprint Planning — OpenAPI Contract Written Before Sprint StartsCritical

For any sprint that includes backend endpoint work, the OpenAPI contract for those endpoints must be written and approved before the sprint begins. Development does not start without a contract. This aligns with Backend Constitution B7 and prevents the frontend waiting on a contract mid-sprint.

T8Maximum 6 Tickets Per Sprint — Quality Over QuantityCritical

No sprint contains more than 6 tickets. Smaller ticket counts mean deeper work, fewer context switches, and higher quality. If a feature requires more than 6 tickets to complete, it is split across multiple sprints with a clear dependency map. A sprint with 3 fully completed tickets is better than one with 8 half-finished ones.

T9Tickets Must Have Acceptance Criteria Before Moving to In ProgressHigh

A ticket cannot move from "To Do" to "In Progress" without documented acceptance criteria. Acceptance criteria define what "done" looks like — not how to implement it. At least three criteria per ticket. Tickets without criteria are sent back to the planning stage.

T10Sprint Retrospective — Actions Documented, Followed Up Next SprintHigh

Every sprint ends with a retrospective that produces at least one concrete action item. Action items from the previous retrospective are reviewed at the start of the next sprint. Retrospectives that produce no actions are considered incomplete. The goal is continuous improvement — not a ritual checkbox.

§ Part 3 — Communication Standards (T11–T15)
Communication Channels
  • Code GitHub PRs + Issues
  • Async GitHub Discussions
  • Sync Scheduled standups only
  • Urgent WhatsApp (flagged)
  • Never Verbal undocumented decisions
PART 3 / T11–T15Communication Standards1 Critical · 4 High
T11All Technical Decisions Documented in Writing — No Verbal-Only DecisionsCritical

Technical decisions — stack choices, architectural changes, process changes, constitutional amendments — must be documented in writing before they are acted upon. GitHub Issues or Discussions are the canonical record. A decision made verbally that is not written down does not exist as far as the system is concerned.

T12Standups Are Async — Three Questions, Written, DailyHigh

Daily standups are asynchronous — posted in writing each morning. Format: (1) What did I complete yesterday? (2) What am I doing today? (3) Any blockers? Standups take under 3 minutes to write. They create a searchable record of progress and surface blockers before they become emergencies.

T13Blockers Are Raised Within 4 Hours — Not End of DayHigh

When a developer encounters a blocker that will prevent completing a sprint commitment, it is raised within 4 hours of identifying it — not at the end-of-day standup. Early blocker identification allows the team to adapt. Sitting on a blocker for 8 hours compounds the problem.

T14Feedback Is Specific and Actionable — No Vague RejectionsHigh

All feedback — in code reviews, PR comments, sprint retrospectives — is specific and actionable. "This is wrong" is not feedback. "This violates Q15 (max 200 lines) — split the service layer from the route handler" is feedback. Vague feedback is returned to the sender with a request to be specific.

T15GrowthCore Solutions Work Does Not Overlap KSDRILL SA SprintsHigh

KSDRILL SA product sprints and GrowthCore Solutions client work are planned in separate lanes. When GrowthCore client deadlines fall within a KSDRILL sprint, the sprint ticket count is reduced accordingly. Context-switching between companies mid-sprint damages both. Communicate cross-company load during sprint planning.

Branch Naming

  • fix/ Bug fix
  • chore/ Maintenance
  • docs/ Documentation only
  • refactor/ No behaviour change
  • Format type/T123-short-desc
Repo Structure
  • NJ One repo per Next.js system
  • ANG Separate repos: Angular + FastAPI
  • Org All under KSDRILL-SA GitHub org
  • Gov system-design-template repo
PART 4 / T16–T21Git & Branching3 Critical · 3 High
T16main Is Always Deployable — Never Commit Broken Code to mainCritical

The main branch is always in a deployable state. Every commit on main has passed all CI checks, all tests, and at least two code reviews. Broken code lives on feature branches — never on main. GitHub branch protection enforces this: direct pushes and merges with failing CI are blocked.

T17Feature Branches From main — Short-Lived, One Ticket Per BranchCritical

Every ticket gets its own branch created from the latest main. Branches are named feat/T123-short-description where T123 is the GitHub issue number. Branches live for the duration of one sprint maximum — long-lived branches drift and create merge conflicts. Branch naming is enforced by a pre-push hook.

T18Angular Stack — Separate Repos for Angular Frontend and FastAPI BackendCritical
ANGULAR STACK

FundsLink and Reserve Bank each have two separate repositories: one for the Angular frontend, one for the FastAPI backend. They are never monorepos. This reflects the separate deployment targets (Vercel for Angular, Railway for FastAPI) and enables independent CI pipelines, versioning, and deployment. Both repos live under the KSDRILL-SA GitHub organisation.

T19Conventional Commit Messages — type(scope): descriptionHigh

All commit messages follow the conventional commit format: type(scope): short description. Types: feat, fix, refactor, docs, test, chore. Scope is the system or module affected. Commitlint enforces this via a commit-msg hook. Bad commit messages are rejected before the commit is created.

T20Rebase Before PR — Clean Linear History on mainHigh

Feature branches are rebased onto the latest main before a PR is opened. This produces a clean, linear history without merge commits. git merge main on a feature branch is forbidden — always git rebase main. Squash merge on PR completion keeps main history one-commit-per-feature.

T21system-design-template Is the Governance Repository — Updated With Every ChangeHigh

The MALULEKE-KS/system-design-template repository is the canonical home for all 10 constitutions. Any amendment to any constitution is committed to this repository first. Platform repositories reference the governance system via a git submodule or clone. The governance repo is the source of truth — not individual platform repos.

§ Part 5 — Constitutional Governance (T22–T26)
Amendment Process
  • 1st Problem documented in Issue
  • 2nd Proposed change written
  • 3rd 48-hour review period
  • 4th Owner approves
  • 5th Version bumped + locked
  • 6th All repos updated
Review Cadence
  • Weekly Standup + blockers
  • Bi-weekly Sprint review
  • Monthly Micro-review of active const.
  • Quarterly Full constitutional review
  • Annual Major version consideration
PART 5 / T22–T26Constitutional Governance1 Critical · 4 High
T22Only the Owner Can Approve Constitutional AmendmentsCritical

Amendments to any of the 10 constitutions require written approval from Maluleke Kurhula Success (KSDRILL SA owner). Proposed amendments are documented in a GitHub Issue, open for 48-hour review, then approved or rejected by the owner. An approved amendment is committed to system-design-template with a version bump and a changelog entry. No amendment takes effect before owner approval.

T23Quarterly Constitutional Review — All 10 ConstitutionsHigh

All 10 constitutions are reviewed quarterly (July, October, January, April). The review checks: are rules still relevant to the current system design? Are there gaps that need new rules? Are any rules in conflict? The next scheduled review is 2026-07-07. Reviews produce a documented outcome — even if no changes are needed.

T24Version Bumping Rules — Minor for Additions, Major for Breaking ChangesHigh

Constitution versioning follows semver: minor bump (v1.0 → v1.1) for adding rules or clarifying existing ones. Major bump (v1.x → v2.0) for changing the stack, removing rules, or restructuring the constitution. Every version bump includes a changelog entry with: what changed, why it changed, and the effective date.

T25Cross-Constitution Conflicts Are Resolved at the Full-System-Design LevelHigh

When two constitutions appear to conflict on the same topic, the Full System Design v2.0 document is the tie-breaker. If the conflict is not addressed there, the Constitutional Order v2.0 defines precedence by phase — earlier constitutions (foundational) take precedence over later ones (product). Conflicts are documented, resolved, and committed as amendments to both affected constitutions.

T26New Systems Must Register With the Constitutional Order Before BuildingHigh

Any new platform or system added to KSDRILL SA's portfolio must be registered in the Constitutional Order v2.0 before development begins. Registration includes: system name, stack assignment, build order slot, and which constitutions govern it. Systems built outside the constitutional framework are not recognised as KSDRILL SA products.

§ Annex A — Forbidden Patterns (FP01–FP14)
⚠ FORBIDDEN PATTERNS — VIOLATION = PROCESS FAILURE
FP01 — PARALLEL PLATFORM DEVELOPMENT
Building two flagship systems simultaneously.
✓ Fix: Sequential only — one system ships before next begins (T1).
FP02 — CODE BEFORE DESIGN IS LOCKED
Writing any production code before architecture and schema are approved.
✓ Fix: Four design phases completed first (T2).
FP03 — MID-BUILD STACK CHANGE
Switching from Angular to Next.js or vice versa after development has started.
✓ Fix: Stack locked before build — requires full constitutional amendment (T4).
FP04 — VERBAL-ONLY DECISIONS
Making a technical or architectural decision in conversation without documenting it.
✓ Fix: All decisions documented in GitHub before acted upon (T11).
FP05 — DIRECT PUSH TO MAIN
Pushing commits directly to main without a PR, review, and CI passage.
✓ Fix: Branch protection on main — PRs required always (T16).
FP06 — SPRINT EXTENSION
Extending a sprint past its two-week boundary because tickets are not done.
✓ Fix: Incomplete tickets move to next sprint, documented (T6).
FP07 — TICKET WITHOUT ACCEPTANCE CRITERIA
Moving a ticket to In Progress without at least three written acceptance criteria.
✓ Fix: Criteria required before In Progress status (T9).
FP08 — AMENDMENT WITHOUT OWNER APPROVAL
Implementing a constitutional change without written approval from the owner.
✓ Fix: Owner must approve every amendment (T22).
FP09 — MONOREPO FOR ANGULAR STACK
Combining Angular frontend and FastAPI backend in a single repository.
✓ Fix: Separate repos — Vercel (Angular) + Railway (FastAPI) (T18).
FP10 — LONG-LIVED FEATURE BRANCHES
Feature branches that live longer than one sprint without being merged or deleted.
✓ Fix: Short-lived branches — one ticket, one sprint max (T17).
FP11 — BLOCKING WITHOUT RAISING
Sitting on a blocker for more than 4 hours without raising it to the team.
✓ Fix: Raise blockers within 4 hours of identifying them (T13).
FP12 — SCOPE CREEP IN v1
Adding secondary features, admin panels, or analytics to a v1 MVP sprint.
✓ Fix: v1 = primary workflow only — constitution governs scope (T5).
FP13 — VAGUE CODE REVIEW FEEDBACK
Review comments like "this is bad" or "redo this" without specific guidance.
✓ Fix: Specific, actionable feedback referencing the relevant rule (T14).
FP14 — NEW SYSTEM WITHOUT REGISTRATION
Building a new KSDRILL SA product without registering it in the Constitutional Order.
✓ Fix: Register in Constitutional Order v2.0 before build begins (T26).
