§ Test Pyramid — v1.0 Strategy
E2E Tests (10-20)
Integration Tests (50-100)
Unit Tests (200-500+)
Distribution Targets:
Unit: 70% of test count
Integration: 20% of test count
E2E: 10% of test count
Execution: Unit (<2s), Integration (<30s), E2E (<5min)
§ Part 1 — Testing Strategy (T1-T4)
Purpose

Define the testing approach, levels, and expectations.

PART 1 / T1-T4Testing Strategy2 Critical · 2 High
T1Test Pyramid RequiredCritical

Test suite MUST follow the test pyramid: many unit tests, fewer integration tests, few E2E tests. Ratio target: 70% unit / 20% integration / 10% E2E.

T2CI Must Run All TestsCritical

CI pipeline MUST run the full test suite. No merging with failing tests (Infrastructure Constitution I15).

T3Test Execution Time LimitsHigh

Unit tests: <2s per test, <2min total. Integration: <30s per test, <10min total. E2E: <5min total. (Infrastructure I16).

T4Test Environment ParityHigh

Tests MUST run in environment matching production (same Node version, same dependencies, isolated DB). Use test containers for database tests.

§ Part 2 — Unit Tests (T5-T8)
Framework

Jest + React Testing Library (Frontend) / Vitest (Backend).

PART 2 / T5-T8Unit Tests2 Critical · 2 High
T5Business Logic CoverageCritical

All business logic (calculations, validations, transformations) MUST have unit tests. No untested logic in production.

T6Edge Cases RequiredCritical

Unit tests MUST cover edge cases: null/undefined inputs, empty arrays, boundary values, error conditions.

T7One Assertion Per Test (Prefer)High

Prefer one logical assertion per test. Tests with multiple assertions MUST test a single behavior.

T8Descriptive Test NamesHigh

Test names MUST describe expected behavior: it('returns user when valid email provided') not it('works').

§ Part 3 — Integration Tests (T9-T12)
Purpose

Verify components work together correctly.

PART 3 / T9-T12Integration Tests2 Critical · 2 High
T9API Endpoint Testing RequiredCritical

Every API endpoint MUST have integration tests covering success, error, and edge cases (Backend Constitution B11).

T10Database Integration TestsCritical

Database queries and mutations MUST have integration tests. Use test database with transactions for isolation.

T11External Service MockingHigh

External API calls (OpenAI, Stripe) MUST be mocked in integration tests. Test both success and failure responses.

T12Auth Flow IntegrationHigh

Authentication flows (register, login, logout, session validation) MUST have comprehensive integration tests.

§ Part 4 — E2E Tests (T13-T16)
Framework

Playwright (cross-browser) or Cypress.

PART 4 / T13-T16E2E Tests2 Critical · 2 High
T13Critical User JourneysCritical

Critical user journeys (auth → dashboard → core feature) MUST have E2E tests. Minimum 1 per major feature.

T14E2E Test EnvironmentCritical

E2E tests MUST run against staging environment (not local). Use CI to deploy staging before E2E.

T15Cross-Browser TestingHigh

E2E tests SHOULD run on Chrome and Firefox. Safari optional for v1.

T16Visual Regression (Optional v1)High

Visual regression tests RECOMMENDED for critical UI components. Defer to v2 if not feasible.

§ Part 5 — Contract Tests (T17-T19)
Purpose

Ensure API contract compliance between services.

PART 5 / T17-T19Contract Tests2 Critical · 1 High
T17OpenAPI Contract ValidationCritical

Contract tests MUST verify API responses match OpenAPI specification (Backend Constitution B7).

T18ApiResponse<T> FormatCritical

Contract tests MUST verify all endpoints return ApiResponse<T> format (Backend Constitution B8).

T19Consumer-Driven Contracts (v2 Target)High

Consumer-driven contract testing (Pact) is NOT required for v1. Defer to v2 for service-to-service contracts.

§ Part 6 — Performance Tests (T20-T23)
Purpose

Ensure system meets performance requirements.

PART 6 / T20-T23Performance Tests1 Critical · 3 High
T20Lighthouse CIHigh

Lighthouse CI MUST run on critical pages. Targets: Performance >90, Accessibility >95, SEO >90.

T21Load Testing (v2 Target)High

Load testing NOT required for v1. Defer to v2 for scale verification.

T22Database Query PerformanceCritical

N+1 queries MUST be detected and prevented. Use Prisma's $queryRaw monitoring or query logging.

T23API Response Time TrackingHigh

Performance regression tests MUST track API response times. Alert on >20% regression (Backend Constitution B24).

§ Part 7 — Test Data Management (T24-T27)
Purpose

Consistent, isolated, realistic test data.

PART 7 / T24-T27Test Data Management2 Critical · 1 High · 1 Medium
T24No Production Data in TestsCritical

Tests MUST NOT use production data. Use factories (Faker.js, Factory Bot) to generate test data.

T25Database IsolationCritical

Tests MUST NOT share database state. Use transactions (rollback after each test) or per-test databases.

T26Test Data FactoriesHigh

Use factories (not fixtures) for generating test data. Fixtures are allowed only for static reference data.

T27Seed Data for E2EMedium

E2E tests MUST use predictable seed data. Test database should be reset before E2E test suite runs.

§ Part 8 — Coverage Requirements (T28-T31)
Targets

Lines: 80% · Branches: 70% · Functions: 80%

PART 8 / T28-T31Coverage Requirements2 Critical · 2 High
T28Minimum Coverage ThresholdsCritical

Minimum coverage: lines 80%, branches 70%, functions 80%. CI fails if thresholds not met. (Backend Constitution CQ6-CQ10).

T29Coverage on New CodeCritical

New code MUST maintain or increase coverage. PRs that decrease coverage are BLOCKED.

T30Coverage Reports in CIHigh

Coverage reports MUST be generated in CI and uploaded to Codecov/CodeClimate.

T31Critical Path CoverageHigh

Authentication and payment flows MUST have 100% line and branch coverage.

§ Part 9 — Flaky Test Management (T32-T34)
Purpose

Maintain CI reliability and trust.

PART 9 / T32-T34Flaky Test Management1 Critical · 2 High
T32No Flaky Tests in CICritical

Flaky tests MUST be quarantined immediately (skip in CI). Do NOT re-run CI without fixing (Code Quality CQ35).

T33Flaky Test TrackingHigh

Quarantined tests MUST have issue with owner and due date. Fix within 2 weeks.

T34Test Retry PolicyHigh

Automatic test retry: 0 for unit, 1 for integration, 2 for E2E. More than 2 retries = flaky test (quarantine).
