§ Part 1 — Test Strategy (TS1–TS6)
Test Pyramid

  • Some Integration tests
  • Few E2E tests (critical paths)
  • Few Visual regression tests
Test File Naming

PART 1 / TS1–TS6Test Strategy4 Critical · 2 High · All Stacks
TS1Tests Written Alongside Code — Never AfterCritical
ALL STACKS

Tests are written in the same PR as the feature code. "I'll write tests later" is forbidden. A feature PR without corresponding tests will not be approved for merge. The only exception is a pure refactor PR that changes no behaviour and relies on existing test coverage to validate.

TS2Test Runner Assignment — Vitest for Angular, Jest for Next.js, pytest for PythonCritical
ALL STACKS

The test runner is assigned per stack and cannot be mixed. Angular systems use Vitest exclusively — never Karma, Jasmine, or Jest. Next.js systems use Jest + React Testing Library. FastAPI uses pytest + pytest-asyncio. Installing a non-assigned test runner in a repo fails CI.

TS3Test the Behaviour, Not the ImplementationCritical
ALL STACKS

Tests assert what a function, component, or endpoint does — not how it does it. Tests that assert on internal state, private methods, or implementation details break on every refactor. Tests that assert on outputs, side effects, and rendered UI survive refactors. Tests that require mocking 5+ dependencies signal a design problem — fix the design.

TS4Tests Must Be Independent — No Shared Mutable State Between TestsCritical
ALL STACKS

Each test must be runnable in isolation and in any order. Tests cannot depend on the state left by a previous test. Use beforeEach/afterEach to reset state. Database tests use transactions that roll back after each test. Shared mutable state between tests is the most common source of flaky tests.

TS5Test Naming — Describes Behaviour in Plain EnglishHigh
ALL STACKS

Test names describe the behaviour being tested, not the function name. Format: it('returns empty array when no scholarships match the threshold') not it('findMatches works'). A failing test name must tell you exactly what broke without reading the test body. Test names are the living documentation of expected behaviour.

TS6Critical Path Tests Run on Every PR — Full Suite Runs NightlyHigh
ALL STACKS

CI on every PR runs: unit tests, integration tests, and critical path E2E tests. The full E2E suite and visual regression suite run on a nightly CI job. This keeps PR CI times under 5 minutes while ensuring full coverage is checked daily.

What to Unit Test
  • ✓ All service layer functions
  • ✓ All utility/helper functions
  • ✓ All Pydantic validators
  • ✓ All Zod schemas
  • ✓ All Angular Guards
  • ✓ All React hooks
  • ✓ Error boundary components
What to Integration Test
  • ✓ API endpoints (request → response)
  • ✓ Auth flows end-to-end
  • ✓ DB + service layer together
  • ✓ Cross-DB sync operations
  • ✓ Angular component + service
PART 2 / TS7–TS16Unit & Integration Testing6 Critical · 4 High · All Stacks
TS7Every Service Function Has a Unit Test — No Untested ServicesCritical
ALL STACKS

Every function in the service layer (Angular Services, Next.js API utilities, Python FastAPI services) must have at least one unit test covering its primary success path and one covering its primary failure path. Service functions without tests block the PR merge.

TS8Angular: Test With TestBed, Not With DOM Queries on InternalsCritical
ANGULAR STACK

Angular component tests use TestBed.createComponent() and assert on rendered output via fixture.nativeElement and fixture.debugElement.query(). Never query internal component properties directly — test what the user sees. Use @testing-library/angular for more accessible query patterns where available.

TS9Next.js: React Components Tested With RTL — No EnzymeCritical
NEXT.JS STACK

React component tests use React Testing Library exclusively. Enzyme is forbidden — it encourages testing implementation details. RTL queries by accessible role, text, or label mirror how users interact with the UI. getByRole, getByText, and findBy* async queries are the standard patterns.

TS10API Integration Tests Use a Real Test Database — Not Mocked DBCritical
ALL STACKS

Integration tests for API endpoints run against a real test PostgreSQL database (not SQLite, not mocked). The test database is seeded with fixtures before each test suite and reset via transaction rollback after each test. Docker Compose provides the test database locally and in CI.

TS11Auth Routes Tested for Both Authenticated and Unauthenticated StatesCritical
ALL STACKS

Every protected API endpoint and Angular route must have integration tests that verify: (1) authenticated user with correct role can access it, (2) unauthenticated request receives 401, (3) authenticated user with wrong role receives 403. Auth test coverage is non-negotiable regardless of overall coverage threshold.

TS12Angular HTTP Interceptor Tested — JWT Attachment and 401 RefreshCritical
ANGULAR STACK

The Angular auth HTTP interceptor (Frontend Rule 68) must have dedicated integration tests covering: (1) access token is attached to requests, (2) 401 triggers silent refresh, (3) refresh success → original request retried, (4) refresh failure → redirect to login. Use HttpClientTestingModule to mock HTTP responses.

TS13Mocks Are Reset Between Tests — Never PersistentHigh
ALL STACKS

All mocks, stubs, and spies are cleared and reset in afterEach. Jest: jest.clearAllMocks() in afterEach or clearMocks: true in config. Vitest: equivalent config. Python: @pytest.fixture(autouse=True) patch teardown. Persistent mock state causes non-deterministic test failures.

TS14MSW for API Mocking in Next.js — Never fetch() MocksHigh
NEXT.JS STACK

Frontend API mocking uses Mock Service Worker (MSW) — not jest.fn() patches on global.fetch. MSW intercepts at the network layer, allowing tests to behave like real browser requests. This tests the actual fetch call, error handling, and retry logic — not just the function that calls fetch.

TS15Cross-Database Sync Operations Have Integration TestsHigh
ANGULAR STACK

Every operation that writes to multiple databases (Postgres + MongoDB, or Postgres + ChromaDB) must have an integration test that verifies both writes succeed correctly, and a separate test verifying rollback behaviour when the second write fails (Database Constitution D48).

TS16Snapshot Tests Are Banned — Use Explicit AssertionsHigh
ALL STACKS

Jest/Vitest snapshot tests (expect(component).toMatchSnapshot()) are forbidden for component testing. They encode implementation details and are blindly updated when they fail. Use explicit assertions: expect(screen.getByRole('button')).toHaveTextContent('Submit'). Visual regression with Playwright handles visual testing separately.

PART 3 / TS17–TS24E2E & Visual Regression4 Critical · 4 High · Both TS Stacks
TS17Playwright for E2E — Both TS Stacks, Same Test PatternsCritical
BOTH TS STACKS

All E2E tests use Playwright for both Next.js and Angular systems. Same test patterns, same Playwright config, same CI integration. This allows shared E2E knowledge across the team. Cypress is not used — Playwright has better async handling, parallel execution, and built-in visual comparison.

TS18E2E Tests Cover Every Critical Path — Auth, Primary Feature, ErrorCritical
BOTH TS STACKS

The minimum E2E test suite for every platform: (1) full registration and email verification flow, (2) login with valid credentials, (3) login with invalid credentials — error shown correctly, (4) access primary platform feature end-to-end, (5) logout and verify session cleared. These 5 paths are the minimum viable E2E suite for every v1 system.

TS19Visual Regression at 320/375/390px — Every PR That Changes UICritical
BOTH TS STACKS

PRs that change any UI component trigger Playwright visual regression tests at exactly 320px, 375px, and 390px. Any layout breakage at these widths fails CI. The test suite uses Playwright's page.setViewportSize() and expect(page).toHaveScreenshot() for deterministic comparison. Baseline screenshots are committed to the repo.

TS20E2E Tests Run Against Staging Environment — Never Against ProductionCritical
BOTH TS STACKS

E2E tests run against the staging environment (preview deployments on Vercel, staging environment on Railway). Never run automated E2E tests against production. The staging environment mirrors production structure but uses isolated data. E2E tests that create, modify, or delete data are safe to run on staging.

TS21Playwright Page Objects — No Inline Selectors in Test FilesHigh
BOTH TS STACKS

All Playwright selectors are encapsulated in Page Object Model classes. Test files contain only test logic — not selector strings. A LoginPage class exposes methods like fillEmail(), clickSubmit(), errorMessage(). This makes tests readable and centralises selector maintenance.

TS22E2E Test Data — Seeded Fixtures, Cleaned After Each TestHigh
BOTH TS STACKS

E2E tests use seeded test fixtures for data (not production data, not manually created). After each test or test suite, created data is cleaned up via API calls or DB reset. E2E tests must be idempotent — running them multiple times produces the same results.

TS23Accessibility Tests in E2E — axe-core on Every Critical PageHigh
BOTH TS STACKS

Playwright E2E tests include an accessibility check using @axe-core/playwright on every critical page (login, registration, main dashboard, primary feature page). Accessibility violations at WCAG 2.1 AA level fail CI. This automates the WCAG AA requirement from Frontend Constitution Rule 15.

TS24Flaky Tests Are Fixed Within One Sprint — Never Skipped PermanentlyHigh
ALL STACKS

A test that fails intermittently (flaky) is logged as a GitHub Issue with priority. The test may be temporarily skipped with test.skip for maximum one sprint. If not fixed within one sprint, it becomes a mandatory sprint ticket. Permanently skipped tests accumulate technical debt — they are removed from the suite entirely if not fixed in two sprints.

§ Part 4 — Coverage & CI Gates (TS25–TS30)
Coverage Thresholds

  • ANG Vitest min 75% lines
  • PY pytest-cov min 80% lines
  • Auth 100% — no exceptions
  • Service 85% minimum
PART 4 / TS25–TS30Coverage & CI Gates4 Critical · 2 High · All Stacks
TS25Coverage Below Threshold Fails CI — Hard GateCritical
ALL STACKS

Coverage thresholds are hard CI gates — not guidelines. Jest: --coverageThreshold global.lines 70. Vitest: thresholds.lines: 75. pytest: --cov-fail-under=80. Dropping below threshold fails the build. New features must include tests that maintain or improve coverage. Coverage exclusions (/* istanbul ignore */) require a comment explaining the exemption.

TS26Auth Module Coverage — 100% RequiredCritical
ALL STACKS

The authentication module — login, register, password reset, token refresh, logout, JWT validation, NextAuth callbacks — requires 100% test coverage. Auth bugs have the highest impact of any code in the system. 100% coverage for auth is configured as a separate coverage threshold in the CI config.

TS27CI Test Suite Completes Under 5 Minutes on PRCritical
ALL STACKS

The PR CI test suite (unit + integration + critical E2E) must complete in under 5 minutes. Slow tests block developer flow and reduce CI run frequency. Tests exceeding this limit prompt an investigation into parallelisation (GitHub Actions matrix), test isolation, or database query optimisation.

TS28All Tests Pass Before Merge — Zero Tolerance for Red CICritical
ALL STACKS

No PR is merged with any failing test, regardless of claimed relevance. "That test was already failing before my change" is not an acceptable justification for merging. Fix the failing test or demonstrate it was already a known flaky test (logged issue). CI green is the merge gate.

TS29Test Coverage Reports Published as PR CommentsHigh
ALL STACKS

GitHub Actions publishes a coverage report as a PR comment showing: current coverage %, delta from base branch, and a list of uncovered lines in changed files. This makes coverage regressions visible in code review without requiring reviewers to run tests locally.

TS30Nightly Full Suite — Including Visual Regression and Full E2EHigh
ALL STACKS

A nightly GitHub Actions workflow runs the complete test suite including: all unit and integration tests, the full E2E suite, visual regression at all 5 breakpoints, and accessibility tests. Failures in the nightly suite are treated as high-priority bugs. Results are posted to the team communication channel.

PART 5 / TS31–TS38Python / FastAPI Testing4 Critical · 4 High · Angular Stack
TS31pytest-asyncio for All Async Tests — Never asyncio.run()Critical
PYTHON / FASTAPI

All async FastAPI endpoint tests and async service function tests use @pytest.mark.asyncio. Never call asyncio.run() inside tests. Configure asyncio_mode = "auto" in pyproject.toml to automatically mark all async test functions.

TS32httpx AsyncClient for API Testing — Not TestClient (Sync)Critical
PYTHON / FASTAPI

FastAPI endpoint tests use httpx.AsyncClient(app=app, base_url="http://test") — not the synchronous TestClient. The async client tests the full async request lifecycle including middleware, dependencies, and background tasks. TestClient blocks the event loop and misses async-specific bugs.

TS33Database Tests Use Transaction Rollback — Never Truncate Between TestsCritical
PYTHON / FASTAPI

Each pytest test that writes to PostgreSQL runs inside a transaction that is rolled back on teardown. This is faster than truncating tables and ensures test isolation. Use a db_session fixture that begins a transaction, yields the session, then rolls back. Never use TRUNCATE in test teardown.

TS34Pydantic Model Validation Tests — Every Schema Has a TestCritical
PYTHON / FASTAPI

Every Pydantic request/response model must have unit tests covering: valid input parses correctly, missing required fields raise ValidationError, invalid field types raise ValidationError, and boundary values (empty strings, zero, None) behave as documented. Pydantic validation is the first line of API security.

TS35factory-boy for Test Fixtures — No Hardcoded Test DataHigh
PYTHON / FASTAPI

Test fixtures (users, accounts, applications) are generated by factory-boy factories — not hardcoded dicts or manually created model instances. Factories produce valid, realistic test data with sensible defaults and support override per-test. This keeps tests DRY and makes fixture maintenance centralised.

TS36MongoDB Tests Use Beanie Test Mode — Isolated In-Memory CollectionHigh
PYTHON / FASTAPI

Tests that involve MongoDB use Beanie's test client with an isolated test database, reset between test suites. Never run MongoDB tests against the development or staging MongoDB instance. Use mongomock for unit tests of service functions, and a real test MongoDB container for integration tests.

TS37AI/LangChain Tests Mock the LLM — Never Call Real API in TestsHigh
PYTHON / FASTAPI

Tests for AI service functions mock the LangChain LLM call — never call the real API. Use unittest.mock.patch or pytest-mock to mock the LLM response with a fixture. This makes tests deterministic, fast, and free. A separate manual integration test suite (not in CI) may test real LLM calls with @pytest.mark.slow.

TS38RBAC Tests — Every Endpoint Tests All Three Access LevelsHigh
PYTHON / FASTAPI

Every FastAPI endpoint that has role restrictions must have parametrised pytest tests for all three access scenarios: (1) authorised role succeeds, (2) unauthenticated request gets 401, (3) wrong role gets 403. Use @pytest.mark.parametrize with a fixture that creates users of different roles.

§ Annex A — Forbidden Patterns (FP01–FP16)
⚠ FORBIDDEN PATTERNS — VIOLATION = BUILD FAILURE
FP01 — TESTS WRITTEN AFTER THE FACT
Merging a feature PR with no tests and adding tests "later" in a follow-up PR.
✓ Fix: Tests required in same PR as feature code (TS1).
FP02 — KARMA/JASMINE IN ANGULAR
Running Angular tests with Karma or Jasmine instead of Vitest.
✓ Fix: Vitest + Angular Testing Utilities exclusively (TS2).
FP03 — SNAPSHOT TESTS
Using toMatchSnapshot() for component testing instead of explicit assertions.
✓ Fix: Explicit assertions on rendered output (TS16).
FP04 — SHARED MUTABLE STATE BETWEEN TESTS
Tests relying on state set up by a previous test in the suite.
✓ Fix: beforeEach/afterEach reset state — tests are independent (TS4).
FP05 — ENZYME IN REACT TESTS
Using Enzyme for React component testing instead of React Testing Library.
✓ Fix: RTL getByRole, getByText, findBy* queries only (TS9).
FP06 — MOCKED DATABASE IN INTEGRATION TESTS
Using SQLite, in-memory DB, or Prisma mocks for API integration tests.
✓ Fix: Real test PostgreSQL database in Docker Compose (TS10).
FP07 — E2E AGAINST PRODUCTION
Running automated Playwright tests against the production environment.
✓ Fix: E2E against staging/preview only (TS20).
FP08 — PERMANENTLY SKIPPED TESTS
Tests left in a permanently skipped state with test.skip beyond two sprints.
✓ Fix: Fix within one sprint or remove entirely (TS24).
FP09 — COVERAGE BELOW THRESHOLD
Merging code that drops coverage below the stack's minimum threshold.
✓ Fix: CI hard gate enforces threshold — must include tests (TS25).
FP10 — REAL LLM API CALLS IN CI TESTS
pytest tests that call the real LangChain/LLM API during CI runs.
✓ Fix: Mock LLM with pytest-mock — real calls only in @pytest.mark.slow (TS37).
FP11 — NO AUTH TESTS ON PROTECTED ENDPOINTS
Protected API endpoints or routes without tests for 401 and 403 scenarios.
✓ Fix: Every protected endpoint tested for auth and forbidden states (TS11).
FP12 — ASYNCIO.RUN() IN PYTHON TESTS
Calling asyncio.run() inside pytest test functions to run async code.
✓ Fix: pytest-asyncio with asyncio_mode="auto" (TS31).
FP13 — TRUNCATE IN DB TEST TEARDOWN
Using TRUNCATE or DELETE FROM to clean up test data in Python tests.
✓ Fix: Transaction rollback per test — no truncate (TS33).
FP14 — INLINE SELECTORS IN PLAYWRIGHT TESTS
Using CSS selectors or data-testid strings directly in test files instead of Page Objects.
✓ Fix: All selectors encapsulated in Page Object classes (TS21).
FP15 — SYNCTESTCLIENT FOR ASYNC FASTAPI
Using Starlette's synchronous TestClient for testing async FastAPI endpoints.
✓ Fix: httpx.AsyncClient(app=app) for all endpoint tests (TS32).
FP16 — MERGING WITH FAILING TESTS
Merging any PR where any test is failing, even if claimed unrelated to the change.
✓ Fix: All tests pass before merge — zero tolerance (TS28).
