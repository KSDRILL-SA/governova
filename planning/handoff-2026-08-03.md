## §3 — The four findings worth carrying forward

### 3.1 — Eleven declared anti-patterns never reach the compiled index (#216)

Six are **Critical**, including `AP-S2.55a` — *secret committed to version control*.

An anti-pattern compiles exactly one way: `parse_anti_patterns` reads the
`**Anti-Patterns:**` block inside a standard's own section. The summary table at the foot of
each constitution and `constitution/indexes/anti-patterns-index.md` are **not parsed**, and
both read to a human as authoritative. A standard written in the compact blockquote form
under a range heading — `### S7.33–S7.38 — Additional Python Testing Standards` — has no
field structure and so no such block. The standard compiles; its anti-patterns vanish.

    compiled (authoritative)                    498
    declared in body summary tables             497   -> 8 not compiled
    listed in the anti-patterns index           110   -> 4 not compiled
    union absent from the compiled index         11

**This changes #205.** That issue is recorded as blocked because *S5.28 carries no
anti-pattern to bind to*. True of the compiled index, false of the constitution:
**`AP-S5.28a` is already written down**, worded exactly as the rule behaves — `Float` column
type for monetary values. It was never invented; it was lost in compilation. #205 is not a
request to ratify new law, it is a request to give already-declared law a home in `C05`.

#218 reports the drift at SEV3. **Promote it to SEV2 once the eleven have homes** — at that
point recurrence is a regression rather than a backlog. Giving them homes edits the
constitution and is **L4**.

### 3.2 — A test that could not fail for its stated reason (#219)

`test_suppression_scanning_stays_linear_on_a_hostile_line` said it existed because a
negative lookahead spanning the rest of the line would reintroduce bounded cost. Swapping
the suppression rule for each design and running its own assertion unchanged:

    linear, two regexes (current)      0.989s   PASS
    rest-of-line negative lookahead    1.066s   PASS
    nested-quantifier lookahead        0.989s   PASS

The gate runs 40 rules per line, so one rule's cost is diluted to nothing. **And the design
was never forbidden** — `AP-D-FINTECH.6b` ships `^(?=.*(?:price|amount|…))`, precisely that
shape, while `AP-S13.1a` and `AP-S13.7a` deliberately bound their scans with `.{0,300}`. The
repository's real discipline is *bound the scan*, and the docstring forbade something the
codebase does.

What it does guard is catastrophic backtracking, where the reasoning holds exactly: 355× the
median rule on an 18-character line, and no completed scan at 25 characters inside 300
seconds. #210's *"differs by orders of magnitude"* was right about that and wrong about the
lookahead, and the docstring asserted both.

**The replacement's ordering is load-bearing.** An exponential rule does not fail a
full-length pass, it *hangs* it — the first draft timed out at 300s instead of reporting.
The committed form measures a 60-character line first and names the offending rule in 4.9s.

## §5 — The semantic tier could not be measured, and that is the finding

**No prompt change was made. No hypothesis was tested. Do not read anything below as a result.**

Three attempts at a 5-run baseline against `gpt-oss:120b-cloud`:

    attempt 1   1/5 complete in 15 tries
    attempt 2   2/5 complete in 15 tries   (after #225)
    attempt 3   0/5 complete in 15 tries

Two distinct provider faults, and separating them mattered:

**Timeouts** — real eval calls timed at 12s, 25s, 12s, **75s** against a 30s default. This was
ours: a timeout carries no HTTP status, so it matched nothing in `TRANSIENT_STATUSES` and was
never retried, while a `502` on the same endpoint got three attempts. Fixed in #225.

**502 bursts** — timing all 17 fixtures directly gave 12 completions at median 11.1s, max
16.2s, comfortably inside 30s, and **5 outright `HTTPError`s**. So latency is not the dominant
fault. `MAX_ATTEMPTS = 3` with 2s + 4s backoff rides out about six seconds; these bursts are
longer.

Short probes (`say ready`) returned 200 in 2–5s throughout. **The endpoint looks healthy to a
naive check while failing real work** — know that before diagnosing this again.

**Deliberately not done:** raising `MAX_ATTEMPTS` or the backoff. That would complete a
measurement by absorbing a provider outage — fixing the check rather than the thing — and
trades away the property the bound exists for. The endpoint being unmeasurable is a true fact
about the endpoint.

For the next attempt: run five **independent** single runs, not `--runs 5`, which discards all
N when any one of ~17N calls fails. The pool is **8 standards against a limit of 12**, so all
8 are submitted on every review — the premise hypothesis (a) rests on, now confirmed.
Hypothesis (b), reordering the `S1.105` catalogue entry so its exemption leads, remains the
cheapest untested lever. **Recall must not fall. Five runs per condition. One change at a time.**

## §7 — Traps this session confirmed or added

Everything in `handoff-2026-08-02.md` §6 still holds. Added:

- **A closing keyword near an issue number closes it, even when the sentence denies it.**
  This has now happened twice, in both directions, and both times it closed an issue the
  author was explicitly describing as *unfixed*:

      #212's commit body   "...filed rather than fixed: #213 above, and #214"   -> closed #213
      #225's PR body       "## This does not close #138"                        -> closed #138

  GitHub matches `fixed: #213` and `close #138` as substrings and reads no negation, no
  colon boundary and no surrounding clause. In both cases the issue was reopened only
  because a later session re-derived the finding from scratch and noticed the state was
  wrong — #213 sat closed-as-completed with its symptom reproducing verbatim.

  **Never put an issue number within a few words of** close, closes, closed, fix, fixes,
  fixed, resolve, resolves or resolved **unless you mean it.** Write "#138 stays open" or
  "this is not a fix for #138". Verify with `gh issue list --state open` after any merge
  whose body mentions issues it does not close.

- **`gh pr merge` was not blocked here.** Single invocations succeeded; a `for` loop over
  several was refused. Merge one per command.
- **A squash-merged parent turns a stacked PR into a conflict.** `git rebase --onto
  origin/main <parent> <branch>` drops the duplicate; do not hand-resolve.
- **`gh project item-add` reported success without adding**, once, exactly as documented.
  Verify every time with `item-list`; the retry then worked.
- **A short liveness probe is not an endpoint health check.** 2–5s `200`s while real
  requests failed 5/17.
- **A hang is a worse test failure than a `FAIL`.** Order cheap adversarial probes before
  expensive ones so a pathological input is named rather than left to burn a job timeout.
- Git Bash stdout is still cp1252 and mangles `—` and `·` in captured output. The files are
  UTF-8; the terminal is not.
