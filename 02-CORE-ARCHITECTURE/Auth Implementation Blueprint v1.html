Section 1

Database Architecture — All Tables

Polymorphic Design · Complete Schema · Both Stacks
1.1Design Principle — Polymorphic from Day One
Foundation

Adding a new authentication method adds a row to an enum and uses existing columns—never requires restructuring. The Credentials table is the centerpiece. This makes passkeys a configuration change rather than a migration.

Section 2

Registration Flow

Both Stacks · Full Validation Pipeline
2.1Registration — Step by Step
Both Stacks

Route: POST /api/v1/auth/register · Body: { name, email, password } · Headers: X-Request-ID

1
Rate Limit Check — Redis: 10 registrations/IP/hour. Exceeded → 429.
2
Password Breach Check — SHA-1 hash → first 5 hex chars to HIBP API (k-anonymity). Found → 400: "This password has appeared in data breaches."
3
Password Strength Validation — Min 8 chars, 1 uppercase, 1 digit, 1 special char. Not on common passwords list. Client validates first, server is authoritative.
4
Email Normalization — Trim, lowercase, Gmail: strip dots and +alias. Check email_normalized for existing accounts (including soft-deleted).
5
Duplicate Detection — EXISTS and ACTIVE → return 200 (not 400—prevents enumeration): "If eligible, a verification email has been sent." Actually send "You already have an account" email. EXISTS and DELETED → same 200 response, do NOT reactivate. DOES NOT EXIST → proceed.
6
Institutional Domain Check (if configured) — Extract domain. If not in allowed_domains → 200: "If eligible…" + guidance message. No account created.
7
Account Creation — bcrypt(password, cost=12) → password_hash. INSERT User + Credentials(type=PASSWORD). Generate 32-byte verification token → SHA-256 → INSERT VerificationToken. Send verification email. AuditLog: REGISTRATION_COMPLETED.
8
Response — Always 200: "Account created. Please check your email to verify." (Strict mode: cannot login until verified. Progressive mode: limited access granted immediately.)
Section 3

Email Verification Flow

Both Stacks · Strict & Progressive Modes
3.1Verification Token Lifecycle
Both Stacks
1
Token Generation — 32-byte crypto.randomBytes(). SHA-256 hash → VerificationToken table (type: EMAIL_VERIFICATION, expires: NOW()+24h). Raw token → email link: /verify-email?token={raw}.
2
User Clicks Link — GET /verify-email?token={raw}. Hash raw → query VerificationToken by token_hash. Not found/expired/used → "Link invalid or expired. Request a new one." Valid → UPDATE User.email_verified = NOW() → DELETE VerificationToken → AuditLog: EMAIL_VERIFIED.
3
Resend Verification — POST /api/v1/auth/resend-verification. Rate limit: 3/hour/user. Delete old EMAIL_VERIFICATION tokens for user. Generate new token, send new email.

Strict mode (Reserve Bank, SyncUp): Unverified users cannot access protected routes. Redirected to /verify-email page. Progressive mode (FundsLink, Maphophe): Limited access—browse, save preferences. Sensitive ops (transactions, applications) require verification.

Section 4

Next.js Stack — Credential Login & OAuth

Maphophe · SyncUp · All Next.js Systems
4.1Credential Login — Every Failure Mode
Next.js

Route: POST /api/v1/auth/login · Body: { email, password } · Headers: X-Request-ID

1
Rate Limit — Redis GET rate:ip:{ip}:auth. ≥10 → 429 with Retry-After.
2
Normalize & Query — email_normalized lookup WHERE deleted_at IS NULL.
3
Not Found — bcrypt.compare() against DUMMY hash (timing attack prevention). 401: "Invalid email or password". AuditLog: LOGIN_FAILED reason:user_not_found.
4
State Checks — email_verified (strict), account lock (Redis EXISTS lock:account:{id}), password (bcrypt). 5 failures → SET lock:account:{id} TTL 900 + security email. ALL return identical 401.
5
Success — NextAuth.authorize() → Session row → HttpOnly cookie → DEL rate counter → AuditLog: LOGIN_SUCCESS → 200 ApiResponse<User>.
4.2OAuth Login — NextAuth Provider System
Next.js

NextAuth handles full OAuth dance: state (CSRF), PKCE, token exchange, userinfo. Institutional domain check post-callback. Account linking by email matching. SyncUp: Google + GitHub. Maphophe: Google. Domain rejection → redirect /login?error=domain_not_allowed.

Section 5

Next.js — Password Reset & Session Management

A30 & A35 Implementation
5.1Password Reset — Complete Flow
Next.js
1
Request — POST /api/v1/auth/forgot-password { email }. Rate limit: 3/IP/hour. ALWAYS return: "If an account exists, a reset link has been sent."
2
Token Generation (internal) — If email exists: 32-byte random → SHA-256 → VerificationToken (type:PASSWORD_RESET, expires:NOW()+1h). Email with raw token link. AuditLog: PASSWORD_RESET_REQUESTED.
3
Validation — Hash received token → query. Invalid/expired → "Link invalid." Valid → show reset form.
4
Execution — POST /api/v1/auth/reset-password { token, new_password }. Re-validate + breach check + strength check. Hash new password → UPDATE User → DELETE VerificationToken → DELETE ALL Session rows for user (A35). AuditLog: PASSWORD_CHANGED method:reset.
5.2Session Management — User-Facing API
Next.js

GET /api/v1/auth/sessions — Returns: session ID (not token), device info, IP (last octet masked), created, expires, "current session" flag. DELETE /api/v1/auth/sessions/{id} — Verify ownership → DELETE row → AuditLog: SESSION_TERMINATED. DELETE /api/v1/auth/sessions?scope=others — DELETE WHERE userId=? AND id≠current → AuditLog: ALL_SESSIONS_TERMINATED.

Section 6

Angular+FastAPI — JWT Login & Token Generation

FundsLink · Reserve Bank · All Angular+FastAPI Systems
6.1Credential Login — JWT Issuance
Angular+FastAPI

Rate limiting + email normalization + password verification identical to Next.js flow. On success:

Access Token (15 min)
RS256 JWT payload: {version:1, sub, role, email, iat, exp:+900, jti:uuid}. Returned in response body. Angular stores in AuthService memory only.
Refresh Token (7 days)
64-byte crypto.randomBytes() → SHA-256 → RefreshToken table. Raw in HttpOnly/Secure/SameSite=Strict cookie scoped to /api/v1/auth. Path-restricted — never sent with general API calls.
6.2Password Reset (Angular+FastAPI)
Angular+FastAPI

Identical token lifecycle as Next.js. Post-reset: UPDATE RefreshToken SET revoked_at=NOW() WHERE user_id=? AND revoked_at IS NULL + add all active JTIs to Redis deny-list → All devices logged out → AuditLog.

Section 7

Angular+FastAPI — Refresh, Logout, Guards

Critical Path · Replay Detection · Cross-Tab Sync
7.1Token Refresh — Complete Flow with Replay Detection
Angular+FastAPICritical

Trigger: Angular HTTP Interceptor receives 401 → checks AuthService.refreshInProgress.

1
Deduplication — If refreshInProgress exists → return existing promise. If not → create promise, store in AuthService.refreshInProgress. POST /api/v1/auth/refresh (cookie auto-attached).
2
Token Not Found/Expired — 401 + clear cookie + AuditLog: REFRESH_FAILED.
3
REPLAY DETECTED — Token found but revoked_at NOT NULL. IMMEDIATE: UPDATE RefreshToken SET revoked_at=NOW() WHERE user_id=? → Redis deny-list all JTIs → Sentry alert → Security email → Clear cookie → AuditLog: TOKEN_THEFT_DETECTED → 401.
4
Rotation — Old token: revoked_at=NOW(), replaced_by=new_id. New access (15min) + refresh (7d) issued. New HttpOnly cookie. Angular stores new access token → clears refreshInProgress → retries queued requests. User sees nothing.
7.2Concurrent Refresh — Detailed Race Condition Prevention
Angular+FastAPI

Dashboard loads 3 API calls simultaneously. All have expired tokens. All receive 401. Request 1: creates refresh promise, stores in AuthService. Requests 2 & 3: detect existing promise, attach to it. All three resolve with same new token. Only one /auth/refresh call made. Without this: Request 2 presents now-revoked old token → replay detected → user logged out everywhere.

7.3Logout — Coordinated Three-Step Process
Angular+FastAPI
1
FastAPI: Extract cookie → hash → UPDATE revoked_at=NOW(). Extract JTI → Redis SET deny:jti:{jti} EX {remaining_life}. Clear cookie Set-Cookie Max-Age=0. AuditLog: LOGOUT.
2
Angular: AuthService.accessToken=null. BroadcastChannel.postMessage({type:'LOGOUT'}). Router navigate /login.
3
Cross-Tab: All tabs receive broadcast → clear token → redirect /login. All redirect simultaneously. Redis down? Access token valid ≤15min—acceptable risk vs blocking logout.
Section 8

Shared Implementation — Both Stacks

8.1Email Normalization
Both

Trim whitespace → lowercase → Gmail: strip dots from local part, strip +alias. Store BOTH original and normalized. Query by normalized, display original.

8.2Password Breach Detection
Both

SHA-1 hash password → first 5 hex chars to HIBP API (k-anonymity model—full hash never sent). Check if full suffix in results. Found → reject: "This password has appeared in known data breaches."

8.3Indistinguishable Error Responses
Both
EndpointAlways Returns
Login (wrong, deleted, locked, unverified)401: "Invalid email or password"
Forgot password200: "If an account exists, a reset link has been sent"
Registration (exists, deleted, domain blocked)200: "If eligible, a verification email has been sent"
8.4Rate Limiting — Three-Layer Implementation
Both

Layer 1 (Per-IP): Redis INCR rate:ip:{ip}:auth, EXPIRE 900. ≥10 → 429 with Retry-After. Layer 2 (Per-Account): Redis INCR rate:account:{userId}:login, EXPIRE 900. ≥5 → SET lock:account:{userId} EX 900 + security email. Layer 3 (Global): Redis INCR rate:global:auth, EXPIRE 60. ≥1000 → 429. Redis failure fallback: Per-IP skips (fail open). Per-account checks PostgreSQL AuditLog (slower). Global skips (fail open). Log alert: "Rate limiting degraded."
