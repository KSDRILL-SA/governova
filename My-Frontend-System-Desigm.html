PART 1 / RULES 1–10 Architecture 7 Critical · 2 High · 1 Medium
RULE 01 One Adaptive System Critical

ONE adaptive system — NEVER build separate mobile and desktop apps. One codebase adapts to all screen sizes using responsive design.

Enforcement
Architecture review + code audit
Violation
mobile/ and desktop/ folders; duplicate component trees
Compliance
Single component with sm: md: lg: responsive classes
Why It Fails
2× work, 2× bugs, divergent UX. No benefit whatsoever.
RULE 02 Mobile-First Design Critical

Design for 320px width FIRST, then enhance with sm: md: lg: breakpoints. Base CSS is always mobile. Larger screens are additions, not defaults.

Enforcement
Code review + visual regression test
Violation
Desktop-first CSS with max-width media queries
Compliance
Base styles for 320px; md: for tablet; lg: for desktop
❌ Desktop-first (Wrong)
/* Starts at large, shrinks down */
.hero { width: 1200px; font-size: 24px; }
@media (max-width: 768px) {
  .hero { width: 100%; font-size: 18px; }
}
✅ Mobile-first (Correct)
/* Starts at 320px, grows up */
<h1 className="text-xl sm:text-2xl
  md:text-3xl lg:text-5xl">
<div className="p-4 md:p-8 lg:p-12">
RULE 03 Brand Visibility — Always Critical

NEVER hide the brand or logo on any screen size. Minimum 20px font on mobile. Brand identifies the site — removing it removes trust and orientation.

Enforcement
Visual regression + a11y audit
Violation
<Logo className="hidden md:block">
Compliance
Logo always rendered; resizes to minimum 20px on mobile
RULE 04 Hero Section — No Fixed Height Critical

Hero sections MUST use min-height, NEVER h-[500px] or any fixed height. Content grows; containers must grow with it or content gets clipped on mobile.

Forbidden
h-[500px] h-[600px] height: 500px
Compliance
min-h-[500px] or min-h-screen
❌ Content clips on mobile
<section className="h-[500px]">
  {/* Content overflows or clips */}
✅ Content always fits
<section className="min-h-[500px]
  flex flex-col justify-center">
RULE 05 Mobile Testing — Mandatory Before Merge High

All layouts MUST pass visual testing at 320px, 375px, and 390px before a feature is considered complete. A feature is not done until it works on the smallest phone.

Enforcement
CI visual regression + manual QA gate
Violation
Feature merged without mobile screenshot test passing
Devices
320px (iPhone SE) · 375px (iPhone 12) · 390px (iPhone 15, Pixel)
RULE 06 Desktop Navigation — Full Navbar Always Visible High

On desktop, the full navbar is always visible. Hamburger menus are reserved for secondary/additional navigation only — never as the primary nav mechanism on desktop.

Violation
Primary nav hidden behind hamburger on desktop
Compliance
Full navbar visible at lg:; hamburger for secondary items only
RULE 07 Hamburger Opens Horizontally — Never Accordion Critical

When the hamburger menu opens, it MUST open as a horizontal dropdown directly below the header. Vertical accordions that push page content down are absolutely forbidden.

Forbidden
Vertical list that pushes page content down on toggle
Compliance
Horizontal overflow-x-auto row below header; overlay only
RULE 08 Core Nav Items Have Breathing Room Medium

Core navigation items (Home, Products, Pricing, Contact) must have adequate padding and visual separation. Maximum 5–6 core items. Crowded nav signals poor information architecture.

Max Items
5–6 core nav items
Spacing
gap-6 lg:gap-8 minimum between items
RULE 09 Mobile Navigation — Bottom Sheet or Horizontal Scroll High

On mobile, the hamburger opens either a bottom sheet drawer (6+ items) or a horizontally scrollable row (4–6 items). Never a vertical accordion. Both patterns are fully implemented in the implementation guide.

Option A (4–6 items)
Horizontal scroll row — flex overflow-x-auto gap-4 px-4
Option B (6+ items)
Bottom sheet — fixed inset-x-0 bottom-0 rounded-t-2xl
mobile-nav.tsx — both patterns
// OPTION A — Horizontal scroll (4–6 items)
{open && (
  <div className="border-t lg:hidden">
    <div className="flex gap-4 overflow-x-auto px-4 py-3 scrollbar-hide">
      {navItems.map(item => (
        <a key={item.href} href={item.href}
           className="whitespace-nowrap text-sm py-2">
          {item.label}
        </a>
      ))}
    </div>
  </div>
)}

// OPTION B — Bottom sheet (6+ items)
{open && (
  <>
    <div className="fixed inset-0 z-40 bg-black/40"
         onClick={() => setOpen(false)} />
    <div className="fixed inset-x-0 bottom-0 z-50
         bg-white rounded-t-2xl shadow-2xl border-t pb-safe">
      <div className="p-4 grid grid-cols-2 gap-3">
        {navItems.map(item => (
          <a key={item.href} href={item.href}
             className="p-3 rounded-lg border text-sm font-medium">
            {item.label}
          </a>
        ))}
      </div>
    </div>
  </>
)}
RULE 10 Vertical Accordion Navigation — Forbidden Absolutely Critical

Any navigation pattern that expands vertically and pushes page content down when a hamburger is clicked is FORBIDDEN. This includes all accordion, collapsible list, and slide-down nav patterns.

!
Why this fails: Vertical nav push is disorienting and kills perceived performance. The user loses their scroll position and the visual hierarchy collapses. Use overlay, horizontal scroll, or bottom sheet — always.

RULE 11Touch Targets — Minimum SizesCritical

Touch targets must be minimum 44×44px on mobile and 32×32px on desktop. Small targets cause miss-taps, frustration, and accessibility failures (WCAG 2.5.5).

Mobile Minimum
min-h-[44px] min-w-[44px]
Desktop Minimum
min-h-[32px] min-w-[32px]
Violation
w-6 h-6 (24px) icon buttons without padding wrapper
WCAG
2.5.5 Target Size
RULE 12Body Text — Minimum 16px on MobileHigh

Body text must be minimum 16px on mobile (18px recommended). Text smaller than 16px forces zooming, breaks readability, and degrades trust.

Violation
text-xs (12px) or text-sm (14px) for body copy
Compliance
text-base (16px) minimum; text-lg (18px) preferred
RULE 13Respect prefers-reduced-motionHigh

All animations MUST be disabled when the user's OS has prefers-reduced-motion enabled (WCAG 2.3.3). Include this in globals.css for all projects.

globals.css — required in every project
/* Respect OS-level motion preference — WCAG 2.3.3 */
@media (prefers-reduced-motion: reduce) {
  *, ::before, ::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
RULE 14Keyboard Accessibility — All Interactive ElementsCritical

Every interactive element must be reachable via Tab and activatable via Enter/Space. Never remove focus styles. Custom components need tabIndex and onKeyDown handlers (WCAG 2.1.1).

Violation
Custom <div> button without role="button" tabIndex={0}
Violation
outline-none with no replacement focus ring
Compliance
Use <button> for actions; focus-visible:ring-2 for focus
RULE 15WCAG 2.1 AA Contrast — Required for All TextCritical

All text must meet WCAG 2.1 AA contrast requirements. Normal text: 4.5:1 ratio. Large text (18px+ or 14px+ bold): 3:1 ratio. This is enforced in CI via automated contrast checks.

RULE 16No Emojis in UI — With Documented ExceptionsCritical

Emojis are FORBIDDEN in all production UI code: React components, user-facing notifications, error messages, aria labels, and console output visible to users. They are unprofessional, platform-inconsistent, and not accessible.

Permitted Exceptions (Not UI Code)
  • Internal documentation (this constitution, README files, ADRs)
  • Git commit messages and PR descriptions
  • Developer CLI output and tooling
  • Code review comments between developers
Enforcement
ESLint rule: no-emoji-in-ui
Violation
<div>🚀 Welcome!</div>
Compliance
<div>Welcome to Dashboard</div>
RULES 17–20Icon System — Priority Chain and ConsistencyHigh

Icons follow a strict priority chain. All icons must have consistent stroke width (Lucide default: 2px) and support hover states. Never mix icon sets without documenting why.

Rule 17 — First Priority

RULE 28Three States for Every Async OperationCritical

Every async operation requires all three states: skeleton loader (loading), error message with X-Request-ID (error), and the actual content (success). NO blank screens — ever.

user-list.tsx
const { data, isLoading, isError, error } = useQuery(...);

// State 1: Loading — never blank
if (isLoading) return (
  <div className="space-y-4">
    <Skeleton className="h-16 w-full" />
    <Skeleton className="h-16 w-full" />
  </div>
);

// State 2: Error — always show request ID for support
if (isError) return (
  <ErrorMessage message={error.message} requestId={error.requestId} />
);

// State 3: Success — render data
return <UserList users={data} />;
RULE 29Inline Form Validation — Under Each FieldCritical

Every form field with a validation error MUST show that error directly beneath the field. Toast notifications are supplementary, never the primary error mechanism.

login-form.tsx — React Hook Form + Zod
const loginSchema = z.object({
  email:    z.string().email('Invalid email address'),
  password: z.string().min(6, 'Password must be at least 6 characters')
});

const { register, handleSubmit, formState: { errors, isSubmitting } } =
  useForm({ resolver: zodResolver(loginSchema) });

// In JSX — error appears under the field
<div>
  <input {...register('email')}
         className={`w-full border rounded p-2 ${errors.email ? 'border-red-500' : ''}`} />
  {errors.email &&
    <p className="text-red-500 text-sm mt-1">{errors.email.message}</p>}
</div>

// Button respects form state
<button disabled={isSubmitting}
        className="flex items-center gap-2 disabled:opacity-50">
  {isSubmitting && <Spinner className="w-4 h-4 animate-spin" />}
  {isSubmitting ? 'Signing in...' : 'Sign In'}
</button>
RULE 30Zod Validation on Every API CallCritical

Every API call must validate BOTH the request payload and the response. Types must be derived from Zod schemas — never manually duplicated. Unsafe data reaching the UI causes silent runtime crashes.

lib/api/auth.ts
import { z } from 'zod';

// Schema is the source of truth
export const LoginResponseSchema = z.object({
  token: z.string(),
  user:  z.object({
    id:    z.string(),
    email: z.string().email(),
    name:  z.string().optional()
  })
});

// Type is DERIVED from schema — never manually written
export type LoginResponse = z.infer<typeof LoginResponseSchema>;

export async function login(email: string, password: string) {
  const res = await apiClient.post('/auth/login', { email, password });
  // Throws if response doesn't match schema
  return LoginResponseSchema.parse(res.data);
}

RULE 61X-Request-ID — Every API CallHigh

Every outgoing API request MUST include an X-Request-ID header (UUID v4). On any 4xx or 5xx error response, display this ID to the user as a support reference code.

lib/api/client.ts
// API client wrapper — generates X-Request-ID per request
async function apiRequest(url: string, options: RequestInit) {
  const requestId = crypto.randomUUID();

  const response = await fetch(url, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      'X-Request-ID': requestId,
      ...options.headers
    }
  });

  if (!response.ok) {
    throw new ApiError(response.status, requestId, response);
  }
  return response;
}

// On 5xx error — show to user for support
// "Something went wrong. Error ID: {requestId}"

A single centralized error handler maps every backend error code to a user-facing message and action. All API calls use it — no direct try/catch bypass allowed.

RULE 63429 Rate Limit UX — Countdown + BackoffHigh

On 429 response, extract retry-after, disable the triggering UI element, show a countdown timer, and implement exponential backoff for auto-retries (max 3). Never retry automatically on auth endpoints.

lib/api/retry.ts
const retryAfter = parseInt(response.headers.get('Retry-After') || '5');

// Disable button, show countdown to user
setButtonDisabled(true);
setCountdown(retryAfter);

// Countdown tick
const timer = setInterval(() => {
  setCountdown(prev => {
    if (prev <= 1) { clearInterval(timer); setButtonDisabled(false); return 0; }
    return prev - 1;
  });
}, 1000);

// Exponential backoff: 1s → 2s → 4s (max 3 retries)
async function retryWithBackoff(fn: () => Promise<any>, attempt = 0) {
  if (attempt >= 3) throw new Error('Max retries reached');
  await sleep(1000 * Math.pow(2, attempt));
  return fn().catch(() => retryWithBackoff(fn, attempt + 1));
}
RULE 64WebSocket Chat Governance — ConditionalHigh (if chat in v1)

If WebSocket chat is in v1, the frontend MUST implement: exponential backoff reconnection (1s→2s→4s→8s→16s, max 5 attempts), streaming token display, offline message queue with replay, connection status indicator, and message deduplication via client-generated IDs.

Backoff Sequence
1s → 2s → 4s → 8s → 16s (5 attempts max, then fail gracefully)
Message Queue
Queue messages on disconnect; replay on reconnect
Deduplication
Client-generated UUID per message; ignore duplicates on replay
Status Indicator
Visible connection state: Connected / Reconnecting... / Offline
RULE 65Feature Flags — Consumed from Backend, Never HardcodedHigh

Feature flags are fetched from GET /api/v1/features on app startup and cached for 5 minutes. Never hardcode flags. Unknown flag name always returns false.

lib/hooks/use-feature-flag.ts
// Fetch on startup, cache 5 minutes
const { data: flags } = useQuery({
  queryKey: ['feature-flags'],
  queryFn: () => api.get('/api/v1/features'),
  staleTime: 5 * 60 * 1000, // 5 minutes
});

// Hook — unknown flag defaults to false
function useFeatureFlag(name: string): boolean {
  return flags?.[name] ?? false;
}

// Usage
const isNewDashboard = useFeatureFlag('new-dashboard');
{isNewDashboard && <NewDashboard />}

// ❌ FORBIDDEN — hardcoded flag
// const isNewDashboard = true;
