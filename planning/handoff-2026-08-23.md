# Handoff — 2026-08-23

**The session Governova was pointed at somebody else's repository for the first
time.** The first command failed for a reason that had nothing to do with the code
it was reading, and neither did the second.

Read §7 first if you only read one section. It is the work order, and everything
in it is now downstream of a release that has already gone out.

---

## 1. `0.2.3` shipped, and the gate now runs somewhere else

**Two releases went out on 2026-08-23.** `0.2.2` first, then `0.2.3` after the engine was
pointed at four repositories it had not written.

`0.2.3` — tag `v0.2.3`, run `32625786562`, success. It is the first release the changelog gate
from `#343` stood in front of, and both checks passed in production:

```
✓ The tag must match the packaged version
✓ The changelog must say this version shipped
```

### The gate runs on four external repositories

`governova-enforce --changed` is wired into `fundslink-academy`, `sunduza-architectural`,
`osi-tcpip-visualizer` and `Xkimi-Xa-Mali` — **three different GitHub owners** — and each gate
proved itself on its own pull request before it landed, in 11–16 seconds.

**The composite action was deliberately not used.** `platform/surfaces/cicd-enforcer` lives in a
private repository, and a private action cannot be resolved from a repository under a different
owner. The *package* is public even though the repository is not, so `pip install governova`
works everywhere and reads identically in all four. Three of the four would have failed with a
confusing resolution error otherwise.

`--changed` scans the diff, not the tree, so existing debt does not block work that did not
touch it. Two real findings are therefore waiting rather than firing:
`fundslink-academy`'s hardcoded fallback DSN with an embedded password, and `Xkimi-Xa-Mali`'s
undeclared `D-FINTECH` domain — 182 findings that are mostly true, and a decision that should
not be a side effect of adding a workflow.

### The approved v1 scope

Persistence, billing, the Angular console, the marketing site. The Intelligence Gateway, the
four stub surfaces and Certification are **v2** — deferred deliberately, the way the Cloud
itself was. Writing that down as an ADR is the next task; a deferral that lives only in a
conversation is a backlog.

## 1a. `0.2.2` shipped

**Published to PyPI on 2026-08-23.** Tag `v0.2.2`, release run `32618475154`,
success, published in 23s with digital attestations. PyPI lists `0.1.0`, `0.2.0`,
`0.2.1`, `0.2.2`, with `0.2.2` as latest.

Every gate re-ran against the exact commit before anything shipped, including
*"The wheel must carry the core constitution, and only the core"* and *"The built
wheel must work with no repository present"*.

**Verified the way an adopter meets it** — clean virtualenv,
`pip install governova==0.2.2` from PyPI, run against `Xkimi-Xa-Mali`:

```
governova --version    ->  0.2.2
governova enforce .    ->  ✓ no blocking violations   (exit 0)
governova onboard      ->  1m11s, bundled index resolved, no checkout present
governova govscore     ->  honest partial assessment
```

Two hours earlier the same three commands produced: *no such command*, then 201
blocking findings from a domain the project had never declared.

`0.2.1` shipped the day before — run `32568392219`, 1m57s at 10:44 on 2026-08-22
— and is the build this release exists to replace.

### What the tag needed first

`#341` prepared it, and two of the three items would have failed the release
outright rather than producing a bad one:

- **`scripts/pyproject.toml` still read `0.2.1`.** `release.yml` compares the tag
  against the packaged version and hard-errors on a mismatch, so the tag would
  have been rejected at the first step.
- **`uv.lock` still pinned `0.2.1`**, and the release workflow installs
  `--frozen`. The lock is part of a release rather than a by-product of one.
- The `0.2.1` changelog entry still said `unreleased` a day after it shipped, and
  had never been given its compare link.

**And then `0.2.2` did it too.** The entry was written as `unreleased` because at
the time it was, and the tag went out without anyone going back. Caught the same
hour rather than the next session, but it is the second occurrence of one
mistake, so it is a process gap rather than an oversight: **the changelog date is
part of tagging, not part of preparing.**

**Closed.** `release.yml` now refuses to publish a version whose changelog entry
is not dated `YYYY-MM-DD`, in `verify` — before anything is built, beside the step
that already checks the tag against the packaged version. Both are the same kind
of check: the tag claims a version, and the changelog claims it shipped.

The check lives in YAML, where nothing type-checks it and no ordinary test would
reach it, so six tests **extract the script from the workflow** and run it — never
a copy, which would pass forever while the workflow ran something else. Verified
by mutation: disabling the date validation fails three of them. A release gate
that cannot fail for its stated reason is worse than no gate, because it is a
gate everybody believes in.

**The tag itself is L4.** It was taken on the founder's explicit instruction —
the decision theirs, the mechanics delegated. Recorded here rather than left
implicit, because "human-only, always" is written in three places in this
repository and the record should show why an agent's hand was on it.

## 2. The adopter run — what `0.2.1` did

Installed `governova==0.2.1` from PyPI into a fresh virtualenv — never the source
checkout, since that is the blind spot that hid both `0.2.0` defects — and ran it
against `Xkimi-Xa-Mali`: a Turbo/Next.js monorepo, 711 TypeScript files,
`node_modules` on disk. A non-Python stack, which tests the dependency-exclusion
fix harder than the case it was written for.

### What held

**The `SKIP_DIRS` fix generalises.** 388 findings, **zero** from `node_modules`.
All 388 in `apps/` and `packages/` across 122 files. Measured against Python's
`.venv`, and it carries to a JavaScript dependency tree unchanged.

**`resolve_index_path` held.** The wheel-bundled index resolved without
complaint. No `no compiled index` anywhere.

**`onboard` is the strongest surface in the product.** It detected node/nextjs/
react, Prisma, GitHub Actions and the test suite with no configuration, then
refused to guess domain and phase and said why in the profile it proposed — *"a
payments ledger and a lesson planner can be structurally identical"*. Its heatmap
declared 75 of 106 standards undetermined and stated that undetermined is never
counted as satisfied.

### What did not

Six defects. Five fixed this session, one filed.

## 3. The finding that matters — `#325`

`onboard` printed:

> no Layer 4 domain declared — sector standards are not counted, and no scan can
> tell which sector this system serves

and proposed a profile with `domains` commented out. `governova-enforce .` then
failed the build with **201 blocking findings, 199 of them `AP-D-FINTECH.1a`** —
a Layer 4 standard from the domain the profile had just declined to declare.

`applicable_standards` has filtered by declared domain since it was written. The
**scanner** never did, and `scan_paths` feeds six surfaces. So the assessment
model and the merge gate answered to different bodies of law, and the gate was
the one that fails builds.

**The adopter genuinely is fintech, so the findings were true. They were true by
luck.** A lesson planner that types a course fee as a plain number receives the
identical build failure from law it has never adopted.

Of the 201 findings that failed that build: 199 from undeclared law, 2 false
positives. **Zero survived as applicable and correct.**

This is the same shape as the `0.2.0` defect — two branches of the product
answering one question differently, the CI-shaped branch correct, the
human-facing one not, and nothing noticing for as long as both existed. There the
split was inside one function. Here it was between two commands.

`governova_checks.applicability` now partitions findings by declared domain, and
every surface that acts on a finding routes through it. Withheld findings are
counted and named, never dropped in silence — a gate that quietly stops checking
something is the same defect in the opposite direction.

## 5. Two defects found while fixing the others — filed, then fixed

**The board report could not show a Layer 4 finding.** `governova_report.compute`
tallies into `index.constitutions`, and the index keeps `domains` in a separate
list — so a domain finding is dropped whether or not the project declared it.
This is the mirror of `#325`: that one applied sector law to projects that never
adopted it, this one withholds it from the board of a project that did. The
sector standards are the ones with a regulatory basis behind them (PCI-DSS, FICA,
FATF), and a report structurally incapable of showing such a finding is worse
than one that omits the section, because the omission reads as an absence.
`test_no_surface_applies_undeclared_layer_4_law` exempted `governova_report`
and documented this as the reason. Fixed, and the exemption is gone: areas are
now the core constitutions plus the domains the profile declares. This
repository declares D-SAAS, so its own report gained a sixteenth area.

**`onboard` took 9m15s, and the obvious cause was wrong.** `assess` does scan
twice — once directly, once inside `compute_score` — and a comment three lines
above that call explains that `enforced_clean_standards` was recomputed rather
than called *because calling it would scan a second time*. The reasoning had been
applied to the cheaper of the two. It looks like the answer. **It is 8% of the
runtime**, and an issue body asserting otherwise was written before it was
profiled, which is the near-miss worth recording.

Profiling said `run_probes` was 81%. The tree was being enumerated in full and
filtered afterwards — `root.rglob("*")` returning **104,536 entries in 6.4s where
a pruned walk finds 877 in 0.1s** — by `iter_source_files`, by sixteen glob sites
in the probes, and by `governova_schema.find_schema_files`, which alone made
210,567 `stat` calls across two invocations.

**Four private copies of the skip list**, none of which pruned. `walk_files` in
`governova_checks.gather` prunes during the walk and is now the only copy;
`site-packages` joined the shared list, because an installed tree is not always
inside a `.venv`.

| | Before | After |
|---|---|---|
| `iter_source_files` | 50.6s | 0.3s |
| `run_probes` | 171s | 15.0s |
| `find_schema_files` | 46s | 0.2s |
| **`governova onboard`** | **9m 15s** | **40s** |

**The two reports are byte-identical.** That is the only reason to trust a 14×
speedup.

Two correctness findings fell out of it, neither of them the point of the work:
`_has_language` counts its 4000-entry budget *before* the dependency test, so it
can answer "no TypeScript" about a TypeScript repository — on the adopter it
reached that repo's own first `.ts` at entry 2556 of 4000, right with 36% to
spare, where the margin is a property of how many packages happen to be
installed. And `roadmap.find_characterisation_tests` matched a file *name* across
an unpruned tree, so a dependency's test could be offered to the reader as their
own project's characterisation test.

## 6. Standing rules, confirmed the hard way

- **The self-scan is not decoration.** `test_this_repository_scans_clean` caught
  `AP-D-FINTECH.1a` firing on a docstring sentence *describing that rule
  over-firing*. It keys on a name-and-type shape with no regard for whether the
  line is code at all — the same imprecision from a third direction, and still
  untouched.
- **Regenerate every number.** The Governova Score is unchanged at **80 (B)**
  after the domain filter. The violation-rate factor now reads `100/100 clean
  across 108 source file(s); 1 withheld (D-FINTECH not declared)`.
- **`uv` is not on PATH** — `C:\Users\kurhu\AppData\Local\Python\pythoncore-3.14-64\Scripts`
- **mypy runs from `scripts/`**, not the repo root, or it finds the same module
  under two names and checks nothing.
- **`pytest --timeout` is not installed.** Passing it fails collection outright.
- **The full suite takes ~7 minutes** and its output is block-buffered when
  redirected, so progress is invisible until it ends. Run it in the background
  and wait for the notification rather than polling.
- **`governova stats` reports implementation bindings, `governova coverage` reports
  rules.** `START-HERE.md` read `72 rules` for at least a session because the two were
  conflated. The rule count is 77.
- **Never run `ruff format` repo-wide.** CI runs `ruff check` only.
- **A closing keyword near `#NNN` closes that issue**, even inside a quotation or
  a negation. These PR bodies cite issue numbers heavily and say "Addresses",
  never "Fixes", so every issue was closed by hand after its merge was confirmed.
  `gh issue list` after every merge; nothing closed by accident this session.
- **A test can be about styling when the claim is about content.** Typer colours
  its own help console in CI and not in a captured local run, and its option
  highlighter splits `--changed` across escape sequences. Reproduce with
  `FORCE_COLOR=1` before believing a CI-only failure is environmental drift.
- **L4 is human-only**: ratifying law, amending the constitution, tagging a
  release.

## 8. What this session actually established

The previous handoff asked whether the thing works when somebody else installs
it, and answered no. This one asked whether it works when pointed at somebody
else's *code*, and the answer was also no — for reasons no amount of self-scanning
would have surfaced, because Governova is not a fintech Next.js monorepo and
never trips its own sector rules.

**Every defect in §4 was invisible from this repository.** The pattern from the
last two sessions holds: the finding is always at the boundary, and the boundary
is always somewhere the tool has not been pointed yet.

The engine now produces a usable answer on a foreign codebase, and it is on PyPI
rather than on a branch. That is the thing that was not true yesterday.

**The next finding will be at the next boundary.** `0.2.2` has been measured
against exactly one external repository, and that repository is a Next.js fintech
monorepo whose author also wrote the engine. A Django project, a Go service, or a
repository nobody in this room has seen is where the next `§3` comes from.
